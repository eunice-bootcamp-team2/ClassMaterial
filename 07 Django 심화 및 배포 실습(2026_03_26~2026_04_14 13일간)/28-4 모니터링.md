#### Grafana 패널 구성 하기
```
[ Django AI 요청 수 ]          [ Django 평균 응답 시간 ]  
[ Django p95 응답 시간 ]       [ FastAPI 요청 수 ]

[ Django 4xx 에러율 ]          [ FastAPI 5xx 에러율 ]
[ Django 누적 요청 수 ]         [ FastAPI 누적 요청 수 ]
```
이 구성은 단순히 그래프를 보는 것이 아니고 아래의 내용의 질문데 답할수 있게 설계되었습니다
- 요청이 많아졌는가? (트래픽 증가)
- 응답이 느려졌는가? (성능 저하)
- 특정 구간에서만 느린가? (p95 문제)
- 에러가 발생하고 있는가? (장애 여부)
- 병목이 Django인지 FastAPI인지? (구간 분석)

즉, 이 대시보드는 요청량, 속도, 지연, 안정성을 기준으로  
Django와 FastAPI를 분리하여 전체 시스템 상태를 분석할 수 있도록 구성되었습니다.

대시보드 영구 저장을 위해 Grafana에 **volume** 을 붙여야 합니다.

`backend/docker-compose.yml`
```yaml
  grafana:
    image: grafana/grafana:latest
    container_name: grafana-server
    restart: always
    ports:
      - "3000:3000"
    depends_on:
      - prometheus
    volumes:
    - grafana_data:/var/lib/grafana  
    networks:
      - app-network
```

맨 아래 `volumes:` 도 추가합니다.
```yaml
volumes:
  product_review_postgres_data:
  grafana_data:
```

적용 순서
```bash
docker compose down  
docker compose up -d
```
이후부터는 Grafana가 `/var/lib/grafana` 내용을 볼륨에 저장해서  
컨테이너를 다시 띄워도 대시보드가 유지됩지다.

#### 패널 1: Django AI 요청 수 (RPS) 
사용자가 AI 분석 기능을 얼마나 자주 호출하는지를 보여주는 지표입니다.  
즉, 현재 서버에 들어오는 트래픽의 크기를 실시간으로 확인할 수 있습니다.

쿼리: 매트릭 이름은 반드시 자신의 이름으로 맞춰야 합니다.
```sql
rate(ai_analyze_request_total[1m])
```

뜻:
`ai_analyze_request_total` 는 누적 요청 수(counter)입니다.  
`rate(...[1m])` 는 최근 1분 동안 얼마나 증가했는지를 초당으로 바꿔줍니다.

즉, Django AI 분석 요청이 지금 초당 몇 번 들어오는지 보는 쿼리입니다.

무엇을 하기 위한 조건인가
- 현재 트래픽이 얼마나 들어오는지 확인
- 부하 테스트할 때 요청 수가 실제로 증가하는지 확인

왜 이렇게 작성하나
Counter는 누적값이라 그대로 보면 계속 올라가기만 합니다.  
그래서 현재 속도를 보려면 `rate()`를 써야 합니다.


Unit
```
requests/sec
```

패널 제목
```
Django AI 분석 요청 수
```
---
#### 패널 2:  Django 평균 응답 시간 : 전체적으로 느려졌는지 확인
요청 하나를 처리하는 데 평균적으로 얼마나 시간이 걸리는지를 의미합니다.  
전체적인 서버 속도가 빠른지 느린지를 가장 기본적으로 판단할 수 있습니다.

쿼리
```sql
rate(ai_analyze_duration_seconds_sum[1m])  
/  
rate(ai_analyze_duration_seconds_count[1m])
```

뜻:
히스토그램/서머리 구조에서
- `sum` = 전체 응답 시간의 합
- `count` = 전체 요청 수 입니다.

```
그래서 
최근 (1분 동안의 총 응답시간) / 최근 (1분 동안의 요청 수)  = 평균 응답 시간
```
즉, Django AI 분석 API의 평균 처리 시간을 보는 쿼리입니다.

무엇을 하기 위한 조건인가
- 전체적으로 서버가 느려졌는지 확인
- 평균 속도가 안정적인지 확인

왜 이렇게 작성하나?
평균은 합계 ÷ 개수로 구합니다.  
Prometheus에서는 누적값이므로 `rate(sum) / rate(count)` 형태로 계산합니다.


Unit
```bash
requests/sec
```

패널 제목
```bash
Django 평균 응답 시간
```

#### 패널 3: Django p95 응답 시간 : 느린 일부 요청을 본다
전체 요청 중에서 느린 상위 5% 요청의 응답 시간을 보여줍니다.  
일부 요청만 유난히 느려지는 병목 현상을 확인할 때 중요합니다.

쿼리
```sql
histogram_quantile(
  0.95,
  sum(rate(ai_analyze_duration_seconds_bucket[1m])) by (le)
)
```

뜻
이건 Django 응답 시간의 p95를 구하는 쿼리입니다.

p95는 전체 요청 중 느린 상위 5% 직전의 응답 시간입니다.

쉽게 말하면, 대부분은 괜찮아 보여도, 일부 느린 요청이 얼마나 느린지 보는 값입니다.

무엇을 하기 위한 조건인가?
- 평균은 정상인데 일부 요청만 느려지는지 확인
- 병목 시작 신호를 찾기 위해 사용

왜 이렇게 작성하나?
히스토그램 메트릭의 백분위수는 `histogram_quantile()`로 구합니다.  
`bucket` 값을 `le` 기준으로 묶어서 계산해야 p95를 구할 수 있습니다.


Unit
```bash
requests/sec
```

패널 제목
```bash
Django p95 응답 시간
```

Django에서 FastAPI로 전달되는 AI 계산 요청의 양을 보여줍니다.  
즉, 실제 AI 서버가 얼마나 일을 하고 있는지를 확인할 수 있습니다.

#### 패널 5: FastAPI 평균 응답 시간
AI 서버가 요청을 처리하는 데 평균적으로 얼마나 걸리는지를 나타냅니다.  
AI 모델 처리 속도가 전반적으로 안정적인지 판단할 수 있습니다.

쿼리
```sql
rate(http_request_duration_seconds_sum{handler="/api/v1/recommend/similarity"}[1m])
```

- Django 평균 응답 시간과 비교해서 어느 쪽이 더 느린지 확인

이기 때문입니다.  특정 handler만 필터링해서 해당 API만 측정합니다.

```bash
requests/sec
```

```bash

```

#### 패널 7: Django 4xx 에러율
잘못된 요청(예: 존재하지 않는 ID, 인증 실패 등)의 비율을 나타냅니다.  
클라이언트 요청 문제나 API 사용 오류가 있는지 판단할 수 있습니다.

쿼리
```sql
(
  sum(rate(django_http_responses_total_by_status_view_method_total{status=~"4.."}[5m])) or vector(0)
)
/
clamp_min(sum(rate(django_http_responses_total_by_status_view_method_total[5m])), 1e-9)
```

뜻:
Django에서 발생한 4xx 에러 비율입니다.
- `status=~"4.."` → 400번대 상태코드만 선택
- 분자 = 4xx 요청 수
- 분모 = 전체 요청 수

즉, 전체 요청 중 4xx가 차지하는 비율 입니다.

무엇을 하기 위한 조건인가?
- 잘못된 요청이 많아졌는지 확인
- 존재하지 않는 ID, 잘못된 호출, 인증 문제 등을 파악

왜 이렇게 작성하나?
에러율은 단순 개수가 아니라 비율로 보는 게 중요합니다.  
요청이 많아지면 에러 개수도 늘 수 있으니, 전체 대비 몇 %인지 봐야 합니다.

추가 문법 의미
- `or vector(0)`  
    → 값이 아예 없을 때 빈 결과 대신 0으로 처리
- `clamp_min(..., 1e-9)`  
    → 분모가 0일 때 나누기 오류 방지

즉, 그래프가 깨지지 않게 안전장치를 넣은 것입니다.


Unit
```bash
Percent (0.0-1.0)
```

패널 제목
```bash
Django 4xx 에러율
```

#### 패널 8: FastAPI 5xx 에러율
AI 서버 내부 오류가 얼마나 발생하는지를 보여주는 지표입니다.  
서버 과부하나 코드 오류 등 시스템 장애 여부를 판단할 수 있습니다.

쿼리
```sql
(
  sum(rate(http_requests_total{status=~"5.."}[1m])) or vector(0)
)
/
clamp_min(sum(rate(http_requests_total[1m])), 1e-9)
```

뜻:
FastAPI의 5xx 에러율입니다.

즉,
전체 FastAPI 요청 중 서버 내부 오류가 몇 %인지 보는 쿼리입니다.

무엇을 하기 위한 조건인가?
- AI 서버 내부 예외, 장애, 과부하 확인
- 서비스가 “느리기만 한지”, “실제로 실패하는지” 구분

왜 이렇게 작성하나?
5xx는 서버 자체 문제이므로 매우 중요합니다.  
단순히 요청 수만 보면 모르고, 실패 비율로 봐야 장애 여부를 판단할 수 있습니다.

Unit
```bash
percent (0-100)
```

패널 제목
```bash
FastAPI 5xx 에러율
```

#### 패널 10: FastAPI 누적 요청 수
AI 서버가 지금까지 처리한 전체 요청 수를 의미합니다.

쿼리

### ✅ STEP 5. k6로 부하 주기

지금까지는

- Prometheus가 수집하는지
- Grafana에서 그래프가 보이는지를 확인한 상태입니다.

이제는 실제로 요청을 계속 보내서 아래 질문에 답할 차례입니다.
- 요청 수가 올라가면 그래프가 같이 올라가는가?

```js
  // 요청 간격

}
```

### ✅ STEP 6. 그래프 해석하기
이 10개 패널은 각각 따로 보는 것이 아니라, 서로 연결해서 같이 봐야 합니다.

예를 들어,
- 요청 수가 올라갔는데 응답 시간은 그대로면 → 서버가 잘 버티는 상태입니다.
- 요청 수가 올라가면서 p95도 같이 올라가면 → 일부 요청이 느려지고 있는 것입니다.
- 요청 수가 올라간 뒤 5xx 에러율도 올라가면 → 서버가 감당하지 못하고 있다는 뜻입니다.

즉, 하나의 패널만 보고 결론 내리면 안 되고, 여러 패널을 같이 비교해야 정확하게 해석할 수 있습니다.

테스트 전 2분 대기 이 시간에는 아직 k6를 실행하지 않고 Grafana만 봅니다.
2분은 기준선 확인 시간입니다.

##### `테스트 전 2~3분 보기`

이때 보는 이유는:
- 원래 0에 가까운지
- 이미 이상한 값이 올라가 있는지
- 이전 테스트 흔적이 남아 있는지
즉, 기준선(베이스라인)을 보는 단계입니다.

이때 체크할 것

- FastAPI 요청 수 거의 0인지

- 에러율 0인지

##### `테스트 시작 직후 30초~1분 집중 관찰`
	k6를 실행하면 요청 수 패널이 가장 먼저 반응합니다.

예를 들어:
- Django 요청 수 상승
- FastAPI 요청 수 상승
- 누적 요청 수 상승

이게 먼저 보여야 정상입니다.

이때 체크할 것

- Django와 FastAPI가 같이 움직이는가

- 에러율이 생기는가
즉, 부하가 들어갔을 때 즉각 반응하는 패널을 보는 단계입니다.

##### `테스트 끝난 후 3~5분 더 보기`
	이 단계가 매우 중요합니다.

k6 끝나면 바로 창을 닫지 말고 3~5분더 관찰합니다.

```
- histogram_quantile()
- 에러율 계산
```

→ 정상 부하 테스트만 따로 진행해야 정확한 분석 가능

### 병목 찾는 방법

개념 먼저 정리
```
p95 = 느린 요청이 있다는 증거  
병목 = 왜 느린지의 원인

즉
p95가 튄다 → 병목이 어딘가 있다
```

지금 시스템 상태는 
✔ p95 상승 = 문제 발생 신호  
👉 원인은 아직 모름 (병목 위치 미확인)

그래서 병목 구간을 찾습니다. 방법은
```
요청을 구간별로 쪼개서 시간 찍기
```

전체흐름
```
[사용자 요청]
    ↓
Django View
    ↓
Celery task 생성
    ↓
Redis Queue
    ↓
Celery Worker 실행
    ↓
FastAPI 호출
    ↓
DB 저장
    ↓
응답
```
여기 중 하나가 느린 겁니다

가장 쉬운 방법 (로그 찍기) : 시간 로그
```python
import time
import logging

logger = logging.getLogger(__name__)
```

Django View
```python
start = time.time()

# Celery task 호출
task = analyze_review.delay(review_id)

logger.info(f"[VIEW] task create time: {time.time() - start:.4f}s")
```

Celery Task
```python
@shared_task
def analyze_review(review_id):
    import time
    start = time.time()

    logger.info(f"[TASK START]")

    # FastAPI 호출
    t1 = time.time()
    result = call_fastapi(...)
    logger.info(f"[FASTAPI CALL] {time.time() - t1:.4f}s")

    # DB 저장
    t2 = time.time()
    save_result(...)
    logger.info(f"[DB SAVE] {time.time() - t2:.4f}s")

    logger.info(f"[TASK TOTAL] {time.time() - start:.4f}s")
```

FastAPI
```python
@app.post("/similarity")
def similarity():
    import time
    start = time.time()

    result = model.predict(...)

    print(f"[MODEL] {time.time() - start:.4f}s")

    return result
```

그리고 로그를 해석합니다. 예시 상황
```
[VIEW] 0.01s  
[TASK START]  
[FASTAPI CALL] 1.2s  
[DB SAVE] 0.02s  
[TASK TOTAL] 1.3s
```
시간이 가장 오래 걸린 FastAPI가 병목입니다.

즉 가장 오래 걸리는 구간이 병목 구간입니다.

그래서 현재 프로젝트에서 가장 의심되는 병목 구간은 그래프 기준으로
```
1순위: Celery queue 대기  
2순위: Django 처리  
3순위: DB  
4순위: FastAPI (가능성 낮음)
```
이유
- FastAPI 요청 거의 없음
- p95만 튐 → 일부 요청만 지연
- → 큐 대기 가능성 높음

### p95 vs 병목 관계
```
p95 ↑ → 병목 존재  
하지만 p95만 보고는 위치 모름  
→ 로그로 위치 찾아야 함
```

p95는 경고등이고,  
로그는 어디 고장났는지 알려주는 도구입니다.
