## 핵심 정리
- 가상환경 → 파이썬 실행 환경 격리
- Docker → 애플리케이션 실행 환경 통째로 패키징
- Kubernetes → Docker 컨테이너들을 자동으로 운영/관리

#### 가상환경 (venv)
가장 작은 단위입니다

✔ 역할
- Python 패키지 충돌 방지
- 프로젝트별 라이브러리 분리

✔ 느낌
- 프로젝트 A → Django 3.2  
- 프로젝트 B → Django 5.0  
  같은 PC에서 충돌 없이 실행

✔ 한계
- OS는 그대로 공유
- 서버 운영 기능 없음
- 배포 개념 없음

#### Docker
가상환경보다 한 단계 위

✔ 역할
- 앱 + 라이브러리 + OS 환경까지 묶어서 실행
- 어디서든 동일하게 실행 가능

✔ 현재 프로젝트 기준
- Django 컨테이너  
- FastAPI 컨테이너  
- Redis 컨테이너  
- PostgreSQL 컨테이너  
- Celery 컨테이너
- Prometheus 컨테이너
- Grafana 컨테이너
- Alertmanager 컨테이너

✔ Docker의 핵심 장점
- 환경 동일성 (로컬 = 서버)
- 배포 쉬움
- 서비스 분리

❗ 하지만 Docker의 한계
지금부터 Kubernetes가 필요한 이유입니다.

Docker만 쓰면:
```
- 컨테이너 죽으면? → 직접 다시 실행해야 함  
- 트래픽 많아지면? → 직접 컨테이너 늘려야 함  
- 서버 여러 대면? → 관리 매우 어려움  
- 롤링 배포? → 거의 수동
```
즉, 운영이 힘듦

#### Kubernetes (쿠버네티스)

✔ 한 줄 정의
- 컨테이너(Docker)를 자동으로 관리하는 시스템

#### Kubernetes가 하는 일 (핵심만)
- 지금 Docker로 하고 있는 걸 자동화 + 시스템화 해줍니다.

① 컨테이너 자동 실행 유지
	컨테이너 죽음 → 자동 재시작

Docker:
- docker restart 해야함

Kubernetes:
- 자동 복구

---
② 자동 확장 (Scaling)
- 요청 많음 → 컨테이너 자동 증가  
- 요청 적음 → 컨테이너 자동 감소

Docker:
- docker-compose scale 직접 해야함

Kubernetes:
- 자동 (HPA)

---
③ 서비스 연결 (네트워크)
- Django → FastAPI 호출

Docker:
http://fastapi:8001

Kubernetes:
http://fastapi-service:8001
내부 DNS 제공

---
④ 배포 자동화
- 무중단 배포 (Rolling Update)

Docker:
- 컨테이너 내리고 다시 띄움 (다운타임 발생)

Kubernetes:
- 하나씩 교체 (서비스 유지)

---
⑤ 설정 관리
.env → ConfigMap / Secret
코드와 설정 분리

---

## `1.` 쿠버네티스란 무엇인가?

쿠버네티스는 다수의 컨테이너를 효율적으로 배포, 확장 및 관리하기 위한 컨테이너 오케스트레이션(관리) 시스템입니다. 쉽게 비유하자면, 도커 컨테이너들을 지휘하는 함대 사령관이나 시스템 관리 로봇과 같습니다.

---
## `2.` 일반 서버(또는 단순 도커)와 쿠버네티스의 차이

개발자들이 왜 일반 서버 대신 쿠버네티스를 선택하는지 그 차이점을 이해하는 것이 중요합니다.

- 명령 기반 vs 선언적 상태 관리:
    - 일반 서버/도커: 사용자가 직접 컨테이너를 실행해라라고 명령합니다. 만약 서버가 죽으면 사용자가 다시 켜야 합니다.
    - 쿠버네티스: 사용자가 이 앱이 항상 3개 떠 있어야 해라고 원하는 상태(Desired State)를 선언합니다. 그러면 쿠버네티스가 실제 상태를 감시하다가, 앱이 죽으면 자동으로 새로 띄워 숫자를 맞춥니다.
- 자가 치유(Self-healing): 서버나 컨테이너에 장애가 나면 쿠버네티스가 이를 감지하고 자동으로 복구하여 서비스 중단을 막습니다.
- 무중단 배포: 서비스 중지 없이 새로운 버전의 앱을 조금씩 교체하는 롤링 업데이트가 가능합니다.

---
## `3.` 쿠버네티스의 핵심 기초 개념 (오브젝트)

연습할 때 반드시 알아야 할 6가지 핵심 리소스입니다:

1. 파드(Pod): 쿠버네티스에서 실행되는 가장 작은 단위로, 하나 이상의 컨테이너가 들어있습니다.
2. 디플로이먼트(Deployment): 파드의 개수를 유지하고 업데이트(버전 관리)하며 자가 복구를 담당하는 관리자입니다.
3. 서비스(Service): 파드들이 죽고 살아나면서 바뀌는 IP 대신, 고정된 주소를 부여하여 내부/외부에서 접근할 수 있게 해주는 창구입니다.
4. 인그레스(Ingress): 클러스터 외부에서 들어오는 요청을 도메인이나 경로에 따라 적절한 서비스로 연결해 주는 정문(Gateway) 역할입니다.
5. 컨피그맵(ConfigMap) & 시크릿(Secret): 설정값이나 비밀번호 같은 민감 정보를 이미지 밖에서 주입해 주는 저장소입니다.
6. HPA(Horizontal Pod Autoscaler): 부하가 많아지면 파드 개수를 자동으로 늘리고, 줄어들면 다시 줄이는 자동 확장기입니다.

## `4.` 실제 현업에서 어떻게 활용되는가?
- 마이크로서비스 아키텍처(MSA): API 서버와 AI 서버처럼 서로 다른 요구사항을 가진 앱들을 독립적으로 배포하고 확장할 때 사용합니다.
- 안정적인 운영: 24시간 서비스가 중단되지 않아야 하는 환경에서 서버 장애 시 자동 복구 기능을 활용합니다.
- 효율적인 자원 관리: 서버의 CPU나 메모리 사용량에 맞춰 앱의 위치를 자동으로 배치(Scheduling)하여 자원 낭비를 줄입니다.

## `5.` 초보자가 연습해봐야 할 단계별 로드맵

이론을 배웠다면 미니쿠베(minikube)를 활용해 로컬 환경에서 다음과 같이 실습해보는 것을 추천합니다:

- 레벨 0 (앱 배포): Deployment를 통해 내 앱을 컨테이너로 띄워보고 `kubectl` 명령어로 상태를 확인합니다.
- 레벨 1 (네트워크 연결): Service를 붙여 내부에서 고정된 주소로 통신이 되는지 확인합니다.
- 레벨 2 (통신 실습): API 앱이 AI 앱을 호출하는 내부 통신 환경을 구축해 봅니다.
- 레벨 3 (외부 접속): Ingress를 설정하고 로컬 도메인(예: `demo.local`)으로 브라우저에서 접속해 봅니다.
- 레벨 4 (오토스케일링): 강제로 부하를 걸어 파드 개수가 자동으로 늘어나는 HPA를 경험해 봅니다.

정리하자면: 개발자가 쿠버네티스를 선택하는 이유는 잠든 사이에도 서버가 알아서 복구되고 확장되게 만들기 위해서입니다.
