현재 우리는 다음을 할 수 있는 상태입니다.
- Docker를 사용하여 컨테이너를 실행할 수 있습니다.
- docker-compose를 이용해 여러 컨테이너를 함께 실행할 수 있습니다.
- 서비스 간 통신을 이름으로 연결할 수 있습니다.

예를 들어:
```
http://fastapi:8001    
redis:6379    
db:5432
```
즉, 이미 MSA 구조의 기초는 완성된 상태입니다.

MSA(Microservices Architecture)는?
하나의 큰 서비스를 여러 개의 작은 서비스로 나눠서 운영하는 구조입니다.

✅ 기존 방식 vs MSA

기존 (Monolithic 구조)
- Django 하나 안에
    - API
    - AI 처리
    - DB 처리
    - 모든 기능이 다 들어있음
👉 하나의 덩어리 (수정하면 전체 영향)

🔸 MSA 구조
- 기능별로 서버를 나눔

예:
```
Django (웹/API 서버)  
FastAPI (AI 서버)  
Redis (큐)  
Celery (비동기 작업)  
PostgreSQL (DB)
```
👉 각각 독립적으로 동작

현재 우리 프로젝트는
```
사용자 → Django → Celery → Redis → Celery Worker → FastAPI → DB
```

| 역할     | 서비스        |
| ------ | ---------- |
| 웹/API  | Django     |
| AI 처리  | FastAPI    |
| 비동기 처리 | Celery     |
| 메시지 큐  | Redis      |
| 데이터 저장 | PostgreSQL |

### 참고: 여기에서 정리할 개념은 언제 서버(EC2)를 나누는가? (실무기준)

1️⃣ 특정 서비스만 느릴 때

예:
- FastAPI (AI 처리)만 느림
- Django는 괜찮음

해결: FastAPI만 EC2 여러 개로 확장
핵심: 느린 놈만 따로 늘린다

2️⃣ 트래픽이 폭발할 때

예:
- 사용자 요청 급증
- Django API 병목 발생

해결: Django 서버 여러 개 (로드밸런싱)
핵심: 사용자가 많아지면 분산

3️⃣ 자원(CPU/메모리) 싸움이 날 때

예:
- FastAPI (AI) → CPU 90% 먹음
- Django까지 느려짐

해결: FastAPI를 다른 EC2로 분리
핵심: 무거운 애는 따로 격리

4️⃣ 장애 영향 분리 (안정성)

예:
- FastAPI 죽으면 전체 서비스 죽음 ❌

해결: FastAPI 따로 서버
핵심: 하나 죽어도 전체 안 죽게

5️⃣ 배포/운영 독립성 필요할 때

예:
- FastAPI만 자주 수정
- Django는 안정 상태

해결: 서버 분리 → 각각 따로 배포
핵심: 각 서비스 독립적으로 관리

서버는 언제 쪼개야 하냐?

케이스 1 (가장 흔함)
- AI 요청 느림
- FastAPI CPU 터짐
👉FastAPI → EC2 2~3개로 분리

---
케이스 2
- 사용자 많아짐
👉Django → 여러 개로 확장  
+ Load Balancer

---
케이스 3
- DB 느려짐
👉DB 전용 서버 분리 (RDS)

---
✅ 절대 하면 안 되는 실수 ❌
👉 초보자가 많이 하는 실수

❌ 처음부터 다 쪼개기

EC2 5개 만들기
결과:
- 돈 날림 💸
- 설정 지옥 🔥
- 장애 대응 어려움

### ✅ 실무에서 흐름

1단계
1단계: EC2 + Docker (초기 스타트)
```
[사용자]
   ↓
EC2 (1대)
 └ Docker
    ├ Django
    ├ FastAPI
    ├ Redis
    ├ DB
```
👉 특징
- 서버 1대에 다 몰아넣음
- Docker로만 관리
- 가장 간단하지만 위험

👉 문제
- 서버 죽으면 끝 ❌
- 확장 불가 ❌
---
2단계: FastAPI 분리
FastAPI만 분리
```
EC2 2대

[EC2-1]
 └ Django

[EC2-2]
 └ FastAPI
```
👉 특징
- AI 서버 분리
- 부하 분산 시작

👉 이유
- AI는 무거움 (CPU/GPU)

---
3단계: Django 확장 + Load Balancer(EC2가 여러대 있어야 가능)
Django 확장 + Load Balancer
```
[사용자]
   ↓
Load Balancer
   ↓
 ┌ Django (EC2)
 ├ Django (EC2)
 └ Django (EC2)
```
👉 특징
- 서버 여러 개
- 트래픽 분산

👉 핵심
- 장애 대응 가능
- 확장 가능

---
4단계: DB → RDS (중요 ⭐)
RDS는 AWS에서 제공하는 관리형 데이터베이스 서비스입니다.
즉, DB 서버를 직접 운영하지 않고 AWS가 대신 관리해주는 서비스입니다. 
비용이 발생하므로 우리 과정에서는 적용을 안해봤습니다.

```
EC2 (서버들)
   ↓
RDS (DB)
```
👉 특징
- DB를 AWS가 관리
- 백업 / 복구 자동

👉 이유
- DB는 가장 중요함
- 직접 관리하면 터짐

---
5단계: Kubernetes (최종 진화)
```
[사용자]
   ↓
Ingress / LoadBalancer
   ↓
Kubernetes Cluster
   ├ Django (Pod 여러 개)
   ├ FastAPI (Pod 여러 개)
   ├ Redis
   ├ Celery
   └ PostgreSQL (StatefulSet)
```
👉 특징
- Docker 직접 관리 ❌
- Kubernetes가 자동 관리 ✅

### ✅ 전체 흐름 (핵심 구조)

```
가상환경 → Docker → Kubernetes
```
👉 점점 운영 자동화 수준이 올라가는 구조입니다


핵심 개념 정리
- 가상환경 → 파이썬 실행 환경 격리
- Docker → 애플리케이션 실행 환경 통째로 패키징
- Kubernetes → Docker 컨테이너들을 자동으로 운영/관리

---
#### 1️⃣ 가상환경 (venv)
가장 작은 단위의 격리입니다

✔ 역할
- Python 패키지 충돌 방지
- 프로젝트별 라이브러리 분리

✔ 특징
- 같은 PC에서 서로 다른 환경 실행 가능  
    (예: Django 3.2 / Django 5.0)

❗ 한계
- OS는 공유 (완전 격리 아님)
- 서버 운영 기능 없음
- 배포 개념 없음

한 줄 정리
> 파이썬 라이브러리만 분리하는 수준입니다.

---
#### 2️⃣ Docker
가상환경보다 한 단계 위

✔ 역할
- 앱 + 라이브러리 + OS 환경까지 묶어서 실행
- 어디서든 동일하게 실행 가능

✔ 현재 프로젝트 기준
```
- Django 컨테이너  
- FastAPI 컨테이너  
- Redis 컨테이너  
- PostgreSQL 컨테이너  
- Celery 컨테이너
- Prometheus 컨테이너
- Grafana 컨테이너
- Alertmanager 컨테이너
```
각각 컨테이너로 실행

✔ Docker의 핵심 장점
- 환경 동일성 (로컬 = 서버)
- 배포 쉬움
- 서비스 단위 분리 가능

❗ 하지만 Docker의 한계
Docker는 “실행”까지만 잘합니다 하지만 운영은 사람이 해야 합니다

Docker만 쓰면:
```
- 컨테이너 죽으면? → 직접 다시 실행해야 함  
- 트래픽 많아지면? → 직접 컨테이너 늘려야 함  
- 서버 여러 대면? → 관리 매우 어려움  
- 롤링 배포? → 거의 수동
```
Docker는 컨테이너 실행 도구이지, 운영 자동화 도구는 아닙니다

---
#### 3️⃣ Kubernetes (쿠버네티스)
	Docker 위에서 동작하는 운영 자동화 시스템입니다


Kubernetes가 해주는 핵심 기능

① 컨테이너 자동 복구
```
컨테이너 죽음 → 자동 재시작
```
- Docker: 직접 restart 필요
- Kubernetes: 자동 복구
👉 운영 안정성 확보

---
② 자동 확장 (Scaling)
```
트래픽 증가 → 컨테이너 자동 증가  
트래픽 감소 → 자동 감소
```
- Docker: 수동 scale
- Kubernetes: 자동 (HPA)
👉 비용 + 성능 최적화

---
③ 서비스 간 통신 관리
```
Django → FastAPI 호출
```
- Docker: [http://fastapi:8001](http://fastapi:8001)
- Kubernetes: [http://fastapi-service:8001](http://fastapi-service:8001)
👉 내부 DNS 자동 제공

DNS 자동 제공이란?
쿠버네티스에서는 서비스(Service)를 생성하면  
해당 서비스 이름을 주소처럼 사용할 수 있도록 자동으로 DNS를 만들어줍니다.

예시
```
http://fastapi-service:8001  
redis-service:6379  
postgres-service:5432
```
IP를 몰라도 이름만으로 통신 가능

쿠버네티스가 서비스 이름을 주소(IP 대신)로 자동 변환해주는 기능입니다

---
④ 배포 자동화
- 무중단 배포 (Rolling Update)
```
기존 서버 유지 + 새 서버 교체
```
- Docker: 재시작 → 다운타임 발생 가능
- Kubernetes: 순차 교체 → 서비스 유지
👉 실무에서 매우 중요

---
⑤ 설정 관리 분리
```
.env → ConfigMap / Secret
```
코드와 설정을 분리하여 관리

---
#### ✅ 현재 프로젝트 기준으로 보면

`docker-compose.yml`
```
web (Django)
fastapi
redis
db
celery
prometheus
grafana
alertmanager
```
의미: 이 컨테이너들을 실행해줘

Kubernetes는 왜 복잡해 보일까?
Docker:
```
“컨테이너 하나 실행”
```

Kubernetes:
```
“컨테이너 실행 + 유지 + 연결 + 저장 + 설정”
```
그래서 역할별로 나눠짐

###### ✅ 핵심 개념 4개만 먼저 이해
|개념|역할|
|---|---|
|Deployment|컨테이너 실행 + 유지|
|Service|네트워크 연결|
|ConfigMap|설정(.env)|
|PVC|데이터 저장|

✅ Docker → Kubernetes 1:1 변환
Docker = 컨테이너 실행을 한다면  
Kubernetes = 컨테이너를 계속 살아있게 + 연결 + 관리를 합니다.

① Deployment : 컨테이너 실행 + 유지

> 이 컨테이너 계속 돌려라 (죽으면 다시 띄워라)

---
② Service : 컨테이너 연결 (주소 역할)

> 다른 서비스가 이걸 이렇게 접근해라

예:
```
fastapi → fastapi-service
```

---
③ ConfigMap / Secret
설정(.env)

> 코드 밖에서 설정 관리

---
④ PVC (스토리지)
데이터 저장

> 컨테이너 죽어도 데이터는 남겨라

Docker와 Kubernetes의 느낌을 비교하면

Docker Compose
```
컨테이너 실행 끝
```

Kubernetes
```
실행 + 유지 + 연결 + 저장 + 설정
```

---
#### ✅ 가장 중요한 차이
| 구분    | 가상환경     | Docker    | Kubernetes |
| ----- | -------- | --------- | ---------- |
| 범위    | Python   | 애플리케이션    | 전체 시스템     |
| 역할    | 라이브러리 분리 | 실행 환경 패키징 | 운영 자동화     |
| 배포    | 없음       | 가능        | 매우 강력      |
| 확장    | 없음       | 수동        | 자동         |
| 장애 대응 | 없음       | 수동        | 자동         |

---
✅ 한 문장으로 이해하기
- 가상환경 → 개발 편하게  
- Docker → 실행 쉽게  
- Kubernetes → 운영 쉽게

여기까지 했기 때문에

이제 Kubernetes는:
이걸 자동으로 운영하는 방법을 배우는 단계입니다.

✅ 쿠버네티스 핵심 용어 정리

`1.` 가장 큰 개념

✔ Kubernetes (쿠버네티스)
	컨테이너(Docker)를 자동으로 관리해주는 시스템

- 컨테이너 죽으면 → 자동 재시작
- 트래픽 많으면 → 자동 확장
- 배포 → 자동 처리

한 줄: Docker를 운영해주는 시스템

---
`2.` 가장 작은 실행 단위

✔ Pod (파드)
	컨테이너가 실제로 실행되는 공간

- Docker 컨테이너가 들어있는 집
- 보통 1 Pod = 1 컨테이너

한 줄: 컨테이너가 실행되는 최소 단위

---
`3.` 컨테이너 관리자

✔ Deployment
	Pod를 자동으로 관리하는 관리자

- 개수 유지 (예: 항상 3개 유지)
- 업데이트 관리
- 자동 복구

한 줄: Pod를 관리하는 자동 관리자


✔ StatefulSet
	DB처럼 상태가 있는 Pod 관리

- Pod 이름 고정 (postgres-0)
- 데이터 유지
- 순서 보장

한 줄: DB 전용 Deployment

---
`4.` 네트워크 (접속 관련)

✔ Service
	Pod에 접근할 수 있는 고정 주소

- Pod는 계속 바뀜 (IP 변경)
- Service는 안 바뀜

한 줄: Pod의 고정 주소 (접속 창구)


✔ Ingress
	외부에서 들어오는 요청을 내부 서비스로 연결

- 브라우저 → Django
- 도메인 연결

한 줄: 외부 → 내부로 들어오는 입구

---
`5.` 설정 관리

✔ ConfigMap
	일반 설정값 저장

예:
- DB_HOST
- DEBUG
- API URL

한 줄: 환경설정 저장소 (.env 대신)


✔ Secret
	비밀번호 같은 민감 정보 저장

예:
- DB_PASSWORD
- API KEY
- AWS KEY

한 줄: 비밀번호 저장소

---
`6.` 저장소

✔ PVC (Persistent Volume Claim)
	데이터 저장 공간 요청

- DB 데이터 저장
- Pod 죽어도 데이터 유지

한 줄: 디스크 요청


✔ PV (Persistent Volume)
	실제 디스크 공간

한 줄: 진짜 저장소

---
`7.` 자동 확장

✔ HPA (Horizontal Pod Autoscaler)
	트래픽에 따라 Pod 자동 증가/감소

한 줄: 자동 스케일링

---
`8.` 구조를 한 번에 보기
```
[사용자]  
    ↓  
Ingress (외부 입구)  
    ↓  
Service (고정 주소)  
    ↓  
Deployment / StatefulSet (관리자)  
    ↓  
Pod (실행 공간)  
    ↓  
Container (앱 실행)  
  
+ ConfigMap / Secret (설정)  
+ PVC (데이터 저장)
```

실습에서 제외된 것
Prometheus / Grafana / Alertmanager

그러나 실무에서는 
```
[쿠버네티스 내부]

Django / FastAPI / Redis / DB
        ↓
Prometheus (수집)
        ↓
Grafana (시각화)
        ↓
Alertmanager (알림)
```
이렇게 설정되는게 맞습니다.

Prometheus / Grafana / Alertmanager
이것을 K8s로 옮기면:
```
앱 + 모니터링 → 전부 K8s
```
전부 한곳에서 관리됩니다.

- Prometheus 죽으면 자동복구 됩니다.
- 확장 가능 
	- 트래픽 많아지면
	- Prometheus도 scale 가능
	- Grafana도 scale 가능
- 서비스 기반 연결
```
prometheus-service  
grafana-service
```
위으 이름이 DNS로 연결됩니다. 즉 IP를 몰라도 자동으로 연결됩니다.
- DNS = 이름 → IP 연결
```
내부적으로 DNS가 동작  
DNS는 이름을 IP 주소로 바꿔주는 기능입니다.
```

---
현재 모니터링에서 까지의 상태를 보면

✔ 현재 (Docker + EC2)
- Prometheus 있음
- Alert → Discord 알림 OK
- 하지만…
    - 서버 죽으면 ❌ 직접 재시작
    - 트래픽 증가 대응 ❌ 수동
    - 장애 대응 ❌ 느림

✔ Kubernetes
- 모니터링 + 자동 운영 시스템

만약 쿠버네티스를 달게되면 달라지는 핵심 5가지
① 자동 복구 (Self-Healing)
```
Prometheus Pod 죽음  
→ Kubernetes 감지  
→ 자동 재생성
```
즉 
- DOWN → 자동 UP
- 사람이 개입 안해도 됨

② 자동 확장 (Auto Scaling, HPA)
```
트래픽 증가  
→ CPU / 메트릭 증가  
→ Pod 자동 증가
```
핵심 메트릭 기반으로 자동 확장 가능

③ 장애 격리 (Isolation)
지금은 앱 하나 죽으면 영향 큼
그러나 쿠버네티스는
```
fastapi 죽음 → fastapi만 재시작  
django는 영향 없음
```

④ 서비스 안정성 (Load Balancing)
Pod 여러 개 뜨면 자동 분산됨
```
요청 → 여러 서버로 분산
```
별도 Nginx 없어도 기본 지원

⑤ 선언형 운영 (apply 한 번으로 전체 관리)
```
kubectl apply -f 전체.yaml
```
결과:
- DB
- Django
- FastAPI
- Prometheus
- Grafana
👉 전부 원하는 상태로 자동 유지

✔ 모니터링 관점에서 추가되는 것
- 기존은 모니터링 + 알람
- 쿠버네티스에서는 모니터링 + 자동대응이 됩니다.

✔ 쿠버네티스에서 모니터링
- Pod 상태 모니터링
- 리소스 모니터링 
```
CPU / Memory 사용량
```
→ HPA 연결

- 헬스체크 (Liveness / Readiness)
```
죽었는지?  
준비됐는지?
```
실패 시 자동 재시작

- 이벤트 추적: 왜 죽었는지 기록 남음
