### ✅ 1단계. 모니터링 개념 이해 단계

#### `1.` 모니터링이 왜 필요한가?

모니터링은 단순히 숫자를 보는 것이 아니라, 서비스의 건강 상태를 실시간으로 진단하여 문제가 생기기 전에 대응하거나 발생한 문제를 빠르게 해결하기 위한 활동입니다.

- **가용성:** 서버가 현재 살아있는가?
- **성능:** 응답 속도가 충분히 빠른가? (평균뿐만 아니라 상위 95%의 속도인 p95 지표가 중요함).
- **안정성:** 에러가 얼마나 발생하는가?
- **자원 상태:** CPU, 메모리 등 서버의 물리적 한계에 도달했는가?.

쉽게 설명하면
- 서버가 살아있는지 알고 싶다
- 느려졌는지 알고 싶다
- 에러가 늘었는지 알고 싶다
- CPU/메모리가 버티는지 알고 싶다
- 장애가 났을 때 “어디부터 봐야 하는지” 알고 싶다

즉, 모니터링은서비스 상태를 눈으로 보는 도구입니다.

--------------------------------------------------------------------------------
#### `2.` Prometheus와 Grafana를 어떻게 이해하면 되는가

① 프로메테우스 (데이터 수집 및 저장소)

수집기 + 저장소
- 각 서버의 `/metrics` 주소에 들어가서 숫자를 가져옴
- 그 숫자를 시간순으로 저장함
- 그래서 나중에 5분 전보다 요청이 늘었나? 같은 걸 볼 수 있음

즉,
> Prometheus = 숫자 수집 담당입니다


② 그라파나 (시각화 및 알림)
- **역할:** 프로메테우스에 저장된 딱딱한 숫자 데이터를 예쁜 그래프와 대시보드로 바꾸어 보여주는 "얼굴" 역할을 합니다.
- **알림:** 설정한 수치(예: 에러율 1% 초과)를 넘으면 디스코드나 슬랙으로 메시지를 보내 담당자를 깨우는 역할을 합니다.

쉽게 다시 설명하면
보여주는 화면
- Prometheus가 모아놓은 숫자를
- 그래프, 패널, 대시보드로 예쁘게 보여줌

즉,
> Grafana = 시각화 담당입니다.

#### `3.` 무엇을 중점적으로 봐야 하는가? (5대 핵심 지표)

개발자가 대시보드를 구성할 때 반드시 포함해야 할 5축 지표입니다:
1. **가용성 (Availability):** `up` 지표가 1인지 확인합니다. 0이면 서버가 죽은 것입니다.
2. **트래픽 (Traffic/RPS):** 초당 요청 수를 확인하여 서비스 규모와 부하를 파악합니다.
3. **성능 (Latency/p95):** 95%의 사용자가 느끼는 속도를 봅니다. 평균에 속지 말고 "꼬리 지연(Tail Latency)"을 잡는 것이 핵심입니다.
4. **오류 (Errors/5xx):** 서버 오류(5xx) 비율을 확인합니다. 보통 1% 미만 유지를 목표(SLO)로 합니다.
5. **리소스 (Resources):** CPU와 메모리 여유가 있는지 확인하여 서버 증설 시점을 판단합니다.

쉽게 설명하면:
- UP: 서버가 살아있는가
- RPS: 요청이 얼마나 들어오는가
- p95: 대부분 사용자 입장에서 얼마나 빠른가
- 5xx: 서버 에러가 얼마나 나는가
- Queue 상태 (Redis)

(1) UP
- 1이면 Prometheus가 잘 가져오고 있음
- 0이면 서버가 죽었거나, 주소가 틀렸거나, metrics가 안 열림

(2) RPS
- 초당 요청 수
- 트래픽이 얼마나 들어오는지 보는 기본 지표

(3) p95
- 평균보다 훨씬 중요함
- 느린 요청 몇 개가 숨어 있어도 평균은 멀쩡해 보일 수 있음
- 그래서 “대부분 사용자”가 느끼는 체감을 보려면 p95를 봄

(4) 5xx
- 서버 내부 오류
- 이게 튀면 장애 신호

(5) Queue 상태 (Redis)
- AI 작업이 얼마나 쌓여 있는지 보는 지표
- Django → Celery → FastAPI로 넘어가는 중간 대기 구간
- AI 작업이 밀리고 있는가? 를 보는 지표

### prometheus.yml 설정 의미
- 5초마다 데이터를 수집
- Django의 `/metrics`를 계속 긁어감

먼저 구조를 다시 잡기
```
product-review-service/
└── backend/
    ├── docker-compose.yml
    ├── Dockerfile
    ├── requirements.txt
    ├── prometheus/
    │   └── prometheus.yml   ← 이번에 추가
    └── ...
```

폴더생성하기
```bash
mkdir -p prometheus
touch prometheus/prometheus.yml
```

내용은 일단 Django만 수집하도록 아주 단순하게 시작합니다.
```yaml
global:
  scrape_interval: 5s

scrape_configs:
  - job_name: "django"
    static_configs:
      - targets: ["web:8000"]
```
이 한 줄이 핵심
```yaml
targets: ["web:8000"]
```
의미:
`web:8000`으로 `targets`을 설정한 이유는 도커 컴포즈 안에서는 컨테이너끼리 서비스명으로 통신합니다. 
`docker-compose.yml` 에 Django 서비스는 아래와 같이 작성되었습니다.
```yml

  web:
    ...
```
그러면 Prometheus 컨테이너는 Django를 `web:8000`으로 접근합니다.
즉:
- `127.0.0.1:8000` → 내 PC 기준
- `web:8000` → `docker compose` 네트워크 내부 기준
Prometheus는 컨테이너 안에서 돌기 때문에 `web:8000` 써야 합니다

`services:` 안에 추가
```yml

  db:
  redis:
  web:
  celery:
  fastapi:

```

![[Pasted image 20260329140251.png]]
여기에서 메트릭 이름은 
```

django_http_responses_before_middlewares_total

```
Prometheus 형식은 항상 이렇게 생깁니다:
```

```

요청수

응답 수
```
django_http_responses_before_middlewares_total
```
의미: 응답 완료된 요청 수

응답 시간
```
django_http_requests_latency_including_middlewares_seconds
```
의미: 요청 처리 시간 (히스토그램)

### 내 서버에 초당 10번 요청을 자동으로 보내는 테스트 도구

터미널 (WSL / backend 위치)에서 실행
```bash
watch -n 0.1 curl -s http://localhost:8000 > /dev/null
```
0.1초마다 명령어를 계속 실행 즉 1초에 10번 실행을 보내봅니다.
```
0.1초마다
→ Django 서버에 요청 보내고
→ 응답은 버리고
→ 계속 반복
```
하는 명령어를 터미널에 작성해서 요청을 보내고 시작합니다.

요청 수 : 총 요청 수 (누적값)
```
django_http_requests_before_middlewares_total
```

응답수 : 응답 완료된 요청 수
```
django_http_responses_before_middlewares_total
```

결과
![[Pasted image 20260329141415.png]]
해석
```
요청: 7592번 들어옴
응답: 7639번 처리됨
👉 서버 정상 동작 중
```
요청수의 특징
- 누적값 (계속 증가함)
- watch 때문에 계속 올라가는 중

응다수는 서버가 응답을 7,639번 보냈습니다.
그런데 왜 응답이 더 많냐?
```
응답(7639) > 요청(7592)
```
이유는 리다이렉트 때문입니다. `리다이렉트(302) 때문`
 
실제 흐름해석
```
요청 1번
→ 응답 302
→ 다시 요청
→ 응답 200

👉 응답이 더 많아짐
```
결론: 서버는 정상적으로 요청을 받고 있고  응답도 잘 처리하고 있다


응답 시간 : 요청 처리 시간 (히스토그램)
```
rate(django_http_requests_latency_including_middlewares_seconds_sum[1m])
/
rate(django_http_requests_latency_including_middlewares_seconds_count[1m])
```
