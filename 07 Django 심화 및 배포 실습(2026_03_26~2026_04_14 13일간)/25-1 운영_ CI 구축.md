- 레포는 **1개**
- 서비스는 **2개**
    - `backend` = Django + DRF + Celery
    - `ai-server` = FastAPI
- `backend/docker-compose.yml` 안에서
    - postgres
    - redis
    - web
    - celery
    - fastapi 를 한 번에 띄우는 구조입니다.

이 구조면 EC2 한 대에 배포하는 구조로 가는 것이 맞고,  
CI도 그에 맞게 작성해야 합니다.

---
1단계: 코드 검증 CI
- Django 설치 및 실행 가능 확인
- FastAPI 설치 및 실행 가능 확인
- Django migration/check/test 확인
- FastAPI import 확인
- Docker image build 확인

2단계: 배포 전 검증 CI
- `backend/docker-compose.yml` 기준으로
- Django / FastAPI / Redis / Celery 구성이 실제로 올라가는지 확인

즉, 단순히 `python manage.py test`만 하는 CI가 아니라,  
이 구조가 EC2에서 실제로 배포될 수 있는가까지 보는 CI로 가야 합니다.

---
`1.` CI의 목표
배포까지 고려한 CI라면 최소한 아래 3단계를 검증해야 합니다.

1단계. 앱 단위 검증
- Django 설치되는가
- FastAPI 설치되는가
- Django check / migrate / test 되는가
- Celery import 되는가
- FastAPI import 되는가

2단계. Docker 이미지 검증
- `backend/Dockerfile` 빌드 되는가
- `ai-server/Dockerfile` 빌드 되는가

3단계. Compose 통합 검증
- `backend/docker-compose.yml`로 전체가 실제로 뜨는가
- `web`, `celery`, `fastapi`, `db`, `redis`가 같이 올라가는가

즉, 코드 + 이미지 + 컨테이너 통합까지 보는 CI가 필요합니다.

---
지금 compose 구조에서 CI가 주의해야 할 점

현재 compose는 이렇습니다.

- `web: build: .`
- `celery: build: .`
- `fastapi: build: context: ../ai-server`

이 말은 곧:
- `docker compose` 명령은 반드시 `backend/` 폴더에서 실행되어야 합니다.
- GitHub Actions에서도 `working-directory: backend` 기준으로 compose를 돌려야 합니다.

이 포인트가 매우 중요합니다.

---
`3.` CI에서 사용할 전략
이번에 추천하는 최종 구조는 아래입니다.

Job 1. app-tests
Python 환경에서 직접 실행
- Django check
- migrate
- test
- Celery import
- FastAPI import

Job 2. docker-build
Dockerfile 빌드 확인
- backend image build
- ai-server image build

Job 3. integration-compose
실제 compose로 전체 서비스 통합 실행
- CI용 `.env` 생성
- `docker compose up -d --build`
- web / fastapi health 확인
- 실패 시 logs 출력
- 마지막에 down

이 흐름으로 가야 배포 전 검증 CI가 됩니다.

`8.` 이 CI를 순서대로 해석하면
이걸 이해하면서 따라가셔야 나중에 CD도 붙일 수 있습니다.

사람이 일일이 수동으로 하지 않아도 GitHub가 알아서 
- 코드 내려받기
- 패키지 설치
- DB/Redis 띄우기
- Django 검사
- 마이그레이션
- 테스트
- Docker 이미지 빌드
- docker compose 통합 실행까지 자동으로 해줍니다.

---
코드해석

`이 워크플로우의 이름`
```yaml
name: Monorepo CI (Django + FastAPI + Celery + Redis + Postgres)
```

`on:`
```yaml
on:
  push:
    branches: ["main", "develop"]
  pull_request:
    branches: ["main", "develop"]
```
이 뜻은:
- `main` 브랜치에 push 하면 실행
- `develop` 브랜치에 push 해도 실행
- `main`, `develop`으로 PR 올려도 실행
즉, 코드가 변경되는 순간마다 자동 검사하겠다는 뜻입니다.

`jobs:` 아래에는 실행할 큰 작업 단위가 들어 있습니다.

지금 이 파일에는 3개의 job이 있습니다.
1. `app-tests`
2. `docker-build`
3. `integration-compose`

이 3단계가 순서대로 흘러갑니다.

`app-tests`
이 job은 코드 자체가 정상인지를 보는 1차 검사입니다.

즉:
- Django 코드가 깨지지 않았는지
- FastAPI import가 되는지
- Redis/Postgres에 연결 가능한지
- 마이그레이션이 되는지
- 테스트가 통과하는지를 확인합니다.

`runs-on: ubuntu-latest`
```yaml
runs-on: ubuntu-latest
```
GitHub가 제공하는 우분투 서버 위에서 이 작업을 실행하겠다는 뜻입니다.
즉, 내 컴퓨터가 아니라 GitHub의 리눅스 서버에서 실행됩니다.

`services:`
```yaml
services:
  postgres:
    image: ankane/pgvector:latest
```
이건 CI 안에서 PostgreSQL 컨테이너를 띄운다는 뜻입니다.

그런데 그냥 `postgres:16`이 아니라:
```yaml
ankane/pgvector:latest
```
를 썼습니다.

이유는 현재 프로젝트가 `vector` 타입을 쓰기 때문입니다.
즉, 일반 Postgres는 안 되고, pgvector가 포함된 Postgres가 필요합니다.

`Postgres 안의 env`
```yaml
env:
  POSTGRES_DB: product_review_db
  POSTGRES_USER: product_review_user
  POSTGRES_PASSWORD: product_review_password
```
이건 DB 컨테이너를 만들 때 사용할:
- 데이터베이스 이름
- 사용자 이름
- 비밀번호입니다.
즉, CI가 뜰 때마다 임시 테스트용 DB를 자동 생성합니다.

`ports:`
```yaml
ports:
  - 5432:5432
```
이건 GitHub runner에서 `127.0.0.1:5432`로 접근할 수 있게 열어주는 것입니다.

그래서 뒤에서 Django가:
```yaml
DB_HOST: 127.0.0.1  
DB_PORT: 5432
```
로 접속할 수 있는 것입니다.

`options:` health check
```yaml
--health-cmd="pg_isready ..."
```
이건 DB가 정말 준비 완료되었는지 확인하는 검사입니다.

필요하냐면:
- 컨테이너는 떴는데
- DB가 아직 내부 초기화 중일 수 있습니다
그래서 살아는 있지만 아직 연결하면 안 되는 상태를 피하기 위해 health check를 둔 것입니다.

`Redis 서비스`
```yaml
redis:
  image: redis:7
```
이건 Celery가 쓸 Redis입니다.

즉, 이 job 안에서는:
- PostgreSQL도 띄우고
- Redis도 띄웁니다
그래서 Django/Celery 설정을 실제와 비슷하게 테스트할 수 있습니다.

`env:` 이 부분은 이 job 전체에서 사용할 환경변수입니다.
```yaml
env:
  DJANGO_SECRET_KEY: ci-secret-key
  DJANGO_DEBUG: "False"
  ...
```
즉, 로컬의 `.env`를 GitHub에 올리지 않고도, CI 안에서만 사용할 값들을 여기서 직접 지정한 것입니다.

`steps:` 이제 job 안에서 실제로 하나씩 실행하는 명령어들입니다.
Checkout repository
```yaml
- name: Checkout repository
  uses: actions/checkout@v4
```
GitHub 저장소 코드를 runner로 가져옵니다.
즉, 내 프로젝트 파일을 다운받는 단계입니다.
이거 없으면 아무 코드도 없어서 다음 단계가 못 돌아갑니다.

`Set up Python 3.12`
```yaml
uses: actions/setup-python@v5
with:
  python-version: "3.12"
```
Python 3.12 환경을 준비합니다.

즉, 내 프로젝트가 Python 3.12 기준이라면 CI도 같은 버전으로 맞춘 것입니다.

`Install backend dependencies`
```yaml
working-directory: backend
run: |
  python -m pip install --upgrade pip
  pip install -r requirements.txt
```
이건 `backend/requirements.txt`를 설치하는 단계입니다.
즉, Django/DRF/Celery/psycopg2 등 backend에 필요한 패키지를 설치합니다.

`Install ai-server dependencies`
```yaml
working-directory: ai-server
run: |
  pip install -r requirements.txt
```
이건 FastAPI 서버용 패키지를 설치합니다.

즉, backend와 ai-server가 서로 다른 requirements를 가지고 있으니  
각자 따로 설치하는 것입니다

`Wait for PostgreSQL`
이 부분은 Python으로 직접 소켓 연결을 시도합니다.
```yaml
with socket.create_connection(("127.0.0.1", 5432), timeout=2)
```
즉,
- Postgres 컨테이너가 뜨긴 했는지
- 5432 포트가 열렸는지를 30번까지 기다리며 확인합니다.
왜 하냐면, DB가 아직 준비 안 됐는데 바로 migrate 하면 실패하기 때문입니다.

`Install PostgreSQL client tools`
```yaml
sudo apt-get install -y postgresql-client
```
이건 `psql` 명령어를 쓰기 위해 설치하는 것입니다.

즉, 뒤에서:
```yaml
psql -h 127.0.0.1 ...
```
이걸 실행하려면 PostgreSQL client가 필요합니다

`Enable pgvector extension`
```yaml
psql \
  -h 127.0.0.1 \
  -U product_review_user \
  -d product_review_db \
  -c "CREATE EXTENSION IF NOT EXISTS vector;"
```
이건 DB 안에서 vector 확장을 실제로 켜는 단계입니다.`
중요한 차이:
- 이미지에 pgvector가 들어있는 것 = 설치
- `CREATE EXTENSION vector` = 사용 가능하게 활성화입니다.

즉, 도구가 설치되어 있음과 DB 안에서 켜서 사용함은 다릅니다.  
이 단계를 거쳐야 Django migration에서 `vector(384)` 타입을 인식합니다.

`Wait for Redis` 이건 PostgreSQL 대기와 똑같은 개념입니다.
```yaml
with socket.create_connection(("127.0.0.1", 6379), timeout=2)
```
즉 Redis가 진짜 연결 가능한 상태인지 기다립니다.

`Django system check`
```yaml
python manage.py check
```
이건 Django 설정 검사를 합니다.

즉:
- settings 문제 없는지
- 앱 등록 문제 없는지
- 기본 구성 문제 없는지를 빠르게 검사하는 단계입니다.

`Run migrations`
```yaml
python manage.py migrate --noinput
```
이건 DB 테이블을 실제로 만드는 단계입니다.

즉:
- accounts
- reviews
- ai_gateway
- interactions
- products
등의 migration을 실제 DB에 반영합니다.

여기서 `vector` 타입 문제 때문에 계속 막혔던 것이고,  
그걸 pgvector 이미지 + extension 생성으로 해결한 것입니다.

`Check missing migrations`
```bash
python manage.py makemigrations --check --dry-run
```
이건 아주 좋은 체크입니다.

뜻은:
모델을 바꿨는데 migration 파일을 안 만들고 올린 건 아니지?를 검사합니다.

즉, 로컬에서는 잘 돌아도 migration 파일을 빼먹고 push하는 실수를 잡아줍니다.


`Run Django tests`
```
python manage.py test
```

이건 말 그대로 테스트 실행입니다.

즉, 프로젝트에 작성된 테스트 코드가 실제로 통과하는지 검사합니다.

`Celery smoke import`
여기서는 Celery worker를 실제로 돌리는 건 아니고, Celery 앱 import가 되는지만 확인합니다.
```yaml
from mysite.celery import app  
print("Celery app loaded:", app.main)
```

뜻은:
- celery.py 문제 없는지
- Django settings와 연결되는지
- import 단계에서 터지지 않는지를 확인하는 최소 검증입니다.

`FastAPI smoke import`
이것도 비슷합니다.
```yaml
module = importlib.import_module("main")
```
즉 FastAPI 앱이 import 시점에 에러 없이 뜨는지 검사합니다.
실행까지는 아니고, 최소한 코드가 깨지지는 않았는지 보는 단계입니다.


`docker-build` job
이건 코드 말고 Dockerfile이 정말 빌드되는지 보는 단계입니다.

즉:
- backend 이미지 빌드
- ai-server 이미지 빌드를 합니다.

왜 필요한가요?
코드는 돌아가도 Docker 빌드가 안 되면 배포가 안 됩니다.

예를 들면:
- `COPY` 경로 잘못됨
- requirements 설치 실패
- Dockerfile 문법 오류

같은 걸 여기서 잡습니다.

`needs: app-tests`
이 뜻은: `app-tests`가 성공해야 `docker-build`가 실행된다 입니다.

즉, 코드가 깨졌으면 굳이 Docker 빌드까지 갈 필요가 없다는 뜻입니다.  
순서를 잘 짠 것입니다.

`integration-compose` job
이게 사실 가장 실무적인 단계입니다.

왜냐하면 이 단계는 실제로 배포 구조처럼 전체 서비스를 같이 띄워보는 단계이기 때문입니다.

`Create CI .env file`
여기서는 backend 폴더에 CI 전용 `.env`를 만듭니다.

왜냐하면 `docker compose`는 내부적으로 `.env` 값을 읽을 수 있기 때문입니다.

중요한 점은 여기서는 `DB_HOST=db`, `REDIS_URL=redis://redis:6379/0`, `FASTAPI_BASE_URL=http://fastapi:8001`처럼  
**docker compose 내부 서비스명 기준**으로 적혀 있다는 것입니다.

즉:
- `app-tests`는 `127.0.0.1`
- `integration-compose`는 `db`, `redis`, `fastapi` 이 차이를 이해하셔야 합니다.

`Show docker compose config`
```yaml
docker compose config
```
이건 compose 파일이 최종적으로 어떻게 해석되는지 보여줍니다.
즉 YAML 문법 문제나 env 치환 문제를 빨리 찾을 수 있습니다.

`Start full stack with docker compose`
```yaml
docker compose up -d --build
```

이건 실제로:
- web
- db
- redis
- celery
- fastapi를 한 번에 띄웁니다.
즉, 당신이 로컬에서 해본 것과 비슷한 걸 GitHub에서 자동으로 해보는 단계입니다.


`Wait for containers to initialize`
```yaml
sleep 25
```
컨테이너가 뜬 직후 바로 테스트하면 아직 초기화 중일 수 있어서  25초 기다리는 단계입니다.
아주 정교한 health check는 아니지만 실용적으로 자주 쓰는 방식입니다.


`Show running containers`
```yaml
docker compose ps
```
이건 어떤 컨테이너가 실제로 떴는지 확인합니다.

즉:
- web Up?
- fastapi Up?
- celery Up?
- db Up?
- redis Up?를 보는 단계입니다.

`Backend health check`
```bash
curl -f http://127.0.0.1:8000/admin/login/
```
이건 Django가 실제 HTTP 응답을 하는지 확인합니다.

왜 `/admin/login/`을 쓰냐면, 루트 URL보다 거의 항상 존재하는 안정적인 엔드포인트이기 때문입니다.

`FastAPI health check`
```bash
curl -f http://127.0.0.1:8001/
```
이건 FastAPI 루트 엔드포인트가 실제 응답하는지 확인합니다.


`Celery container check`
```bash
docker compose ps celery
```
이건 Celery 컨테이너가 떠 있는지 확인합니다.
즉, Celery worker가 최소한 죽지 않고 기동되었는지를 보는 것입니다.


`Print logs if failed`
```bash
if: failure()  
docker compose logs --no-color
```
이건 실패했을 때만 전체 로그를 출력합니다.

이게 아주 중요합니다.  
왜냐하면 CI가 실패해도 로그가 없으면 원인을 못 찾기 때문입니다.


`Shutdown containers`
```bash
if: always()  
docker compose down -v
```
이건 성공하든 실패하든 마지막에 컨테이너를 정리합니다.
즉, CI 러너를 깨끗한 상태로 종료하는 단계입니다.

이 파일에서 가장 중요한 핵심 개념 5개

첫째
CI는 내 로컬이 아니라 GitHub의 깨끗한 새 서버에서 실행된다.
그래서 로컬에서 되던 것도 CI에서 안 될 수 있습니다.

둘째
`app-tests`와 `integration-compose`는 DB 접속 방식이 다르다.
- app-tests: `127.0.0.1`
- integration-compose: `db`

셋째
pgvector는 Postgres 안에 있어야 한다.
호스트에 설치하는 게 아니라, DB가 돌아가는 환경에서 지원되어야 합니다.

넷째
`CREATE EXTENSION vector;`는 꼭 필요하다.
이미지가 pgvector를 포함해도, DB 안에서 확장을 켜야 `vector` 타입을 쓸 수 있습니다.

다섯째
CI는 “코드 테스트”만 하는 게 아니라 “배포 가능성 검사”까지 한다.
그래서 Docker 빌드와 docker compose 통합 검사까지 들어가 있는 것입니다.
