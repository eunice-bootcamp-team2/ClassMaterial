### ✅ STEP 7. 운영/확장 단계 (Alert + Observability)

Alert + Observability가 무엇인가?
Observability (옵저버빌리티)
```
시스템 내부 상태를 외부에서 이해할 수 있게 만드는 것

쉽게 말하면
왜 느린지 / 어디가 문제인지 알 수 있는 상태
```

구성 3가지 (핵심)
```
1. Metrics (숫자)  
→ Prometheus + Grafana (이미 완료)  
  
2. Logs (로그)  
→ 지금 우리가 찍은 logger  
  
3. Traces (흐름)  
→ 요청이 어디를 거쳤는지
```

지금 현재까지 진행한 상태
```
✔ Metrics 있음 (그래프)  
✔ Logs 일부 있음 (시간 로그)  
❌ Trace 없음 (요청 흐름 추적)
```

Alert (알람)
```
문제 발생 시 사람이 안 보고 있어도 알려주는 시스템
```
예시
```
- p95가 0.2초 넘으면 → discode 알림  
- 5xx 에러율 5% 넘으면 → 경고  
- 요청이 갑자기 0 되면 → 서버 다운
```

###### 두개의 핵심 차이는
| 구분            | 역할      |
| ------------- | ------- |
| Observability | 문제를 분석  |
| Alert         | 문제를 알려줌 |
현재까지 진행한 상태는
```
✔ 병목 의심 가능  
✔ p95 문제 확인  
✔ 그래프 해석 가능
```
그러나
```
사람이 계속 Grafana 보고 있어야 함

그래서 필요한 것:
자동 감지 + 자동 알림
```

### Alert 설계 (가장 중요)
언제 문제인지 기준 정해야 합니다.

🚨 Django
```
1. p95 > 0.2초 → 성능 문제  
2. 4xx > 10% → 사용자 오류 증가  
3. 요청 수 = 0 → 서버 다운
```

🚨 FastAPI
```
1. p95 > 0.5초 → AI 느림  
2. 5xx > 1% → 장애  
3. 요청 수 급감 → Celery 문제
```

Alert 설정 전체 흐름
```
Prometheus (감지)
        ↓
Alertmanager (알림 처리)
        ↓
Slack / Email / Discord (전송)
```

### 실제 운영용 Discord 알람 규칙

운영용 알람 설계의 핵심
```
1. 너무 많이 울리면 안됨 (노이즈 제거)  
2. 진짜 문제만 울려야 함  
3. 원인 추적 가능해야 함
```

현재 우리가 측정한 모니터링 결과 결론은 다음과 같습니다.
- 20명 동시 요청: 안정 구간
- 50명 동시 요청: p95 상승이 분명해지고, 병목 조짐이 시작되는 경계 구간
- 100명 동시 요청: p95 반복 상승, 평균 응답도 증가, 병목 진입 구간

즉 운영 알람은 이렇게 가야 합니다.
- 50명 수준에서 보이던 초기 징후를 warning
- 100명 수준에서 보이던 반복 지연을 critical
- 단순 요청 수보다 p95, 평균 응답 시간, 에러율, 트래픽 급감을 같이 봐야 함

핵심 판단
현재 진행하는 프로젝트의 모니터링 결과에서 제일 중요한 사실은 다음과 같습니다.
병목의 첫 징후는 요청 수가 많다가 아니라, 50명부터 p95가 의미 있게 튄다는 점입니다.  
평균 응답 시간은 50명에서도 아직 비교적 안정적이지만, p95가 0.22초까지 올라가며 일부 요청이 느려지기 시작했습니다. 이를 병목 시작 신호, 경계로 해석합니다.

운영용 알람 설계 원칙
첫째, p95를 가장 중요한 선행지표로 둡니다.  
둘째, 평균 응답 시간은 보조 지표로 둡니다.  
셋째, 50명 부근은 장애가 아니라 경계 진입이므로 warning으로 둡니다.  
넷째, 100명 수준에서 보인 패턴은 critical로 둡니다.  
다섯째, 테스트용처럼 즉시 울리는 방식이 아니라 `for`를 넣어 노이즈를 제거해야 합니다.

(1) Django p95 경고 알람
50명 부근에서 p95가 약 0.22초까지 상승했으므로, 운영 경계선은 0.20초 초과가 맞습니다. 실제 측정 결과를 토대로 정한 기준입니다.

`backend/prometheus/alert_rules.yml`
```yaml
- alert: DjangoHighP95Warning
        expr: |
          histogram_quantile(
            0.95,
            sum(rate(ai_analyze_duration_seconds_bucket[1m])) by (le)
          ) > 0.20
        for: 2m
        labels:
          severity: warning
          service: django
        annotations:
          summary: "Django p95 latency warning"
          description: "Django p95가 0.20초를 초과했습니다. 50명 이상 부하에서 관찰된 병목 조짐과 유사합니다."
```
50명 부하에서 p95가 약 0.22초까지 상승했고, 그 시점이 병목 시작 구간입니다.

(2) Django p95 심각 알람
100명 구간에서는 p95가 한 번만 튄 게 아니라 반복 상승했습니다. 그래서 critical은 warning보다 확실히 높게 잡아야 합니다.
- 0.30초 초과
- `for: 3m`
```yaml
- alert: DjangoHighP95Critical
        expr: |
          histogram_quantile(
            0.95,
            sum(rate(ai_analyze_duration_seconds_bucket[1m])) by (le)
          ) > 0.30
        for: 3m
        labels:
          severity: critical
          service: django
        annotations:
          summary: "Django p95 latency critical"
          description: "Django p95가 0.30초를 초과한 상태가 지속되고 있습니다. 병목 진입 가능성이 높습니다."
```
100명 구간에서 평균 응답 시간도 증가하고, p95가 반복적으로 튀며 병목 진입으로 판단합니다.

(3) Django 평균 응답 시간 경고 알람
50명에서는 평균이 아직 버텼지만, 100명에서는 평균도 올라가기 시작했습니다. 즉 평균 응답 시간은 후행 지표입니다.  
그래서 p95보다 덜 민감하게, 그러나 병목이 본격화되면 함께 잡히게 두는 것이 좋습니다.
- 평균 응답 시간 > 0.07초
- `for: 3m`
```yaml
- alert: DjangoMeanLatencyHigh
        expr: |
          (
            rate(ai_analyze_duration_seconds_sum[1m])
            /
            clamp_min(rate(ai_analyze_duration_seconds_count[1m]), 1e-9)
          ) > 0.07
        for: 3m
        labels:
          severity: warning
          service: django
        annotations:
          summary: "Django mean latency high"
          description: "Django 평균 응답 시간이 상승했습니다. p95와 함께 병목 여부를 확인하세요."
```

(4) Django 4xx 에러율 알람은 운영에서 분리해서 봐야 함
업로드한 테스트는 일부러 `999999` 같은 실패 요청을 섞었기 때문에, 4xx는 테스트 상황에서는 정상 증가였습니다. 그래서 이 기준을 운영에 그대로 쓰면 오탐이 날 수 있습니다. 실습을 위한 테스트로 4xx 증가는 구조상 의도된 실패입니다.

그래도 운영에서는 유효하니, 너무 예민하지 않게 둡니다.
```yaml
- alert: DjangoHigh4xxRate
        expr: |
          (
            sum(rate(django_http_responses_total_by_status_view_method_total{status=~"4.."}[5m]))
            /
            clamp_min(sum(rate(django_http_responses_total_by_status_view_method_total[5m])), 1e-9)
          ) > 0.10
        for: 5m
        labels:
          severity: warning
          service: django
        annotations:
          summary: "Django 4xx error rate high"
          description: "Django 4xx 에러율이 10%를 초과했습니다."
```

(5) FastAPI 5xx 에러율 알람
모니터링 결과상 FastAPI는 병목으로 보이지 않았고, 5xx도 거의 없었습니다. 즉 FastAPI 쪽은 성능 경고보다 장애 감지용 알람이 더 중요합니다. 모니터링 결과 FastAPI는 병목이 없었습니다.
```yaml
- alert: FastAPIHigh5xxRate
        expr: |
          (
            sum(rate(http_requests_total{status=~"5.."}[5m]))
            /
            clamp_min(sum(rate(http_requests_total[5m])), 1e-9)
          ) > 0.05
        for: 1m
        labels:
          severity: critical
          service: fastapi
        annotations:
          summary: "FastAPI 5xx error rate high"
          description: "FastAPI 5xx 에러율이 5%를 초과했습니다."
```

(6) 요청 급감 / 서비스 정지 알람
알람의 핵심은 요청 수가 갑자기 0이 되면 서버 다운이 됩니다.
```yaml
- alert: DjangoNoTraffic
        expr: |
          sum(rate(ai_analyze_request_total[1m])) < 0.01
        for: 2m
        labels:
          severity: critical
          service: django
        annotations:
          summary: "Django no traffic"
          description: "AI 분석 요청 수가 거의 없습니다."
```

FastAPI도 넣습니다
```yaml
- alert: FastAPINoTraffic
        expr: |
          sum(rate(http_requests_total{handler="/api/v1/recommend/similarity"}[5m])) < 0.01
        for: 3m
        labels:
          severity: warning
          service: fastapi
        annotations:
          summary: "FastAPI no traffic"
          description: "FastAPI 요청이 거의 없습니다. Celery 큐 또는 호출 경로를 확인하세요."
```

운영 기준 정리
- 안정 구간: 20명 수준
- 경계 구간: 50명 수준
- 위험 구간: 100명 수준

그래서 알람도 2단계로 나눕니다.
- warning
    - Django p95 > 0.20초
    - Django 평균 응답 시간 > 0.07초
    - Django 4xx > 10%
- critical
    - Django p95 > 0.30초
    - FastAPI 5xx > 5%
    - 요청 수 0

```yaml
          summary: "Django p95 latency critical"
          description: "Django p95가 0.30초를 초과한 상태가 지속되고 있습니다. 병목 진입 가능성이 높습니다."

      - alert: DjangoMeanLatencyHigh
        expr: |
          (
            rate(ai_analyze_duration_seconds_sum[1m])
            /
            clamp_min(rate(ai_analyze_duration_seconds_count[1m]), 1e-9)
          ) > 0.07
        for: 3m
        labels:
          severity: warning
          service: django
        annotations:
          summary: "Django mean latency high"
          description: "Django 평균 응답 시간이 상승했습니다. p95와 함께 병목 여부를 확인하세요."

      - alert: DjangoHigh4xxRate
        expr: |
          (
            sum(rate(django_http_responses_total_by_status_view_method_total{status=~"4.."}[5m]))
            /
            clamp_min(sum(rate(django_http_responses_total_by_status_view_method_total[5m])), 1e-9)
          ) > 0.10
        for: 5m
        labels:
          severity: warning
          service: django
        annotations:
          summary: "Django 4xx error rate high"
          description: "Django 4xx 에러율이 10%를 초과했습니다."

      - alert: DjangoNoTraffic
        expr: |
          sum(rate(ai_analyze_request_total[1m])) < 0.01
        for: 2m
        labels:
          severity: critical
          service: django
        annotations:
          summary: "Django no traffic"
          description: "AI 분석 요청 수가 거의 없습니다."

  - name: fastapi-alerts
    rules:
      - alert: FastAPIHigh5xxRate
        expr: |
          (
            sum(rate(http_requests_total{status=~"5.."}[5m]))
            /
            clamp_min(sum(rate(http_requests_total[5m])), 1e-9)
          ) > 0.05
        for: 1m
        labels:
          severity: critical
          service: fastapi
        annotations:
          summary: "FastAPI 5xx error rate high"
          description: "FastAPI 5xx 에러율이 5%를 초과했습니다."

      - alert: FastAPINoTraffic
        expr: |
          sum(rate(http_requests_total{handler="/api/v1/recommend/similarity"}[5m])) < 0.01
        for: 3m
        labels:
          severity: warning
          service: fastapi
        annotations:
          summary: "FastAPI no traffic"
          description: "FastAPI 요청이 거의 없습니다. Celery 큐 또는 호출 경로를 확인하세요."
```

### k6 테스트 시나리오를 3가지로 나누기
```
1. p95 / 평균응답시간 테스트 → k6 파일 1개  
2. 4xx 에러율 테스트 → k6 파일 1개  
3. no traffic 테스트 → k6 없이 대기
```

기존 테스트 하던 k6파일은 backend/k6_ai_analyze_mixed.js 로 이름을 변경해둡니다.
그리고 용도는 정상 + 실패 요청을 섞어서 전체 시스템 반응을 보는 종합 관찰용입니다.
- 기존 파일 → 종합 관찰용
- 새 파일 2개 → 알람 검증용
```
backend/
├── k6_ai_analyze_mixed.js     # 기존 파일 (종합 관찰용)
├── k6_alert_p95.js            # p95 / 평균 응답 시간 알람 검증용
└── k6_alert_4xx.js            # 4xx 에러율 알람 검증용
```


p95 warning/critical 테스트용 (새로 작성)
`backend/k6_alert_p95.js`
```js
import http from 'k6/http';
import { sleep, check } from 'k6';

export const options = {
  vus: 50,
  duration: '3m',
};

export default function () {
  const reviewId = 43;

  const res = http.post(`http://127.0.0.1:8000/ai/reviews/${reviewId}/analyze/`);

  check(res, {
    'status is 202': (r) => r.status === 202,
  });

  sleep(1);
}
```
이 파일은 정상 요청만 계속 보내서 p95와 평균 응답 시간을 올려보는 용도입니다.

- `DjangoHighP95Warning`
- `DjangoHighP95Critical`
- `DjangoMeanLatencyHigh`

✅ 최종 해석

본 테스트는 Django 서비스의 p95 응답 시간 기반 경고 알람(`DjangoHighP95Warning`)의 정상 동작 여부를 검증하기 위해 수행되었다.

테스트는 k6를 이용하여 동시 사용자 50명, 3분 동안 부하를 발생시키는 방식으로 진행되었으며, 예상 결과는 p95 응답 시간이 0.20초를 초과하고 해당 상태가 2분 이상 유지될 경우 경고 알람이 발생하는 것이었다.

그러나 실제 테스트 결과에서는 다음과 같은 현상이 관찰되었다.
- Django 요청 수는 증가하여 부하 테스트가 정상적으로 수행되었음을 확인하였다.
- 그러나 평균 응답 시간과 p95 응답 시간은 모두 안정적인 수준을 유지하였으며, p95 값은 설정된 임계값(0.20초)을 초과하지 않았다.
- 이에 따라 `DjangoHighP95Warning` 알람은 발생하지 않았으며, Prometheus에서도 해당 알람은 INACTIVE 상태를 유지하였다.
- 반면, 테스트 시작 이전 요청이 없는 상태에서는 `DjangoNoTraffic` 알람이 정상적으로 발생하였고, 이후 요청이 발생함에 따라 해당 알람은 정상적으로 해제되는 흐름을 보였다.

이 결과는 알람 시스템 자체의 문제를 의미하는 것이 아니라, 현재 테스트 환경에서 동시 사용자 50명 수준의 부하는 설정된 p95 임계값을 초과하기에 충분하지 않았음을 의미한다.

### 테스트 D. DjangoMeanLatencyHigh 검증
이건 p95 테스트와 같이 올라올 가능성이 큽니다.

모니터링 결과평균 응답 시간은 50명에서는 아직 안정적이지만, 100명에서 증가하기 시작합니다. 그래서 평균 응답 시간은 p95보다 뒤늦게 반응하는 보조 지표입니다.

- Grafana에서 평균 응답 시간 패널 확인

- 즉 장애가 없는 것일 수도 있지만, 동시에 알람 기준이 현실과 안 맞는 것일 수도 있습니다

지금 결과 기준 해석하면:
- 50명, 100명 부하에서도 `p95 > 0.20`가 지속되지 않음

- 4xx/5xx도 의미 있게 증가하지 않음

```

```

### 조치사항
p95 warning 기준 낮추기

현재설정:
```yaml
> 0.20
```

조치사항
```yaml
warning: > 0.15  
critical: > 0.20
```
이유:
- 지금 테스트에서 p95가 대체로 0.10~0.15 근처에서 움직였음
- 0.20은 현재 시스템에서 너무 높은 경계일 수 있음
- warning은 “병목 시작 조짐”을 잡아야 하므로 더 민감해야 함
```yaml
- alert: DjangoHighP95Warning
  expr: |
    histogram_quantile(
      0.95,
      sum(rate(ai_analyze_duration_seconds_bucket[1m])) by (le)
    ) > 0.15
  for: 2m
```

평균 응답 시간 기준도 조금 낮추기

현재설정:
```yaml
> 0.07
```

조치사항
```yaml
warning: > 0.06
```
이유:
- 현재 평균이 0.04~0.05 수준이면
- 0.07은 꽤 많이 느려져야만 울림
- 평균은 p95보다 둔감하므로 약간 더 민감하게 잡아도 됨
```yaml
- alert: DjangoMeanLatencyHigh
  expr: |
    (
      rate(ai_analyze_duration_seconds_sum[1m])
      /
      clamp_min(rate(ai_analyze_duration_seconds_count[1m]), 1e-9)
    ) > 0.06
  for: 3m
```

`NoTraffic`는 개발 단계에서 너무 민감하니 분리 운영
지금 `DjangoNoTraffic`가 잘 뜨는 건 정상입니다.  
하지만 개발/실습 환경에서는 요청이 원래 없을 시간이 많아서 너무 자주 울릴 수 있습니다.

그래서 지금은 이렇게 하는 걸 권장합니다.

개발 중:
- `DjangoNoTraffic`는 주석 처리하거나
- `for`를 더 길게 늘리기

예:
```
for: 10m
```

운영:
- 다시 활성화

조치사항 수정후 다시 테스트를 진행해 봅니다.

```python
from fastapi import APIRouter, HTTPException
from schemas.recommend_schema import (
    EmbeddingRequest,
    SimilarityRequest,
    SimilarityResponse,
)
from services.recommend_service import calculate_similarity, make_embeddings

router = APIRouter(prefix="/api/v1/recommend", tags=["recommend"])


@router.post("/embed")
def embed_text(request: EmbeddingRequest):
    vectors = make_embeddings(request.texts)
    return {"embeddings": vectors}


@router.post("/similarity", response_model=SimilarityResponse)
def similarity(payload: SimilarityRequest):
    return {"similarity": calculate_similarity(payload.text1, payload.text2)}
```
