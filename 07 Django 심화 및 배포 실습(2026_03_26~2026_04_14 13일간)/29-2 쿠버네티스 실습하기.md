기존에 Docker Compose로 구성된 프로젝트를  
Kubernetes 환경에서 동일하게 동작하도록 구성하고, 운영 개념까지 이해하는 것입니다

◈ 실습을 완료하면 다음을 할 수 있게 됩니다

- Docker Compose로 구성된 서비스를  
    → Kubernetes의 Deployment와 Service 구조로 변환할 수 있습니다
- Django, FastAPI, Redis, PostgreSQL 간의 통신을  
    → IP가 아닌 Service 이름 기반으로 연결할 수 있습니다
- 기존 `.env` 파일의 설정값을  
    → ConfigMap과 Secret으로 분리하여 관리할 수 있습니다
- Pod를 일부러 삭제하더라도  
    → Kubernetes가 자동으로 다시 생성하여  
    서비스가 유지되는 구조를 확인할 수 있습니다
- Ingress를 설정하여  
    → 브라우저에서 도메인 기반으로 서비스에 접근할 수 있습니다
- HPA(Horizontal Pod Autoscaler)를 통해  
    → 부하에 따라 Pod 개수가 자동으로 증가/감소하는 것을 직접 체험할 수 있습니다

---
◈ 이번 실습의 핵심 변화

기존 Docker Compose에서는 다음과 같은 구조였습니다.
```
사용자 → Django → Celery → Redis → Celery Worker → FastAPI → DB
```
그리고 서비스 간 통신은 다음과 같이 이루어졌습니다.
```
http://fastapi:8001  
redis:6379  
db:5432
```
---
◈ Kubernetes에서는 이렇게 바뀝니다
구조 자체는 동일하지만 접속 방식과 운영 방식이 Kubernetes 방식으로 변경됩니다
```
http://fastapi-service:8001  
redis-service:6379  
postgres-service:5432
```
즉, 서비스 이름이 Kubernetes Service 이름으로 변경될 뿐이며 전체 아키텍처 흐름은 그대로 유지됩니다

Docker로 만든 구조를 Kubernetes에서 자동 운영 구조로 바꾸는 것이 이번 실습의 목표입니다

✅ 각각의 역할 (이미지 기준 완성 정리)
- **User / Internet** = 사용자 요청 (서비스 시작점)
---
🌐 External Entry & Routing
- **LoadBalancer** = 외부에서 들어오는 입구 (공인 IP 제공)
- **Ingress** = 길 안내 (도메인/URL 기반 라우팅)
---
⚙️ Service & Workload Layer
- **Kubernetes Service (ClusterIP)** = 내부 교차로 (Pod로 트래픽 분산)
- **Pod** = 작업 공간 (컨테이너 실행 단위)
- **Container (Django / FastAPI)** = 실제 일하는 서버 (애플리케이션 실행)
---
🔐 설정 관리
- **ConfigMap** = 설정 파일 저장소 (환경변수 관리)
- **Secret** = 비밀 금고 (DB 비밀번호 / API 키)
---
🗄️ Data & Background Task
- **PostgreSQL (StatefulSet + PVC)** = 데이터 창고 (데이터 영구 저장)
- **Redis** = 빠른 메모리 캐시 (데이터 임시 저장 + 큐)
- **Celery** = 백그라운드 작업 처리자 (비동기 작업 실행)
---
📊 Monitoring & Automation
- **metrics endpoint** = 상태 보고 창구 (/metrics 데이터 제공)
- **Prometheus** = 감시 시스템 (메트릭 수집)
- **Grafana** = 대시보드 (데이터 시각화)
- **Alertmanager** = 경보 시스템 (이상 발생 시 알림)
- **HPA** = 자동 증설 시스템 (부하에 따라 Pod 수 증가)
- **Self-healing** = 자동 복구 기능 (Pod 죽으면 자동 재생성)

```bash
sudo install -o root -g root -m 0755 kubectl /usr/local/bin/kubectl
kubectl version --client
```

#### STEP 3. Docker 이미지 준비
이 단계의 목표
```
Kubernetes가 사용할 Django 이미지와 FastAPI 이미지를 먼저 만듧니다.
그리고 Minikube 안에서 그 이미지를 사용할 수 있게 만듧니다.
```
Docker Compose에서는 `build:`가 있으면 `docker compose up -d` 할 때 알아서 이미지 빌드와 컨테이너 실행이 같이 진행됩니다.  
하지만 Kubernetes는 그런 방식이 아니라, 이미 존재하는 이미지를 가져다가 Pod를 띄우는 구조입니다.

왜 이 단계가 필요한가요?
지금까지는 Docker Compose에서 이런 느낌으로 작업했습니다.
```yml
web:
  build: .
fastapi:
  build: ../ai-server
```
즉 Compose가:
- Dockerfile을 보고
- 이미지를 만들고
- 그 이미지로 컨테이너를 띄워줬습니다
Compose 동작 방식
```
build: .  
→ Dockerfile로 이미지 자동 생성 
→ Docker Compose는 build: . 을 사용하면  
Dockerfile로 이미지를 자동 생성하고 프로젝트명 기반으로 이미지 이름을 자동으로 붙입니다.
```
그래서 우리는 “이미지 이름”을 신경 안 써도 됐습니다.

그런데 Kubernetes는 yaml 안에 보통 이렇게 씁니다.
```bash
spec:
      containers:
        - name: django
          image: review-django:local
          imagePullPolicy: IfNotPresent
```
containers: 이 Pod 안에 어떤 컨테이너를 띄울지
name: django 컨테이너 이름 (별명)
image: review-django:local 내가 직접 만든 Docker 이미지 이름

그런데 Kubernetes는 다릅니다. 
```
build 기능 없음 그래서 이렇게 요구합니다. 
```

Kubernetes는 ❗
```bash
"이미지는 준비되어 있겠지? 그걸로 Pod를 만들겠다."
```
그래서 우리가 먼저 해야 하는 일이:
1. Docker 이미지 빌드
2. Minikube가 도커에서 빌드한 이미지를 볼 수 있게 복사(로드)
3. 쿠버네티스 yaml에서 i`mage: review-django:local` 내가 직접 만든 Docker 이미지 이름을 사용

#### STEP 5. PostgreSQL 배포
Docker에서 DB 컨테이너를 띄우던 것을  
이제 Kubernetes가 DB를 대신 띄우고 관리하도록 바꾸는 단계입니다.

PostgreSQL 배포 개요
PostgreSQL 데이터베이스를 Kubernetes 환경에서 실행할 수 있도록 설정합니다.  
지금까지 (Docker 기준)
```
db 컨테이너 실행  
→ Django / FastAPI가 db로 접속
```
도커는 단순히 컨테이너가 하나였습니다.

Kubernetes에서는 이렇게 바뀝니다
DB 하나를 이렇게 나눠서 관리합니다
- StatefulSet → DB Pod 실행 및 유지
- Service → 접속 주소 제공
- PVC → 데이터 저장

왜 이렇게 나누나요? 이유는 3가지 입니다.

1️⃣ DB를 자동으로 관리
	DB가 죽으면 Kubernetes가 다시 실행합니다
2️⃣ 이름으로 접속 가능
```
postgres-service
```
Django에서 이렇게 사용:
```
DB_HOST = postgres-service
```
	
3️⃣ 데이터 유지 (중요 ⭐)
	Pod가 죽어도 데이터는 남습니다
	PVC가 저장해줌

가장 중요한 부분 ⭐ : Django 설정과 반드시 맞아야 합니다
```python
DB_NAME
DB_USER
DB_PASSWORD
DB_HOST
DB_PORT
```
특히 이것 중요:
```
DB_HOST = postgres-service
```

Docker의 db 컨테이너를 Kubernetes에서는 Pod + Service + PVC로 나눠서 
더 안전하게 운영하는 것입니다

---
`k8s/base/postgres.yaml`
```yml
# =========================================
# PostgreSQL 구성 전체 개념
# -----------------------------------------
# 이 파일은 PostgreSQL을 쿠버네티스에서 실행하기 위해
# 아래 3가지 역할로 나누어 작성한 파일입니다.
#
# 1. StatefulSet → DB Pod 실행 및 유지
# 2. Service     → DB 접속 주소 제공
# 3. PVC         → DB 데이터 저장
#
# 즉,
# "DB를 실행하고 / 접속 가능하게 하고 / 데이터는 유지되게 한다"
# 를 한 파일에 정의한 것입니다.
# =========================================

# =========================================
# [1] PostgreSQL Headless Service
# -----------------------------------------
# 역할:
# - StatefulSet의 안정적인 네트워크 식별용
# - DB Pod 자체를 위한 서비스
# =========================================
apiVersion: v1
kind: Service
metadata:
  name: postgres
  namespace: review-k8s
  labels:
    app: postgres
spec:
  clusterIP: None
  selector:
    app: postgres
  ports:
    - name: postgres
      port: 5432
      targetPort: 5432

---
# =========================================
# [2] PostgreSQL 일반 Service
# -----------------------------------------
# 역할:
# - Django / FastAPI / Celery 가 실제로 접근할 DB 주소 제공
# - DB_HOST=postgres-service 와 연결되는 실제 Service 이름
# =========================================
apiVersion: v1
kind: Service
metadata:
  name: postgres-service
  namespace: review-k8s
  labels:
    app: postgres
spec:
  type: ClusterIP
  selector:
    app: postgres
  ports:
    - name: postgres
      port: 5432
      targetPort: 5432

---
# =========================================
# [3] PostgreSQL StatefulSet
# -----------------------------------------
# 역할:
# - PostgreSQL 컨테이너를 실행
# - DB Pod를 유지/복구
# - 상태 저장형 DB이므로 StatefulSet 사용
# =========================================
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgres
  namespace: review-k8s
spec:
  serviceName: postgres
  replicas: 1
  selector:
    matchLabels:
      app: postgres

  template:
    metadata:
      labels:
        app: postgres
    spec:
      terminationGracePeriodSeconds: 30

      containers:
        - name: postgres
          image: ankane/pgvector:v0.5.1
          imagePullPolicy: IfNotPresent

          ports:
            - name: postgres
              containerPort: 5432

          env:
            # DB 이름
            - name: POSTGRES_DB
              valueFrom:
                configMapKeyRef:
                  name: review-config
                  key: DB_NAME

            # DB 사용자명
            - name: POSTGRES_USER
              valueFrom:
                configMapKeyRef:
                  name: review-config
                  key: DB_USER

            # DB 비밀번호
            - name: POSTGRES_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: review-secret
                  key: DB_PASSWORD

            # PostgreSQL 데이터 저장 경로
            - name: PGDATA
              value: /var/lib/postgresql/data/pgdata

            # 시간대
            - name: TZ
              value: Asia/Seoul
            - name: PGTZ
              value: Asia/Seoul

          volumeMounts:
            - name: postgres-data
              mountPath: /var/lib/postgresql/data

          resources:
            requests:
              cpu: "100m"
              memory: "256Mi"
            limits:
              cpu: "500m"
              memory: "512Mi"

          # DB가 요청 받을 준비가 되었는지 확인
          readinessProbe:
            exec:
              command:
                - sh
                - -c
                - pg_isready -U "$POSTGRES_USER" -d "$POSTGRES_DB"
            initialDelaySeconds: 10
            periodSeconds: 5
            timeoutSeconds: 3
            failureThreshold: 6

          # DB 프로세스가 살아있는지 확인
          livenessProbe:
            exec:
              command:
                - sh
                - -c
                - pg_isready -U "$POSTGRES_USER" -d "$POSTGRES_DB"
            initialDelaySeconds: 30
            periodSeconds: 10
            timeoutSeconds: 5
            failureThreshold: 6

  # =========================================
  # [4] PVC 자동 생성
  # -----------------------------------------
  # 역할:
  # - DB 데이터를 디스크에 저장
  # - Pod가 재생성되어도 데이터 유지
  # =========================================
  volumeClaimTemplates:
    - metadata:
        name: postgres-data
      spec:
        accessModes:
          - ReadWriteOnce
        resources:
          requests:
            storage: 5Gi
```

PostgreSQL YAML 전체 흐름
```
1. DB Pod 실행 (StatefulSet)
   → PostgreSQL 컨테이너를 쿠버네티스가 실행하고 유지한다

2. DB 접속 주소 만들기 (Service)
   → 다른 서비스(Django, FastAPI)가 
     postgres-service:5432 로 접속할 수 있게 한다

3. 환경변수 연결 (ConfigMap / Secret)
   → DB_NAME, DB_USER, DB_PASSWORD 등을
     settings.py와 동일한 이름으로 주입한다

4. 데이터 저장 (PVC)
   → 컨테이너가 죽어도 DB 데이터는 유지되게 한다

5. 상태 체크 (Probe)
   → readinessProbe: DB가 준비되었는지 확인 (트래픽 허용 여부)  
   → livenessProbe: DB가 죽었는지 확인 (문제 시 재시작)
```
PostgreSQL을 실행하고, 접속 가능하게 만들고, 데이터는 안전하게 저장하고, 문제가 생기면 자동으로 복구하도록 설정한 파일입니다

#### STEP 6. Redis 배포

반드시 해야 하는 건
```
Redis 주소를 Kubernetes 기준으로 바꾸는 것
```

왜 바꿔야 하냐면 현재 코드는 아래와 같습니다.
`mysite/settings.py` : 이건 Docker Compose에서 쓰던 이름
```python
REDIS_URL = os.getenv("REDIS_URL", "redis://redis:6379/0")
```

❗ Kubernetes에서는 다름
```
Service 이름 = redis-service
```
그래서 실제 접속 주소:
```
redis://redis-service:6379/0
```

그러나 선택지는 2개가 있으며 
- settings.py 그대로 두고  
👉 ConfigMap에서 바꾸기 
그래야 환경마다 설정을 다르게 쓸수 있기 때문입니다.

❗ 만약 settings.py를 직접 수정하면
```python
REDIS_URL = "redis://redis-service:6379/0"
```
👉 문제 발생
```
Docker에서는 redis-service 없음 ❌  
→ 연결 실패
```

그래서 settings.py의 코드 수정 없이 ConfigMap에서 바꾸기로 진행하며 이게 실무 방식입니다.

Redis가 Kubernetes에서 동작하는 과정
```
1. kubectl apply로 Deployment와 Service가 생성된다
   쿠버네티스에 Redis를 실행하는 설정을 등록한다
     
2. Deployment가 Redis Pod를 생성한다
   쿠버네티스가 Redis를 실행하기 위한 작업을 시작한다
    
3. Pod 안에서 redis:7 컨테이너가 실행된다
   실제 Redis 프로그램이 실행된다
     
4. readinessProbe가 요청을 받을 준비 상태인지 확인한다
   Redis가 사용할 준비가 되었는지 확인한다 (아직 준비 안 되면 연결 안 시켜줌)
   
5. Service(redis-service)가 내부 접속 주소를 제공한다
   다른 프로그램이 Redis에 접속할 수 있도록 redis-service라는 주소를 만들어준다
   
6. Django / Celery가 redis-service:6379로 Redis에 접속한다
   Django와 Celery가 그 주소로 Redis를 사용한다
   
7. livenessProbe가 계속 상태를 확인한다
   Redis가 살아있는지 계속 체크한다
   
8. Pod 장애 시 Deployment가 새 Pod를 재생성한다
   Redis가 죽으면 자동으로 다시 실행된다
```

`k8s/base/redis.yaml`
```yaml
# =========================================
# Redis 구성 전체 개념
# -----------------------------------------
# 이 파일은 Redis를 Kubernetes에서 사용하기 위해
# 아래 2가지 리소스를 정의합니다.
#
# 1. Deployment
#    - Redis Pod를 생성한다
#    - Redis 컨테이너를 실행한다
#    - Pod가 죽으면 다시 만든다
#    - 상태 확인(Probe)과 리소스 제한도 함께 설정한다
#
# 2. Service
#    - Django / Celery가 Redis에 접속할 수 있는
#      내부 주소(redis-service)를 제공한다
#
# 즉, 이 파일은
# "Redis를 실행하고 / 유지하고 / 내부에서 접속 가능하게 만드는"
# 역할을 한다.
# =========================================

# =========================================
# [1] Redis Deployment
# -----------------------------------------
# 역할:
# - redis:7 이미지를 사용해 Redis Pod를 생성한다
# - Pod가 죽으면 다시 생성한다
# - 리소스 사용량을 제한한다
# - readiness/liveness probe로 상태를 확인한다
# =========================================
apiVersion: apps/v1
kind: Deployment
metadata:
  name: redis
  namespace: review-k8s
spec:
  replicas: 1
  selector:
    matchLabels:
      app: redis

  template:
    metadata:
      labels:
        app: redis
    spec:
      containers:
        - name: redis
          image: redis:7

          # Redis가 컨테이너 내부에서 사용하는 포트
          ports:
            - containerPort: 6379

          # -----------------------------
          # 리소스 설정
          # -----------------------------
          # requests: 최소 보장 자원
          # limits: 최대 사용 가능 자원
          # Redis가 너무 많은 CPU/메모리를 쓰지 않도록 제한
          resources:
            requests:
              cpu: "50m"
              memory: "128Mi"
            limits:
              cpu: "200m"
              memory: "256Mi"

          # -----------------------------
          # readinessProbe
          # -----------------------------
          # Redis가 요청을 받아도 되는 준비 상태인지 확인
          # 준비되지 않았으면 Service 연결 대상에서 제외됨
          readinessProbe:
            tcpSocket:
              port: 6379
            initialDelaySeconds: 5
            periodSeconds: 5

          # -----------------------------
          # livenessProbe
          # -----------------------------
          # Redis가 살아있는지 확인
          # 문제가 있으면 Kubernetes가 컨테이너를 재시작함
          livenessProbe:
            tcpSocket:
              port: 6379
            initialDelaySeconds: 10
            periodSeconds: 10

---
# =========================================
# [2] Redis Service
# -----------------------------------------
# 역할:
# - Django / Celery가 Redis에 접근할 수 있는
#   내부 주소(redis-service)를 만든다
#
# settings.py / ConfigMap 과 연결되는 핵심 주소:
# REDIS_URL = redis://redis-service:6379/0
#
# type: ClusterIP
# - 클러스터 내부에서만 접근 가능
# - 외부 브라우저 접근용이 아니라 내부 통신용 서비스
# =========================================
apiVersion: v1
kind: Service
metadata:
  name: redis-service
  namespace: review-k8s
spec:
  type: ClusterIP
  selector:
    app: redis
  ports:
    - port: 6379
      targetPort: 6379
```

Redis YAML 전체 흐름
```
Redis YAML 전체 흐름

1. Deployment가 Redis Pod를 생성한다
   → Redis 프로그램을 실행한다

2. Deployment가 Redis Pod를 계속 유지한다
   → Redis가 꺼지면 자동으로 다시 켜준다

3. 리소스 사용 범위를 지정한다
   → Redis가 사용할 CPU랑 메모리를 제한한다 (너무 많이 못 쓰게 막아주는 설정)

4. Redis 상태를 확인한다
   → Redis가 정상적으로 실행됐는지 확인한다
   → 문제가 생기면 다시 실행한다

5. Service(redis-service)를 생성한다
   → Redis에 접속할 수 있는 이름(주소)을 만들어준다

6. 다른 서비스가 redis-service 이름으로 Redis에 접속한다
   → Django / Celery가 그 주소로 Redis를 사용한다
```
이 파일은 Redis를 Kubernetes에 배포하기 위해 Deployment로 실행/유지하고,
Probe로 상태를 확인하며, Service(redis-service)로 Django와 Celery가 내부 네트워크에서 접속할 수 있게 만드는 설정입니다.

핵심이해
```
postgres → 내부 Pod 직접 연결용 (Headless)  
postgres-service → Django가 접속하는 주소
```
이줄의 의미
```bash
postgres ClusterIP None <none> 5432/TCP
```
이건 Headless Service 라고 합니다.

Headless Service란?
	IP를 하나 주는 게 아니라 Pod에 직접 연결되게 하는 방식

#### STEP 7. FastAPI 배포
이제 AI 서버를 Deployment + Service로 띄웁니다.  
K8s 문서에서 말한 API 앱이 AI 앱을 호출하는 내부 통신 환경 구축 단계에 해당합니다.

`k8s/base/fastapi.yaml`
```yml
# =========================================
# FastAPI 구성 전체 개념
# -----------------------------------------
# 이 파일은 FastAPI를 Kubernetes에서 사용하기 위해
# 아래 2가지 리소스를 정의합니다.
#
# 1. Deployment
#    - FastAPI Pod를 생성한다
#    - FastAPI 컨테이너를 실행한다
#    - Pod가 죽으면 다시 만든다
#    - 포트, 리소스, 상태 확인(Probe)도 함께 설정한다
#
# 2. Service
#    - Django가 FastAPI에 접속할 수 있는
#      내부 주소(fastapi-service)를 제공한다
#
# 즉, 이 파일은
# "FastAPI를 실행하고 / 유지하고 / 내부에서 접속 가능하게 만드는"
# 역할을 한다.
# =========================================

# =========================================
# [1] FastAPI Deployment
# -----------------------------------------
# 역할:
# - review-fastapi:local 이미지를 사용해 FastAPI Pod를 생성한다
# - Pod가 죽으면 다시 생성한다
# - FastAPI가 사용하는 포트(8001)를 연다
# - 리소스 사용량을 제한한다
# - readiness/liveness probe로 상태를 확인한다
#
# [프로젝트 설정과 반드시 맞아야 하는 부분]
# - Django는 FASTAPI_BASE_URL 값을 읽어서 FastAPI를 호출한다
# - Kubernetes에서는 보통 ConfigMap에서 아래처럼 맞춘다
#   FASTAPI_BASE_URL=http://fastapi-service:8001
# =========================================
apiVersion: apps/v1
kind: Deployment
metadata:
  name: fastapi
  namespace: review-k8s
  labels:
    app: fastapi
spec:
  replicas: 1
  selector:
    matchLabels:
      app: fastapi

  template:
    metadata:
      labels:
        app: fastapi
    spec:
      containers:
        - name: fastapi
          image: review-fastapi:local
          imagePullPolicy: IfNotPresent

          # FastAPI 컨테이너가 내부에서 사용하는 포트
          ports:
            - containerPort: 8001

          # -----------------------------
          # 환경 설정
          # -----------------------------
          # FastAPI 자체에서 직접 쓰지 않더라도
          # 운영 시 시간대 통일을 위해 넣어둔다
          env:
            - name: TZ
              value: Asia/Seoul

          # -----------------------------
          # 리소스 설정
          # -----------------------------
          # requests: 최소 보장 자원
          # limits: 최대 사용 가능 자원
          # FastAPI가 너무 많은 CPU/메모리를 쓰지 않도록 제한
          resources:
            requests:
              cpu: "100m"
              memory: "256Mi"
            limits:
              cpu: "500m"
              memory: "512Mi"

          # -----------------------------
          # readinessProbe
          # -----------------------------
          # FastAPI가 요청을 받아도 되는 준비 상태인지 확인
          # 준비되지 않았으면 Service 연결 대상에서 제외됨
          readinessProbe:
            tcpSocket:
              port: 8001
            initialDelaySeconds: 5
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 6

          # -----------------------------
          # livenessProbe
          # -----------------------------
          # FastAPI가 살아있는지 확인
          # 문제가 있으면 Kubernetes가 컨테이너를 재시작함
          livenessProbe:
            tcpSocket:
              port: 8001
            initialDelaySeconds: 15
            periodSeconds: 10
            timeoutSeconds: 2
            failureThreshold: 6

---
# =========================================
# [2] FastAPI Service
# -----------------------------------------
# 역할:
# - Django가 FastAPI에 접근할 수 있는
#   내부 주소(fastapi-service)를 만든다
#
# settings.py / ConfigMap 과 연결되는 핵심 주소:
# FASTAPI_BASE_URL = http://fastapi-service:8001
#
# type: ClusterIP
# - 클러스터 내부에서만 접근 가능
# - 외부 브라우저 접근용이 아니라 내부 통신용 서비스
# =========================================
apiVersion: v1
kind: Service
metadata:
  name: fastapi-service
  namespace: review-k8s
  labels:
    app: fastapi
spec:
  type: ClusterIP
  selector:
    app: fastapi
  ports:
    - name: http
      port: 8001
      targetPort: 8001
```

전체흐름
```
1. Deployment가 FastAPI Pod를 생성한다
   → review-fastapi:local 이미지를 사용해서 FastAPI를 실행한다

2. Deployment가 FastAPI Pod를 계속 유지한다
   → Pod가 죽으면 새 Pod를 다시 생성한다

3. FastAPI가 사용하는 포트(8001)를 연다
   → FastAPI가 8001 포트로 요청을 받을 수 있게 한다

4. 환경 설정을 적용한다
   → TZ=Asia/Seoul 값을 넣어서 로그 시간대를 맞춘다

5. 리소스 사용 범위를 지정한다
   → CPU / 메모리의 최소 사용량(requests)과 최대 사용량(limits)을 설정한다

6. FastAPI 상태를 확인한다
   → readinessProbe: 요청을 받아도 되는 준비 상태인지 확인한다
   → livenessProbe: 살아있는지 확인하고, 문제 있으면 재시작한다

7. Service(fastapi-service)를 생성한다
   → Django가 FastAPI에 접속할 수 있는 내부 주소를 만든다

8. Django가 fastapi-service 이름으로 FastAPI에 접속한다
   → Django는 http://fastapi-service:8001 주소로 FastAPI를 호출한다
```
FastAPI 서버를 실행하고, 상태를 체크하며,  
Django가 `fastapi-service`라는 이름으로 호출할 수 있게 만드는 설정입니다.

`k8s/base/django.yaml`
```yml
# =========================================
# Django 구성 전체 개념
# -----------------------------------------
# 이 파일은 Django를 Kubernetes에서 사용하기 위해
# 아래 2가지 리소스를 정의합니다.
#
# 1. Deployment
#    - Django Pod를 생성한다
#    - Django 컨테이너를 실행한다
#    - Pod가 죽으면 다시 만든다
#    - 포트, 실행 명령, 환경변수도 함께 설정한다
#
# 2. Service
#    - 다른 서비스가 Django에 접속할 수 있는
#      내부 주소(django-service)를 제공한다
#
# 즉, 이 파일은
# "Django를 실행하고 / 유지하고 / 내부에서 접속 가능하게 만드는"
# 역할을 한다.
# =========================================

# =========================================
# [1] Django Deployment
# -----------------------------------------
# 역할:
# - review-django:local 이미지를 사용해 Django Pod를 생성한다
# - Pod가 죽으면 다시 생성한다
# - Django가 사용하는 포트(8000)를 연다
# - gunicorn 명령으로 Django 서버를 실행한다
# - ConfigMap / Secret 값을 환경변수로 주입한다
#
# [프로젝트 설정과 반드시 맞아야 하는 부분]
# - DB_HOST          → postgres-service
# - REDIS_URL        → redis://redis-service:6379/0
# - FASTAPI_BASE_URL → http://fastapi-service:8001
# - DJANGO_DEBUG / DJANGO_ALLOWED_HOSTS / DJANGO_SECRET_KEY
#   도 ConfigMap / Secret 값과 일치해야 한다
# =========================================
apiVersion: apps/v1
kind: Deployment
metadata:
  name: django
  namespace: review-k8s
spec:
  replicas: 1
  selector:
    matchLabels:
      app: django
  template:
    metadata:
      labels:
        app: django
    spec:
      containers:
        - name: django
          image: review-django:local
          imagePullPolicy: IfNotPresent

          # Django 컨테이너가 내부에서 사용하는 포트
          ports:
            - containerPort: 8000

          # Django 실행 명령
          # 개발 서버가 아니라 gunicorn으로 실행
          command: ["gunicorn"]
          args:
            - mysite.wsgi:application
            - --bind
            - 0.0.0.0:8000

          # -----------------------------
          # 환경변수 설정
          # -----------------------------
          # ConfigMap / Secret 에 저장한 값을
          # Django 컨테이너 안으로 주입한다
          env:
            # Django 기본 설정
            - name: DJANGO_DEBUG
              valueFrom:
                configMapKeyRef:
                  name: review-config
                  key: DJANGO_DEBUG

            - name: DJANGO_ALLOWED_HOSTS
              valueFrom:
                configMapKeyRef:
                  name: review-config
                  key: DJANGO_ALLOWED_HOSTS

            - name: DJANGO_SECRET_KEY
              valueFrom:
                secretKeyRef:
                  name: review-secret
                  key: DJANGO_SECRET_KEY

            # -----------------------------
            # DB 설정
            # -----------------------------
            # PostgreSQL 접속에 필요한 값
            - name: DB_NAME
              valueFrom:
                configMapKeyRef:
                  name: review-config
                  key: DB_NAME

            - name: DB_HOST
              valueFrom:
                configMapKeyRef:
                  name: review-config
                  key: DB_HOST

            - name: DB_PORT
              valueFrom:
                configMapKeyRef:
                  name: review-config
                  key: DB_PORT

            - name: DB_USER
              valueFrom:
                configMapKeyRef:
                  name: review-config
                  key: DB_USER

            - name: DB_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: review-secret
                  key: DB_PASSWORD

            # -----------------------------
            # Redis 설정
            # -----------------------------
            # Celery / Cache 용 Redis 접속 주소
            - name: REDIS_URL
              valueFrom:
                configMapKeyRef:
                  name: review-config
                  key: REDIS_URL

            # -----------------------------
            # FastAPI 설정
            # -----------------------------
            # Django가 FastAPI를 호출할 때 사용할 주소
            - name: FASTAPI_BASE_URL
              valueFrom:
                configMapKeyRef:
                  name: review-config
                  key: FASTAPI_BASE_URL

            # 타임존 설정
            - name: TZ
              value: Asia/Seoul

---
# =========================================
# [2] Django Service
# -----------------------------------------
# 역할:
# - 다른 서비스가 Django에 접근할 수 있는
#   내부 주소(django-service)를 만든다
#
# 핵심 주소:
# - http://django-service:8000
#
# type: ClusterIP
# - 클러스터 내부에서만 접근 가능
# - 외부 브라우저 접근용이 아니라 내부 통신용 서비스
# =========================================
apiVersion: v1
kind: Service
metadata:
  name: django-service
  namespace: review-k8s
spec:
  selector:
    app: django
  ports:
    - port: 8000
      targetPort: 8000
  type: ClusterIP
```

Django YAML 전체 흐름
```

   → review-django:local 이미지를 사용해서 Django 서버를 실행한다
```

#### STEP 9. Celery 배포
이 파일은 Celery를 Kubernetes에 배포하기 위해  Deployment로 실행/유지하고,  
Django 설정 / DB / Redis / FastAPI 설정을 함께 사용하여 백그라운드 작업을 계속 처리하게 만드는 설정입니다.

`k8s/base/celery.yaml`
```yml
# =========================================
# Celery 구성 전체 개념
# -----------------------------------------
# 이 파일은 Celery 워커를 Kubernetes에서 실행하기 위해
# Deployment 리소스를 정의합니다.
#
# 1. Deployment
#    - Celery Pod를 생성한다
#    - Celery 워커 프로세스를 실행한다
#    - Pod가 죽으면 다시 만든다
#    - Django 설정값 / DB / Redis 등을 함께 사용한다
#
# 특징:
# - Django와 같은 이미지(review-django:local)를 사용한다
# - 웹 서버가 아니라 "백그라운드 작업 처리용 서버"이다
#
# 즉, 이 파일은
# "Celery 작업 처리 서버를 실행하고 / 유지하고 / 큐를 계속 처리하게 만드는"
# 역할을 한다.
# =========================================

# =========================================
# [1] Celery Deployment
# -----------------------------------------
# 역할:
# - review-django:local 이미지를 사용해 Celery Pod를 생성한다
# - celery worker 명령으로 작업 처리 프로세스를 실행한다
# - Pod가 죽으면 다시 생성한다
# - Django 설정 / DB / Redis / FastAPI 설정을 함께 사용한다
#
# [프로젝트 설정과 반드시 맞아야 하는 부분]
# - REDIS_URL        → redis://redis-service:6379/0
# - DB_HOST          → postgres-service
# - FASTAPI_BASE_URL → http://fastapi-service:8001
```

Celery YAML 전체 흐름
```
1. Deployment가 Celery Pod를 생성한다
   → Celery 작업 처리 서버를 실행한다

2. Deployment가 Celery Pod를 계속 유지한다
   → 서버가 꺼지면 자동으로 다시 실행한다

3. celery worker 명령을 실행한다
   → 백그라운드에서 작업을 처리하는 프로그램을 실행한다

4. Django 설정값을 함께 사용한다
   → Django 프로젝트 설정을 그대로 공유해서 사용한다

5. DB 연결 정보를 적용한다
   → PostgreSQL에 접속해서 데이터를 읽고 저장할 수 있게 한다

6. Redis 연결 정보를 적용한다
   → Redis에서 작업 목록을 가져와 처리할 수 있게 한다

7. FastAPI 주소를 적용한다
   → 작업 처리 중 FastAPI를 호출할 수 있게 한다

8. HTTPS 리다이렉트 설정을 적용한다
   → 실습 중 불필요한 리다이렉트를 막는다

9. 타임존을 설정한다
   → 서버 시간 기준을 한국 시간으로 맞춘다

10. 리소스 사용 범위를 지정한다
    → CPU / 메모리를 너무 많이 쓰지 않도록 제한한다
```



| 상황                             | 선택          |                    |

#### STEP 11. Ingress 적용

#### Ingress란 무엇인가?
	Ingress는 외부(브라우저, 사용자)에서 들어오는 요청을  
	쿠버네티스 내부 서비스로 연결해주는 입구(Gateway)입니다.
	
한줄 요약: 외부 요청을 내부 서비스로 라우팅하는 관문

구조로 이해하기
```
브라우저 → (Ingress) → Service → Pod
```
- 사용자는 Ingress로 접속합니다
- Ingress가 어떤 서비스로 보낼지 결정합니다
- Service를 통해 Pod로 연결됩니다

전체흐름
```
브라우저 (review.local)  
    ↓  
Ingress (라우팅 규칙)  
    ↓  
Service (django-service / fastapi-service)  
    ↓  
Pod (Django / FastAPI)
```
이 구조는 Kubernetes 핵심 구조입니다

---
#### Ingress가 필요한 이유

(1) Service만으로는 외부 접속이 불편합니다
	쿠버네티스에서 기본적으로 Pod는 외부에서 직접 접근이 불가능합니다.

Service를 통해 접근해야 하는데:
- ClusterIP → 내부 전용 (외부 접근 불가)
- NodePort → 포트가 이상함 (예: 30001)
- LoadBalancer → 클라우드 비용 발생

(2) Ingress는 웹사이트처럼 만들어 줍니다

Ingress를 사용하면:
```
http://내도메인.com  
http://내IP
```
이런 형태로 접속이 가능합니다

(3) 여러 서비스를 하나의 입구로 관리 가능

예를 들어:
```
/        → Django  
/ai      → FastAPI  
/admin   → Admin
```
Ingress 하나로 라우팅 가능

(4) 실제 운영 환경과 동일한 구조
	실무에서는 반드시 이런 구조를 사용합니다:
```
Nginx / Ingress  
      ↓  
Backend 서비스들
```
Ingress = Kubernetes에서의 Nginx 역할

Ingress의 핵심 역할
- 라우팅 (Routing)
- 도메인 기반 라우팅
- HTTPS 처리 (SSL 종료)
- 중앙 진입점
```
[브라우저]
    ↓
Ingress
    ↓
django-service (8000)
fastapi-service (8001)
```
이 역할을 하는 것이 바로 Ingress입니다

수정하는 이유는
static 요청 오면 Django 안 보내고 Nginx가 직접 파일 찾는다는 뜻입니다.

❗ 그런데 문제
Nginx 컨테이너에는 `/app/staticfiles` 없습니다.
그래서
```
Nginx → 파일 없음 → 404
```
Django까지 요청이 안갑니다.

우리가 원하는 구조
```
브라우저 → Nginx → Django → WhiteNoise → static 반환
```

그러나 현재 구조는
```
브라우저 → Nginx → ❌ 여기서 끝 (404)
```
이래서 css가 적용되지 않는 겁니다.

#### STEP 14. HPA 실습
이 단계에서는 쿠버네티스의 자동 확장 기능인 HPA(Horizontal Pod Autoscaler)를 간단히 체험합니다.  
HPA는 트래픽(부하)에 따라 Pod 개수를 자동으로 늘리거나 줄이는 기능입니다.

HPA를 위한 사전 준비 (resources 설정)
HPA는 보통 CPU 사용률 기준으로 동작하기 때문에 Deployment에 `resources` 설정이 반드시 필요합니다.

`k8s/base/django.yaml` 파일에서 컨테이너 부분에 아래를 추가합니다.
```yml
spec:
  containers:
    - name: django
      image: review-django:v7
      imagePullPolicy: IfNotPresent
	
	  # 추가된 코드
      resources:
        requests:
          cpu: "100m"
          memory: "256Mi"
        limits:
          cpu: "500m"
          memory: "512Mi"
```
설정 의미:
- requests → 최소 보장 자원
- limits → 최대 사용 가능 자원
- HPA는 이 값을 기준으로 CPU 사용률을 계산합니다

수정 후 다시 적용:
```bash
kubectl apply -f k8s/base/django.yaml
```

HPA 리소스 생성
`k8s/base/hpa.yaml` 파일을 생성합니다.
```yml
apiVersion: autoscaling/v2  
kind: HorizontalPodAutoscaler  
metadata:  
  name: django-hpa
  namespace: review-k8s  
spec:  
  scaleTargetRef:  
    apiVersion: apps/v1  
    kind: Deployment  
    name: django  
  minReplicas: 1  
  maxReplicas: 3  
  metrics:  
    - type: Resource  
      resource:  
        name: cpu  
        target:  
          type: Utilization  
          averageUtilization: 50
```
설정 의미 (핵심만)
- 최소 Pod 수: 1
- 최대 Pod 수: 3
- CPU 50% 넘으면 → Pod 증가

🔷 적용:
```bash
kubectl apply -f k8s/base/hpa.yaml
```

🔷 확인:
```bash
kubectl get hpa -n review-k8s
```
정상 결과
```
NAME         REFERENCE           TARGETS              MINPODS   MAXPODS   REPLICAS   AGE
django-hpa   Deployment/django   cpu: <unknown>/10%   1         3         0          13s
```

두번째 터미널: Pod 감시 상황
```bash
kubectl get pods -n review-k8s -w
```
CPU가 기준 넘으면 Django Pod가 새로 생김.

결과
```
NAME         REFERENCE           TARGETS       MINPODS   MAXPODS   REPLICAS   AGE
django-hpa   Deployment/django   cpu: 1%/10%   1         3         1          4m12s
django-hpa   Deployment/django   cpu: 70%/10%   1         3         1          6m
django-hpa   Deployment/django   cpu: 70%/10%   1         3         3          6m15s
django-hpa   Deployment/django   cpu: 119%/10%   1         3         3          7m
django-hpa   Deployment/django   cpu: 41%/10%    1         3         3          8m
django-hpa   Deployment/django   cpu: 40%/10%    1         3         3          10m
```
이 의미는:
- 현재 CPU 사용률이 목표치 10%를 넘음
- HPA가 “지금 Pod 수로는 부족하다”고 판단
- 그래서 Replica 수를 1개에서 **3개까지 확장**
- 즉 자동 확장 성공

아주 쉽게 말하면
```
평소엔 서버 1개면 충분  
근데 부하가 많이 들어옴  
→ CPU 사용률 급증  
→ Kubernetes가 자동으로 서버 수를 늘림
```

핵심 포인트 정리

`cpu: 70%/10%`
- 현재 CPU 사용률 70%
- 목표는 10%
- 목표보다 훨씬 높음  
    → 확장 필요

`REPLICAS 3`
- HPA가 Django Pod를 3개까지 늘림
- `maxReplicas: 3` 이라서 거기까지 확장된 것

`cpu: 119%/10%`
- 순간적으로 CPU가 더 많이 튐
- 그래도 이미 max 3개라 더는 못 늘어남

```
업데이트됨: 3  
Total: 3  
가용: 3
```
의미:
- Django Pod가 3개 떠 있음
- 전부 정상 동작 중

호리즌탈 파드 오토스케일러
```
이름: django-hpa  
최소: 1  
최대: 3  
참조: Deployment/django
```
해석:
- 최소 Pod → 1개
- 최대 Pod → 3개
- 지금은 최대까지 확장된 상태

이벤트: 이게 제일 중요함
![[Pasted image 20260411225749.png]]
이 문장 의미
```
처음: Pod 1개  
↓  
부하 발생  
↓  
HPA 판단  
↓  
Pod 3개로 증가
```
즉, 자동 확장 성공 로그

전체 흐름 정리
```
초기 상태
→ Django Pod 1개

부하 테스트 시작
→ CPU 사용량 증가

HPA 감지
→ 목표 CPU 초과

자동 확장
→ Pod 3개로 증가

현재 상태
→ 안정적으로 3개 유지
```
