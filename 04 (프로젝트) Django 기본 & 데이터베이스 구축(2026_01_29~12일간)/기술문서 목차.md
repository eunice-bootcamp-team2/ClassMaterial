# 2. 사용자 시나리오 및 화면 흐름 (행동 중심 전용)

✅ 사용자 역할 정의  
✅ 대표 사용자 여정 (한 줄)  
✅ 화면 흐름 다이어그램
✅ 흐름 해설(행동 기준 요약)
✅ 설계 의도(행동 흐름 중심 정의 원칙)
❌ CRUD / 검증 / 제약 설명 금지


예시 작성:
###### 사용자 역할 정의
```
- User: 개인 계좌 및 거래 데이터 관리
- Admin: 운영 및 데이터 관리 목적
```

대표 사용자 여정
```
회원가입 → 로그인 → 계좌 생성 → 거래 등록 → 영수증 첨부 → 대시보드 확인
```

화면 흐름 다이어그램
```
[비인증]
   │
   ▼
로그인 / 회원가입
   │
   ▼
[인증]
   │
   ▼
계좌 목록
   │
   ▼
거래 목록
   │
   ▼
대시보드
```
###### 흐름 해설 (핵심만 간결하게)
- 비인증 사용자는 로그인 또는 회원가입 화면만 접근 가능
- 인증이 완료되면 계좌 관리 화면이 서비스의 진입점 역할 수행
- 계좌는 거래 데이터의 상위 개념으로 동작
- 거래 생성 과정에서 선택적으로 영수증 파일을 첨부할 수 있음
- 누적된 거래 데이터는 대시보드에서 요약 형태로 제공됨

###### 설계 의도
화면 구성은 UI 중심이 아니라 사용자 행동 흐름 기준으로 정의

# 3. 시스템 아키텍처

 ✅ 전체 구성도(서버렌더링 중심 MVT)  
 ✅ 세부 클래스기반 요청 (질문)

전체 구성도 (서버 렌더링 중심 MVT)
```
[Browser]
   │  GET /transactions/
   ▼
[urls.py]
   │
   ▼
[TransactionListView]
   │
   ▼
[Transaction.objects.filter()]
   │
   ▼
[PostgreSQL DB]
   │
   ▼
[transactions/list.html]
   │
   ▼
[Browser]
```
이 그림 하나로 설명 가능한 것
- URL의 역할
- View가 중심이라는 것
- Model은 데이터 처리
- Template은 화면
- 서버에서 HTML을 만들어서 돌려준다는 점

클래스 기반 요청 흐름 그림 예시
```
[POST /transactions/create/]
        │
        ▼
urls.py
(path: "transactions/create/")
        │
        ▼
transactions/views.py
TransactionCreateView (CreateView)
        │
        ▼
TransactionCreateView.form_valid()
        │
        ▼
transactions/models.py
Transaction.save()
        │
        ▼
HttpResponseRedirect
        │
        ▼
[GET /transactions/]
TransactionListView
```

# 4. 데이터베이스 설계

✅ ERD 첨부(Lucidchart 이미지)
✅ ERD 관계 요약(1:N, 1:1)
✅ 제약조건 설계(무결성 규칙) 
✅ 인덱스 설계(조회 패턴 기반)
✅ Data Dictionary

---
###### ERD
- Lucidchart로 ERD 작성 (PK/FK, Cardinality 표기)
- 첨부: ERD 이미지 1장
    
---
###### ERD 관계 요약
- User 1:N Account
- User 1:N Transaction
- Account 1:N Transaction
- Category 1:N Transaction
- Transaction 1:1 Attachment (MVP)
    
예시:
```
ERD 관계 요약

- User 1 : N Account  
- User 1 : N Transaction  
- Account 1 : N Transaction 
- Category 1 : N Transaction  
- Transaction 1 : 1 Attachment (MVP 기준: 거래당 영수증 1개)
```
---
###### 제약조건 / 인덱스 설계

- 제약조건 = 이상한 데이터 못 들어오게 막는 규칙(제약조건 파트는 models.py 기준으로 작성)
예:
- 금액이 0이면 안 됨
- 거래 유형은 IN/OUT만 가능
- 날짜는 비어 있으면 안 됨
    
👉 데이터 품질 보호 규칙
코드 예외처리랑 다른 개념입니다.
> 저장되기 전에 DB가 직접 검사

---
- 인덱스 = 조회 빠르게 만드는 장치(인덱스 설계는 “실제 조회 패턴”, 특히 쿼리스트링 / 필터 조건을 보고 작성)
예:
- 사용자별 거래 목록 자주 조회
- 날짜 기준 정렬 자주 사용
    
👉 검색/필터 속도 개선 목적

---
작성예시:

✅ 제약조건 (쉽게 쓰는 버전)
본 프로젝트의 주요 데이터 무결성 규칙:
- 거래 금액은 0보다 큰 값만 허용
- 거래 유형은 IN / OUT 값으로 제한
- 거래 일시는 필수 값
- 첨부 파일은 거래 단위로 연결 (거래당 1개)

제약조건
- amount 값은 0 초과 조건
- tx_type 값은 IN / OUT 제한
- occurred_at 필수 값
- Attachment는 Transaction과 1:1 관계(MVP)

✅ 인덱스 설계 (초간단 버전)
주요 조회 성능 고려 사항:
- 사용자 기준 거래 목록 조회 빈도 높음
- 거래 일시 기준 정렬/필터 사용
- 계좌 기준 거래 필터 사용
    
적용 전략:
- user_id 기준 조회 최적화 고려
- occurred_at 컬럼 기반 정렬 성능 고려

인덱스 고려
- 사용자별 거래 조회 빈도 고려
- 날짜 기준 정렬 / 필터 사용
- 계좌 기준 조회 패턴 고려

---
###### Data Dictionary (핵심 테이블)
- Transaction 테이블: 주요 컬럼/타입/설명 표로 정리
    
| 컬럼          | 타입       | Null | 설명      | 예시         |
| ----------- | -------- | ---: | ------- | ---------- |
| id          | bigint   |    N | PK      | 101        |
| user_id     | FK       |    N | 소유자     | 3          |
| account_id  | FK       |    N | 계좌      | 7          |
| category_id | FK       |    Y | 카테고리    | 2          |
| tx_type     | varchar  |    N | IN/OUT  | OUT        |
| amount      | decimal  |    N | 금액(0초과) | 12000      |
| occurred_at | datetime |    N | 거래일시    | 2026-02-01 |

###### 컬럼(Column)  컬럼 = 필드명 = 속성
|컬럼|의미|
|---|---|
|id|거래의 고유 번호|
|user_id|이 거래의 주인|
|account_id|어떤 계좌에서 발생한 거래인지|
|category_id|거래 분류(식비, 교통 등)|
|tx_type|입금인지 출금인지|
|amount|금액|
|occurred_at|거래가 일어난 날짜/시간|

###### 타입(Type) 타입 = 그 칸에 어떤 종류의 값이 들어가는지
|타입|쉽게 말하면|
|---|---|
|bigint|큰 숫자|
|FK|다른 테이블의 id를 가리키는 값|
|varchar|짧은 글자|
|decimal|소수점이 있는 숫자(금액용)|
|datetime|날짜 + 시간|

###### Null = “비어 있어도 되는가?”
|Null|의미|
|--:|---|
|N|**비어 있으면 안 됨 (필수)**|
|Y|**비어 있어도 됨 (선택)**|

설명(Description) 이 컬럼이 어떤 역할을 하는지 사람에게 알려주는 말
- `user_id`: 이 거래의 소유자
- `tx_type`: 입금인지 출금인지
- `amount`: 거래 금액 (0보다 커야 함)

###### 예시 = 실제로 저장될 수 있는 값의 예 : 이 컬럼에는 이런 값이 들어간다”를 보여주는 샘플
| 컬럼          | 예시         | 뜻           |
| ----------- | ---------- | ----------- |
| id          | 101        | 101번 거래     |
| user_id     | 3          | 3번 사용자      |
| account_id  | 7          | 7번 계좌       |
| category_id | 2          | 2번 카테고리     |
| tx_type     | OUT        | 출금          |
| amount      | 12000      | 12,000원     |
| occurred_at | 2026-02-01 | 2026년 2월 1일 |

PK는 거래하나마다 자동으로 붙는 번호
FK는 다른 테이블을 가르키는 번호 `user_id = 3` 이 거래는 User 테이블 3번 사용자 것이다.
tx_type = OUT : IN은 입금 OUT은 출금

거래 CRUD
###### 기능 요약 표
| 기능    | 설명            |
| ----- | ------------- |
| 거래 생성 | 입금/출금 거래 등록   |
| 거래 조회 | 사용자별 거래 목록/상세 |
| 거래 수정 | 금액, 날짜, 메모 수정 |
| 거래 삭제 | 거래 기록 삭제      |

###### 입력 검증 정책
| 항목    | 검증 내용               |
| ----- | ------------------- |
| 계좌 선택 | 로그인한 사용자의 계좌만 선택 가능 |
| 금액    | 0보다 큰 값만 허용         |
| 거래 유형 | IN / OUT 중 하나       |
| 거래일   | 필수 입력               |
설명 예시

> 거래 생성 및 수정 시, 선택 가능한 계좌는 로그인한 사용자의 계좌로 제한하였다.  
> 이를 통해 타 사용자 계좌에 대한 거래 생성이 불가능하도록 설계하였다.

---
거래 필터 / 검색 / 정렬 (request.GET 기반)

###### 지원 기능 표
| 구분      | 내용             |
| ------- | -------------- |
| 기간 필터   | 시작일 ~ 종료일      |
| 계좌 필터   | 특정 계좌 선택       |
| 카테고리 필터 | 거래 분류          |
| 거래 유형   | 입금 / 출금        |

| 정렬      | 최신순 기본         |
설명 예시

> 거래 목록은 JavaScript 없이, `request.GET` 쿼리스트링을 이용하여 서버에서 필터링 및 정렬을 수행한다.

예시 URL
```
/transactions/?account=1&category=2&q=카페
```

> 영수증 파일은 로컬 MEDIA 디렉토리에 저장되며,

대시보드 요약

###### 제공 정보 표
| 구분    | 내용             |
| ----- | -------------- |
| 월별 요약 | 총수입 / 총지출 / 순합 |
| 카테고리별 | 지출 합계          |
| 월 변경  | 쿼리스트링 기반       |
| 시각화   | 표 + CSS 막대바    |

설명 예시

> 대시보드는 선택한 월을 기준으로 거래 데이터를 집계하여  
> 월별 수입/지출 현황과 카테고리별 소비 내역을 보여준다.  
> JavaScript 차트 라이브러리를 사용하지 않고,  
> 표와 CSS 스타일을 활용하여 간단한 시각화를 구현하였다.

예시 URL
```
/dashboard/?month=2026-02
```

###### 객체 접근 404 전략
- 상세/수정/삭제 요청 시 객체 소유자 검증 수행
- 본인 소유 데이터만 접근 허용
- 타 사용자 소유 데이터 요청은 404 응답으로 처리(리소스 존재 은닉)
적용화면 인증샷
방법:
포트 하나(`127.0.0.1:8000`)만 사용합니다.
1. 일반 창(Chrome) → 사용자 A로 로그인
2. 시크릿 창(Incognito) 또는 다른 브라우저(Edge) → 사용자 B로 로그인
3. 사용자 A로 글/거래 1개 생성 → URL 확인 (예: `/transactions/5/`)
4. 시크릿 창(사용자 B)에서 그 URL로 접속
5. 404 Not Found(또는 페이지를 찾을 수 없습니다) 화면 캡처

이게뭐냐면:
✔ 남의 데이터 URL을 직접 찍어도 “없음(404)”으로 처리해서, 데이터 존재 여부 자체를 숨기는 전략

예를 들어:
- 내 거래: `/transactions/5/` → 정상 표시
- 남의 거래: `/transactions/5/` → **404 Not Found**
    
왜 403(권한 없음)이 아니라 404를 쓰냐면,
- 403이면 “거기 뭔가 있긴 한데 너만 못 봄”이 됨
- 404면 “그런 건 없는 것처럼” 보임 → **정보 노출 최소화**
    
이걸 보통 리소스 존재 은닉(resource hiding) 성격으로 씁니다.

어디에 적용?
목록 조회(QuerySet 필터)는 **리스트에서 남의 데이터가 안 보이게** 하는 거고,  
객체 접근 404 전략은 **상세/수정/삭제에서 URL 직접 접근을 막는 것**입니다.

적용 대상:
- Detail(상세)
- Update(수정)
- Delete(삭제)

# 10. Git 브랜치/PR 전략

✅ 브랜치 규칙`(main/feature/*)`
✅ 브랜치 네이밍 규칙
✅ 커밋 메시지 규칙  
✅ 작업 흐름(이슈→브랜치→커밋→PR→리뷰→머지)
✅ 커밋 메시지 규칙(Conventional type)
✅ 충돌 처리 원칙(rebase/merge 기준)

###### 브랜치 규칙
| 브랜치         | 용도              |
| ----------- | --------------- |
| `main`      | 항상 배포 가능한 상태 유지 |
| `feature/*` | 기능 개발 및 수정      |

네이밍 규칙 예시
- `feature/account-crud`
- `feature/transaction-filter`
- `feature/dashboard-summary`

> main 브랜치에는 직접 커밋하지 않고, 반드시 PR을 통해 병합한다.

Type 정의 (팀 협업 표준)

|Type|의미|사용 시점|
|---|---|---|
|**feat**|기능 추가|새로운 API, 화면, 기능|
|**fix**|버그 수정|오류 해결, 잘못된 동작 수정|
|**refactor**|리팩토링|동작 변화 없이 구조 개선|
|**docs**|문서 변경|README, 주석, 가이드|
|**test**|테스트 코드|테스트 추가/수정|
|**chore**|잡작업 / 설정|패키지, 환경설정, 정리|
|**style**|코드 스타일|공백, 포맷팅 (로직 변화 없음)|
|**ci**|CI/CD 설정|GitHub Actions 등|
|**build**|빌드 관련|requirements, 버전 변경|

---
작업 흐름 (Workflow)

작업 단계 요약
```
이슈 확인
   ↓
feature 브랜치 생성
   ↓
작업 & 커밋
   ↓
PR 생성
   ↓
리뷰(셀프 또는 팀)
   ↓main 브랜치 병합
```

간단 설명
> 모든 작업은 `feature/*` 브랜치에서 수행하고,
> 작업 완료 후 Pull Request를 통해 `main` 브랜치로 병합한다.

---
충돌 해결 원칙
###### 기본 원칙
| 상황      | 기준               |
| ------- | ---------------- |
| 기능 개발 중 | rebase 사용        |
| PR 병합 시 | merge 사용         |
| 충돌 발생   | feature 브랜치에서 해결 |

설명 예시
> 충돌은 feature 브랜치에서 먼저 해결한 뒤 PR을 업데이트한다.
> main 브랜치에서는 충돌을 직접 수정하지 않는다.

---
커밋 메시지 규칙
###### 커밋 타입 규칙
| 타입       | 의미           |
| -------- | ------------ |
| feat     | 새로운 기능 추가    |
| fix      | 버그 수정        |
| docs     | 문서 수정        |
| refactor | 코드 리팩토링      |
| test     | 테스트 코드 추가/수정 |
| chore    | 설정/빌드 관련 작업  |

커밋 메시지 예시
- `feat: 거래 필터 기능 추가`
- `fix: 타 사용자 거래 접근 오류 수정`
- `docs: 기술문서 6장 보안 파트 정리`
- `test: 거래 CRUD 테스트 추가`

> 커밋 메시지는 “무엇을 했는지 한눈에 알 수 있도록” 작성한다.

이슈별 해결 과정 (원인 → 시도 → 해결)

① 권한 누락으로 타 사용자 데이터 노출 가능성

|단계|내용|
|---|---|
|문제 상황|거래 상세 URL을 직접 입력하면 타 사용자 데이터 접근 가능|
|원인 분석|QuerySet 필터링만 적용하고, 객체 단위 접근 검증 누락|
|시도|목록 조회에 user 필터 추가|
|해결|상세/수정/삭제 시 객체 소유자 확인 후 404 처리|
|결과|타 사용자 데이터 접근 완전 차단|

설명
> 조회 단계뿐 아니라 객체 접근 단계에서도 권한 검증이 필요함을 인지했다.

---

② 파일 업로드 검증/경로 문제

|단계|내용|
|---|---|
|문제 상황|업로드 파일이 저장되지 않거나 경로 오류 발생|
|원인 분석|MEDIA_ROOT / MEDIA_URL 설정 누락|
|시도|파일 저장 경로 하드코딩|
|해결|Django 기본 MEDIA 설정 사용 + 확장자/용량 검증|
|결과|정상 업로드 및 조회 가능|

설명
> 파일 업로드는 경로 설정과 검증을 함께 고려해야 안정적으로 동작한다.

---
③ PostgreSQL 연결/마이그레이션 문제

|단계|내용|
|---|---|
|문제 상황|migrate 실행 시 DB 연결 오류|
|원인 분석|환경변수 누락 및 권한 설정 오류|
|시도|[settings.py](http://settings.py) 직접 수정|
|해결|환경변수(.env) 기반 설정 분리|
|결과|로컬/배포 환경 동일 구조 유지|

설명
> DB 설정은 코드가 아니라 환경변수로 관리해야 재사용과 배포가 쉬워진다.
