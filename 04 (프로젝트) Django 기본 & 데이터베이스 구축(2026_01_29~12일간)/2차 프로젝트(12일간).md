# `0.` 프로젝트 개요 

프로젝트명: AccountBook
	계좌 기반 거래 내역 관리 시스템

> 로그인한 사용자가 여러 개의 계좌를 등록하고,  
> 각 계좌에 대한 입출금 거래 내역을 기록·조회·수정·삭제하며, 
> 영수증 파일 업로드와 대시보드에서 월별/카테고리별 요약을 확인할 수 있는  
> Django + PostgreSQL 기반 웹 서비스

목표(MVP)
- **계정 기반 서비스**: 로그인한 사용자만 이용 가능
- **개인 데이터 분리**: 모든 데이터는 사용자별로 분리되어 **본인만 조회/수정/삭제**
- **계좌/거래 관리**: 계좌 CRUD + 거래 CRUD + 거래 필터/검색
- **영수증 첨부**: 거래에 영수증 파일(이미지/PDF) 업로드/조회/삭제
- **대시보드 요약**: 월별 총수입/총지출/순합 + 카테고리별 집계(그래프 느낌)
- **DB는 PostgreSQL**: 개발 DB를 PostgreSQL로 사용(로컬 설치 기반)
- **관리자 페이지**: `list_display`, `list_filter`, `search_fields` 정도의 기본 커스터마이징
	- `/admin/` 경로 사용
	- `createsuperuser`로 생성한 관리자 계정만 접근 가능
	- 일반 사용자 계정은 관리자 페이지 접근 불가

# `1.` 핵심 도메인(엔티티) 정의 (필드/관계 포함)

#### `1)` User (Django 기본 User)
- `django.contrib.auth` 기본 User 사용
- 정책
    - `Account`, `Transaction`, `Attachment`는 모두 User 소유
    - 접근 제어 원칙: 본인 데이터만(QuerySet 필터 + 객체 접근 차단)
        
#### `2)` Account (계좌)
- 역할: 거래가 발생하는 계좌 단위(통장/카드/현금지갑)
	
- 필드(예시)
	- `user` (FK → User)
	- `name` : 계좌 별칭(예: 생활비 통장)
	- `bank_name` : 은행/기관명
	- `account_number` : 계좌번호(저장)
	    - **출력은 항상 마스킹**(예: 110-****-1234)
	- `balance` : 잔액(선택)
	- `is_active` : 비활성(선택, 삭제 대신 숨김 가능)
	- `created_at`, `updated_at`
- 규칙
- 계좌는 반드시 `user`에 속함
- 계좌번호는 화면/로그에서 **마스킹**만 노출
    
#### `3)` Category (카테고리)
- 역할: 거래 분류(식비/교통/월세/쇼핑/급여 등)

- 필드(예시)
	- `name` : 카테고리명
	- `type` : 수입/지출/공통(선택)
	- (선택) `user` : 개인 커스텀 카테고리 허용 시
	
- MVP 운영 방식
	- 빠른 구현을 위해 기본 카테고리 seed(초기 데이터)로 시작 (CRUD는 선택)
	
#### `4)` Transaction (거래)
- 역할: 입금/출금 기록의 핵심 데이터
	
- 필드(예시)
	- `user` (FK → User) : 권한/필터용(명시 권장)
	- `account` (FK → Account)
	- `category` (FK → Category, null 가능)
	- `tx_type` : `IN`(입금) / `OUT`(출금)
	- `amount` : 금액(Decimal, 0 초과)
	- `occurred_at` : 거래일(날짜/시간)
	- `merchant` : 가맹점/거래처(선택)
	- `memo` : 메모(선택)
	- `created_at`, `updated_at`
- 규칙
	- 거래 생성/수정 시 선택 가능한 계좌는 본인 계좌만
	- 거래 필터/검색은 서버에서 `request.GET`로 처리(JS 불필요)
    
#### `5)` Attachment (영수증 첨부)
- 역할: 거래에 영수증 이미지/PDF 파일을 첨부
	
- 필드(예시)
	- `user` (FK → User)
	- `transaction` (OneToOne 또는 FK)
	- `file` (FileField/ImageField)
	- `uploaded_at`
	- (선택) `original_name`, `size`, `content_type`
	
- MVP 결정(권장)
	- “거래당 1개 영수증”이면 `OneToOne`
	- “여러 장 가능”이면 FK로 여러 개 허용  
	    (12일 MVP면 1개(OneToOne) 추천)

#### `6)` 관리자 페이지(Admin)
- 관리자 페이지 목적
	- 개발·테스트 단계에서 전체 데이터 상태를 빠르게 확인
	- 운영 관점에서 사용자/계좌/거래/카테고리/첨부파일 관리
	- 일반 사용자는 접근 불가, 관리자(superuser)만 접근 가능
- User (Django 기본 User)
	- 사용자 계정 목록 조회
	- 활성/비활성 여부 확인
	- Django 기본 Admin 기능 사용 (커스터마이징 최소)
- Account (계좌)
	- 전체 계좌 목록 조회
	- 계좌 소유 사용자(User) 확인
	- 계좌명, 은행명, 활성 여부 수정
	- 계좌번호는 관리자 페이지에서도 마스킹된 값만 표시
- Category (카테고리)
	- 기본 카테고리 관리(추가/수정/삭제)
	- 카테고리명 및 타입(수입/지출/공통) 관리
	- MVP 기준: **카테고리 관리는 관리자 페이지에서만 수행**
- Transaction (거래 내역)
	- 전체 거래 내역 조회
	- 사용자 / 계좌 / 카테고리 / 입출금 타입 기준 필터링
	- 거래 금액, 거래일, 메모 확인
	- 테스트 및 오류 데이터 수정/삭제 목적
- Attachment (영수증 파일)
	- 거래별 첨부파일 목록 확인
	- 업로드 파일 존재 여부 점검
	- 잘못 업로드된 파일 삭제

# `2.` 필수 요구사항 (12일 내 구현 기준, 최종 확정)

`1)` 프로젝트 요구사항 분석
- 유저 시나리오/화면 목록/권한 규칙(본인 데이터만) 문서화
- MVP 범위와 제외 범위 명시(**JS 0 / Docker 0 / CI만**)
    
`2)` 데이터베이스 설계(ERD)
- 5개 도메인(User, Account, Transaction, Category, Attachment) ERD 작성
	- User: FK로만 참조
		- 시스템에 로그인하는 사용자 계정 정보
		- 모든 데이터(Account/Transaction/Attachment)의 소유자 기준
	- Account (계좌): 한 사용자는 여러 계좌를 가질 수 있음 1 : N
		- 사용자가 보유한 계좌(통장/카드/현금 등) 정보
		- 거래(Transaction)가 발생하는 기준 단위
	- Transaction (거래 내역): 
	  User 1 : N Transaction, Account 1 : N Transaction, Category 1 : N Transaction
		- 계좌에서 발생한 입금/출금 기록
		- 금액, 날짜, 카테고리 등 핵심 비즈니스 데이터
	- Category (카테고리): Category **1 : N** Transaction
		- 거래(Transaction)를 분류하기 위한 분류 기준 테이블
		- 예: 식비, 교통, 월세, 급여 등
	- Attachment (영수증/첨부파일): Transaction 1 : 1 Attachment
		- 거래(Transaction)에 첨부되는 영수증 이미지/PDF 파일 정보
		- 파일 자체는 디스크에 저장, DB에는 메타데이터만 저장
- 관계/제약조건(유저 소유, FK 연결, 거래일 인덱스 등) 정의
- Django 모델로 구현 + 마이그레이션 반영
ERD 관계도 요약
```
User
 ├─ Account        (1:N)
 │    └─ Transaction (1:N)
 │          ├─ Category   (N:1)
 │          └─ Attachment (1:1 or 1:N)
```

`8)` 대시보드 UI (간단 합계/그래프 느낌, JS 없이)
- 월별 요약: 총수입/총지출/순합
- 카테고리별 합계 Top N
- 그래프 느낌: 표 + CSS 막대바(JS 없이 가능)
- 월별 대시보드 요약을 바꾸기 위해서 월 변경은 `?month=YYYY-MM` 같은 쿼리로 처리 (쿼리스트링(Query String))
views.py에서 처리 (예시)
```python
# dashboard/views.py
from datetime import date
from django.utils.timezone import now

def dashboard_view(request):
    month_param = request.GET.get("month")  # '2026-01' 또는 None

    if month_param:
        year, month = map(int, month_param.split("-"))
    else:
        today = now().date()
        year, month = today.year, today.month

    # 이 year, month로 DB 집계
```
- 사용자가 `?month=2026-01`로 들어오면  
    → 2026년 1월 데이터 집계
    
- 파라미터 없으면  
    → 현재 달 기준으로 집계

#### 전체 간단 흐름 쿼리스트링(Query String)
urls.py(라우터) -> views.py -> template
	`1. urls.py(라우터)`
		- `/dashboard/` 같은 경로를 어떤 view로 보낼지 연결
		- `name="dashboard"` 같은 이름도 여기서 붙임
    
	2. views.py
		- request.GET.get("month"),request.GET.get("category")같은 쿼리스트링을 읽어서
		- 그에 맞는 필터링 + 집계(SUM, GROUP BY)를 해서 템플릿에 값들을 넘김(context)
    
	3. template
		- <form method="get">로 월/카테고리를 선택하면  
	    → URL이 /dashboard/?month=2026-01&category=3 이렇게 바뀜
		- 뷰가 계산해준 “월별/카테고리별 합계”를 숫자/표/CSS 막대바로 보여줌(=시각화)
