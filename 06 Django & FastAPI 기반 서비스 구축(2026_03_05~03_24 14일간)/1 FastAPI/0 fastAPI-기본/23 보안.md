### JWT란?
	JWT (JSON Web Token) 는 이런 인증 토큰을 JSON 형식으로 만들어 암호화한 것입니다. 
	구조는 3가지 조각으로 나뉩니다:
```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.
eyJzdWIiOiJ1c2VyMSIsImV4cCI6MTYzNzk5Njk4Mn0.
7kAgCj...암호화된서명...
```

`Header` : 토큰의 종류, 사용한 암호화 알고리즘
`Payload` : 사용자 정보 (ex: id, 이름, 권한 등)
`Signature`	: 암호화된 서명 (위조 방지용)

###### JWT vs 일반 토큰 (Session Token 등) 비교
| 항목     | 세션 기반             | JWT              |
| ------ | ----------------- | ---------------- |
| 저장 위치  | 서버 (DB / Redis 등) | 클라이언트            |
| 서버 상태  | Stateful          | Stateless        |
| 구조     | 단순 sessionid      | JSON + 서명        |
| 인증 방식  | 서버 조회             | 서명 검증            |
| 위변조 방지 | 랜덤 sessionid      | Signature        |
| 확장성    | 낮음 (동기화 필요)       | 높음               |
| 로그아웃   | 즉시 가능             | 어려움 (토큰 만료까지 유지) |
| 보안 위험  | CSRF              | 토큰 탈취            |
세션 vs JWT 차이의 본질
```
세션 = 서버가 기억  
JWT = 토큰이 모든 정보를 들고 다님
```

보안 측면에서 JWT는 왜 유리할까?
1. 위조 방지:  
    JWT는 서명이 포함되어 있어, 누가 내용을 바꾸면 검증에 실패합니다.
    
2. 서버가 기억 안 해도 됨:  
    사용자가 보내는 토큰만 있으면, 다시 로그인 없이 확인 가능.  
    서버는 "이 토큰이 위조된 게 아닌지만" 확인하면 됨.
    
3. 토큰 안에 정보 포함 가능:  
    예: `{"username": "eunice", "role": "admin"}`  
    → 권한, 유저 정보도 포함 가능

JWT(JSON Web Token)는 서명이 포함된 JSON 기반 인증 토큰으로, 서버가 사용자를 식별하고 권한을 확인할 수 있게 해줍니다.  서명으로 인해 위조는 어렵지만, 토큰이 탈취되면 누구나 사용할 수 있기 때문에 관리가 중요합니다.  또한 서버에 세션 상태를 저장하지 않는 Stateless 구조라 
확장성이 뛰어난 인증 방식입니다.

그래서 실무에서는
- HTTPS
- 짧은 만료시간
- Refresh token
- Blacklist 등을 사용합니다.

###### Django나 Google API, Amazon Cloud에서 내려받는 **보안키**(비밀 키, API 키 등)와는 다른 역할:
| 항목            | JWT                            | 보안 키(API Key / Secret Key)           |
| ------------- | ------------------------------ | ------------------------------------ |
| 정의            | 사용자 정보를 담고 있는 토큰 <br>(디지털 신분증) | 서버끼리 통신 시, 인증을 위한 비밀키                |
| 형태            | `aaaaa.bbbbb.ccccc` 같은 문자열     | `sk_test_xxxxx` / `AIzaSy...` 같은 문자열 |
| 누가 만듬         | 서버가 사용자 로그인 후 발급               | 서비스 제공자(Google, AWS 등)가 발급           |
| 용도            | 로그인된 유저의 상태를 확인                | 외부 API 인증(예: Stripe, Google Maps 등)  |
| 보관 위치       . | 클라이언트(브라우저/앱)에 저장              | 서버(환경변수 등)에만 저장                      |
| 예시            | FastAPI에서 로그인 후 JWT 발급         | `.env`에 `SECRET_KEY=xxxxx` 등 저장      |

JWT 관련 설정 (`auth.py`)
- 로그인 정보 확인 (`authenticate_user`)
- 비밀번호 암호화 (`get_password_hash`)
- JWT 토큰 생성 (`create_access_token`)
- JWT 토큰 검증 (`get_current_user`)
```python
# JWT 관련 에러 및 토큰 인코딩/디코딩 함수 제공
from jose import JWTError, jwt

# 토큰 만료 시간을 위한 datetime 도구
from datetime import datetime, timedelta

# 비밀번호 암호화/검증 기능을 위한 라이브러리
from passlib.context import CryptContext

# FastAPI에서 예외처리 및 의존성 주입 관련 도구
from fastapi import HTTPException, Depends, status

# OAuth2 인증을 위한 의존성 (토큰 방식 인증을 구현할 때 사용)
from fastapi.security import OAuth2PasswordBearer

# 시간을 다룰 때 쓰는 모듈 중 일부를 가져오는 코드
from datetime import datetime, timezone

# ----------------------
# 1. 기본 설정
# ----------------------

# 토큰 암호화 비밀 키 (실제 서비스에서는 .env 환경변수로 관리해야 안전)
SECRET_KEY = "mysecretkey" # 발급된 보안키를 여기에 저장

# 사용할 암호화 알고리즘 (HS256: 대칭키 방식)
ALGORITHM = "HS256"

# 토큰 유효 시간: 30분
ACCESS_TOKEN_EXPIRE_MINUTES = 30


# ----------------------
# 2. 비밀번호 해싱 및 검증 설정
# ----------------------

# bcrypt 해시 알고리즘을 사용할 비밀번호 암호화 컨텍스트 생성
pwd_context = CryptContext(schemes=["bcrypt"], deprecated="auto")


# ----------------------
# 3. OAuth2PasswordBearer 설정
# ----------------------

# 클라이언트가 토큰을 헤더로 보낼 때, 그 토큰을 추출할 수 있도록 설정
# tokenUrl="token"은 /token 엔드포인트에서 토큰을 발급한다는 의미
oauth2_scheme = OAuth2PasswordBearer(tokenUrl="token")


# ----------------------
# 4. 비밀번호 관련 함수
# ----------------------

# 사용자가 입력한 비밀번호와 DB에 저장된 해시값을 비교
def verify_password(plain_password, hashed_password):
    return pwd_context.verify(plain_password, hashed_password)

# 사용자의 비밀번호를 bcrypt 방식으로 해시 처리하여 저장
def get_password_hash(password):
    return pwd_context.hash(password)


# ----------------------
# 5. 유저 인증 관련 로직 (임시 유저 DB 사용)
# ----------------------

# 임시 사용자 DB (실제 앱에서는 DB 모델로 교체해야 함)
fake_user_db = {
    "testuser": {
        "username": "testuser",
        "hashed_password": get_password_hash("test123")  
        # 평문 비밀번호를 해시해서 저장
    }
}

# 사용자 인증 함수: 입력한 아이디/비번이 fake_user_db와 일치하는지 확인
def authenticate_user(username: str, password: str):
    user = fake_user_db.get(username)  # 사용자 정보 가져오기
    if not user:
        return False  # 사용자 없음
    if not verify_password(password, user["hashed_password"]):
        return False  # 비밀번호 불일치
    return user  # 인증 성공 시 사용자 정보 반환


# ----------------------
# 6. JWT 토큰 생성 함수
# ----------------------

# JWT 토큰 생성: 사용자 정보(data)를 받아 유효시간과 함께 암호화된 토큰을 생성
def create_access_token(data: dict, expires_delta: timedelta = None):
    to_encode = data.copy()  # 원본 딕셔너리를 복사해서 수정
    expire = datetime.now(timezone.utc) + (expires_delta or timedelta(minutes=15))  # 만료 시간 계산
    to_encode.update({"exp": expire})  # 토큰에 만료 시간 추가
    return jwt.encode(to_encode, SECRET_KEY, algorithm=ALGORITHM)  # JWT 토큰 생성 및 리턴


# ----------------------
# 7. 토큰을 통해 현재 사용자 정보 가져오기 (API 보호 시 사용)
# ----------------------

# 토큰이 유효한지 확인하고, 사용자 정보를 추출하여 리턴
def get_current_user(token: str = Depends(oauth2_scheme)):
    try:
        # 토큰 디코딩 및 검증 (유효하지 않거나 변조된 토큰은 예외 발생)
        payload = jwt.decode(token, SECRET_KEY, algorithms=[ALGORITHM])
        
        # 토큰에서 username(sub)을 꺼냄
        username: str = payload.get("sub")

        # username이 없으면 유효하지 않은 토큰으로 간주
        if username is None:
            raise HTTPException(status_code=401, detail="Invalid token")
        
        # 성공적으로 사용자명 추출하면, 딕셔너리 형태로 리턴
        return {"username": username}
    
    # 토큰 디코딩/검증 중 에러가 발생하면 인증 실패 예외 처리
    except JWTError:
        raise HTTPException(status_code=401, detail="Invalid token")

```

FastAPI 앱 구성 (`main.py`)
```python
# FastAPI 주요 모듈 불러오기
from fastapi import FastAPI, Depends, HTTPException, status

# OAuth2 기반 로그인 폼 처리를 위한 클래스
from fastapi.security import OAuth2PasswordRequestForm

# 인증 관련 함수들 (auth.py에서 직접 만든 함수 import)
from auth import authenticate_user, create_access_token, get_current_user

# 토큰 만료 시간 설정을 위한 모듈
from datetime import timedelta

# FastAPI 앱 인스턴스 생성
app = FastAPI()


# ----------------------------
# 로그인 엔드포인트
# ----------------------------
@app.post("/token")
def login(form_data: OAuth2PasswordRequestForm = Depends()):
    """
    사용자로부터 username/password를 받아 JWT access_token을 발급
    Swagger UI에서는 자동으로 grant_type 등도 포함된 POST요청이 이뤄짐.
    """

    # 사용자 인증 수행 (ID, PW 일치 확인)
    user = authenticate_user(form_data.username, form_data.password)

# 인증 실패 시 예외 발생 (401 Unauthorized 아님. 일부러 400으로 처리)
    if not user:
        raise HTTPException(
            status_code=400,
            detail="Incorrect username or password"
        )

    # 인증 성공 시, access_token(JWT)을 생성 (만료시간: 30분)
    access_token = create_access_token(
        data={"sub": user["username"]},  
        # "sub"는 subject(토큰 소유자)의 약자
        
        expires_delta=timedelta(minutes=30)
    )

    # 토큰 응답 반환 (token_type은 "bearer"로 고정)
    return {
        "access_token": access_token,
        "token_type": "bearer"
    }


# ----------------------------
# 인증이 필요한 보호된 API
# ----------------------------
@app.get("/protected")
def read_protected(current_user: dict = Depends(get_current_user)):
    """
    JWT 토큰을 가지고 있어야 접근 가능한 보호된 API입니다.
    현재 로그인한 사용자 정보(current_user)를 토큰에서 가져와 인증을 확인합니다.
    """

    # 인증된 사용자를 위한 응답 메시지 반환
    return {
        "msg": f"Hello {current_user['username']}, you're authenticated!"
    }
```

```python
# users/api_views.py

from rest_framework.views import APIView
from rest_framework.response import Response
from rest_framework import status
from django.contrib.auth import authenticate
from rest_framework.permissions import IsAuthenticated
from .serializers import UserLoginSerializer

from rest_framework_simplejwt.tokens import RefreshToken

# 로그인 API
class LoginView(APIView):
    def post(self, request):
        serializer = UserLoginSerializer(data=request.data)
        serializer.is_valid(raise_exception=True)
        user = authenticate(
            username=serializer.validated_data["username"],
            password=serializer.validated_data["password"]
        )

        if not user:
            return Response({"detail": "Invalid credentials"}, status=status.HTTP_400_BAD_REQUEST)

        refresh = RefreshToken.for_user(user)
        return Response({
            "access_token": str(refresh.access_token),
            "refresh_token": str(refresh),
            "token_type": "bearer"
        })


# 보호된 API
class ProtectedView(APIView):
    permission_classes = [IsAuthenticated]

    def get(self, request):
        return Response({
            "msg": f"Hello {request.user.username}, you're authenticated!"
        })
```

### 웹 인증/보안 필수 개념 정리 (실무 기준)

#### 1️⃣ Session Authentication

##### 개념: 
로그인하면 서버가 세션을 생성하고 브라우저 쿠키에 sessionid 저장하는 방식
```
Browser  
   ↓ 로그인  
Server (세션 생성)  
   ↓  
Set-Cookie: sessionid=abc123
```

이후 요청
```
GET /todos/  
Cookie: sessionid=abc123
```
서버는 sessionid로 로그인 사용자 확인

장점
```
- 구현 간단
- Django 기본 방식
- 서버가 인증을 관리
```
    
단점
```
- 서버가 세션 저장해야 함
- 모바일 앱에 부적합
- CSRF 공격 대상
```

#### 4️⃣ CSRF (Cross Site Request Forgery)

##### 개념:
CSRF는 사용자가 로그인된 상태를 이용해서 사용자가 모르게 서버에 요청을 보내는 공격입니다.

예
```
사용자는 로그인 상태  
↓  
악성 사이트 방문  
↓  
악성 사이트가 서버에 요청 전송  
↓  
서버는 로그인된 사용자의 요청이라고 착각
```

예
```
사용자가 은행 사이트 로그인 상태  
↓  
악성 사이트 방문  
↓  
POST /transfer (돈 송금 요청)
```
이 경우 사용자는 요청을 보낸 적이 없지만 서버는 정상 요청으로 처리할 수 있습니다.

##### 해결 방법: CSRF token
CSRF 공격을 막기 위해 CSRF Token을 사용

폼 요청
```
csrfmiddlewaretoken=abc123
```

요청 흐름
```
사용자 요청  
↓  
CSRF token 포함  
↓  
서버가 token 검증  
↓  
정상 요청 처리
```
만약 토큰이 없으면
```
403 Forbidden
```
응답을 반환한다.


---

Django는 CSRF 보호 기능이 기본적으로 활성화되어 있습니다. 템플릿에서 POST 요청을 보낼 때 반드시 토큰을 포함해야 합니다.

템플릿
```html
<form method="POST">  
{% csrf_token %}  
</form>
```

#### 5️⃣ CORS

##### 개념:
CORS는 브라우저에서 다른 도메인(origin)으로 요청을 보내는 것을 제한하는 보안 정책입니다.

예를 들어 다음과 같은 상황이 있습니다.
```
frontend.com → 프론트엔드 서버  
api.com → 백엔드 API 서버
```
프론트엔드가 `frontend.com`에서 실행되고 있는데  
API 요청을 `api.com`으로 보내면 브라우저는 이를 다른 출처(origin) 요청으로 판단하여 기본적으로 차단합니다.

이 문제를 해결하기 위해 서버에서 특정 도메인의 요청을 허용하도록 설정하는 것이 CORS 설정입니다.

##### FstAPI
```python
from fastapi.middleware.cors import CORSMiddleware  
  
app.add_middleware(  
    CORSMiddleware,  
    allow_origins=["*"],  
    allow_credentials=True,  
)
```

##### Django
```bash
uv pip install django-cors-headers
```

```python
CORS_ALLOW_ALL_ORIGINS = True
```

### 이미지 업로드와 CSRF 처리 방식

##### 상황:
웹 서비스에서 이미지 업로드 요청을 보낼 때 보통 다음과 같은 데이터 형식을 사용합니다.

보통
```
multipart/form-data
```
이 방식은 파일(이미지)과 텍스트 데이터를 함께 서버로 전송하기 위한 HTTP 요청 형식입니다.

경우 1️⃣ Session 인증 기반
Django 템플릿 기반 웹사이트에서 Session Authentication을 사용하는 경우에는  
이미지 업로드 요청에도 CSRF Token이 반드시 포함되어야 합니다.

요청 예
```html
<form method="POST" enctype="multipart/form-data">  
{% csrf_token %}  
<input type="file" name="image">  
</form>
```

요청 흐름
```
사용자 로그인  
↓  
브라우저에 sessionid 쿠키 저장  
↓  
이미지 업로드 요청  
↓  
CSRF Token 포함  
↓  
서버가 Session + CSRF 검증
```

즉,
```
Session Authentication  
+  
CSRF Token
```
이 두 가지를 함께 사용하여 보안을 유지합니다.

경우 2️⃣ JWT 인증 기반
React, Vue, 모바일 앱, API 기반 서비스에서는 JWT 인증을 사용하는 경우가 많습니다.
이 경우 요청은 다음과 같이 Authorization Header에 토큰을 포함하여 전송합니다.
```
Authorization: Bearer access_token
```

요청 예
```
POST /upload  
Content-Type: multipart/form-data  
Authorization: Bearer token
```
JWT 방식에서는 인증이 쿠키가 아닌 Authorization Header를 통해 이루어지기 때문에  
일반적으로 CSRF Token이 필요하지 않습니다.

이미지 업로드는 multipart/form-data 방식으로 전송하며, 인증 방식이 Session이면 CSRF가 필요하고 JWT 인증이면 Authorization Header로 인증합니다.

### 추가로 알아두면 좋은 보안 개념

Refresh Token
JWT 인증에서는 보안을 위해 토큰의 유효 기간을 짧게 설정하는 경우가 많습니다.

예를 들어
```
Access Token : 15분  
Refresh Token : 7일
```
Access Token은 API 요청에 사용되는 토큰이며 유효 시간이 짧습니다.  
토큰이 만료되면 Refresh Token을 이용하여 새로운 Access Token을 다시 발급받을 수 있습니다.

이 방식은 토큰이 탈취되더라도 장시간 사용되는 것을 방지하기 위한 보안 방법입니다.

---
#### Access Token Rotation
Access Token Rotation은 토큰을 한 번 사용할 때마다 새로운 토큰을 발급하는 방식입니다.

즉,
```
요청  
↓  
새 Access Token 발급  
↓  
기존 토큰 폐기
```
이 방법을 사용하면 토큰이 탈취되었을 때 재사용되는 위험을 줄일 수 있어 보안이 강화됩니다.

---
#### Rate limiting
Rate Limiting은 사용자가 일정 시간 동안 보낼 수 있는 요청 횟수를 제한하는 보안 방법입니다.

예를 들어 로그인 요청을 다음과 같이 제한할 수 있습니다.
```
로그인 5회 제한
```
이렇게 하면 비밀번호를 무작위로 시도하는 공격(브루트포스 공격)을 방지할 수 있습니다.

Django에서는 다음과 같은 라이브러리를 사용합니다.
```
django-ratelimit
```

astAPI에서는 다음 라이브러리를 사용할 수 있습니다.
```
slowapi
```

#### XSS (Cross Site Scripting)
XSS는 웹 페이지에 악성 스크립트를 삽입하여 사용자의 정보를 탈취하는 공격 방식입니다.

예를 들어 다음과 같은 코드가 입력되면 문제가 발생할 수 있습니다.
```js
<script>alert(1)</script> // 이코드는 실제 취약점 테스트 코드임
```
이 스크립트가 실행되면 사용자의 쿠키 정보나 로그인 정보가 탈취될 위험이 있습니다.
이를 방지하기 위해 입력값 검증과 HTML 이스케이프 처리를 해야 합니다.

결론은 쉽게 풀어서:
XSS는 사용자가 입력한 스크립트가 웹페이지에서 실행되게 만드는 공격이고, Django는 템플릿에서 `{{ 변수 }}`로 출력하면 자동으로 escape 처리하여 이를 기본적으로 막아줍니다.

실제상황 연출

`1` XSS 공격
사용자가 댓글 같은곳에 이런 코드를 넣습니다.
```html
<script>alert(1)</script>
```
이 코드가 실행되면 브라우저에서 JavaScript가 실행될 수 있다.

`2` Django 기본방어 방식
장고 탬플릿에서 
```html
{{comment}}
```
사용자가 입력한 값의 필드를 변수로 받아옵니다. 이렇게 하면 장고에서는 자동으로 이스케이프 문자로 변환되어 XXS기본 방어를 해줍니다.
```
&lt;script&gt;alert(1)&lt;/script&gt;
```

#### SQL Injection
SQL Injection은 사용자가 입력한 값을 이용하여 데이터베이스 쿼리를 조작하는 공격 방식입니다.

예를 들어 다음과 같은 입력이 있을 수 있습니다.
```
' OR 1=1
```
이 값이 SQL 쿼리에 그대로 사용되면 모든 데이터가 조회되거나 인증이 우회될 수 있습니다.

하지만 Django나 FastAPI에서 ORM(Object Relational Mapping)을 사용하면 대부분의 SQL Injection 공격을 자동으로 방어할 수 있습니다.

실제 상황
로그인 코드가 이렇게 되어 있다고 가장합니다.
```sql
SELECT * FROM users  
WHERE username = 'admin'  
AND password = '1234'
```
그런데 사용자가 비밀번호 입력창에 이런 값을 넣습니다
```
' OR 1=1
```
그러면 실제 쿼리는 이렇게 바뀝니다.
```sql
SELECT * FROM users  
WHERE username = 'admin'  
AND password = '' OR 1=1
```
여기서
```
1=1
```
은 항상 참(true)이기 때문에 로그인 우회가 가능해 질수 있습니다.

그래서 이것이 공격입니다.
공격 목적은 
```
로그인 우회  
데이터 조회  
데이터 삭제  
데이터 수정
```
같은 일을 하기 위해 사용한다.

그런데 Django에서는 보통 이렇게 쿼리를 작성합니다.
```python
User.objects.filter(username=username)
```
이걸 우리는 ORM이라고 부릅니다.

ORM은 내부적으로 SQL Injection 방어를 자동으로 해줍니다.
그래서 Django에서는 ORM 사용 = 대부분 SQL Injection 방어가 됩니다.

```
XSS  
→ 브라우저 공격

SQL Injection  
→ 데이터베이스 공격
```
둘 다 대표적인 웹 보안 공격 방식입니다.

실무에서는 다음과 같은 보안 요소들을 함께 고려하여 서비스를 설계합니다.
```
JWT 인증  
+  
Refresh Token  
+  
Rate Limiting  
+  
XSS 방어  
+  
SQL Injection 방어
```
이러한 보안 요소들을 함께 적용하면 웹 서비스의 인증과 데이터 보호를 보다 안전하게 유지할 수 있습니다.

5️⃣ Microservice 인증 (Gateway + JWT)
대규모 서비스에서는 하나의 서버가 모든 기능을 처리하는 대신,  
기능별로 여러 개의 서비스로 나누어 운영하는 마이크로서비스(Microservice) 구조를 많이 사용합니다.

이 구조에서는 여러 서비스에 대한 접근을 관리하기 위해  
API Gateway와 JWT 인증을 함께 사용하는 방식이 일반적입니다.

전체 구조는 다음과 같은 흐름으로 구성됩니다.
```
Client  
↓  
API Gateway  
↓  
Auth Service  
↓  
각 Microservice
```
즉, 사용자의 요청은 먼저 API Gateway를 통해 들어오고, 그 이후에 인증을 확인한 뒤 각 서비스로 전달됩니다.


예를 들어 프론트엔드와 여러 백엔드 서비스가 있는 경우 다음과 같은 구조가 될 수 있습니다.
React에서 요청이 들어오면 API Gateway를 통해 여러 백엔드 서버로 요청이 전달됩니다.
```
React (Frontend)  
↓  
API Gateway  
↓  
여러 Backend 서비스  
├ Django API  
├ FastAPI (AI 서비스)  
├ Node.js 서비스  
└ Notification 서비스
```
이렇게 요청이 흐릅니다.
```
사용자 → React → Gateway → 실제 서버들
```

API Gateway가 뭐냐?
API Gateway는 클라이언트 요청을 받아서 적절한 백엔드 서비스로 전달해주는 중간 서버입니다.
쉽게 말하면 요청을 분배하는 관문 서버입니다.

API Gateway는 하나의 서버 프로그램입니다. 대표적인 것들은
```
Nginx  
Kong  
AWS API Gateway  
Traefik  
Spring Gateway
```
예를 들어 Nginx로도 Gateway를 만들 수 있습니다.

포트폴리오 프로젝트에서도 Nginx를 중간 서버로 두고, 들어온 요청을 Django나 FastAPI 같은 백엔드 서버로 나눠 보내는 구조를 만들 수 있습니다.

예를 들어 구조가 이렇다고 하면
```
사용자
 ↓
Nginx
 ├ /api/      → Django
 ├ /ai/       → FastAPI
 └ /static/   → 정적파일
```
사용자는 그냥 한 주소로 접속하지만,  
Nginx가 중간에서 요청을 보고 어느 서버로 보낼지 결정합니다.

- Django: 회원가입, 로그인, 게시글, 리뷰
- FastAPI: AI 추천, 감정분석
- Nginx: 중간에서 요청 분배
```
        React / Django Template
                 │
                 ▼
              Nginx
           ┌─────┴─────┐
           ▼           ▼
        Django      FastAPI
```

Nginx가 하는 일 
- 요청 분배
- 정적 파일 제공
- HTTPS 연결 처리
- 여러 서버를 하나의 입구로 묶기

EC2에서 자세히 다루겠습니다.

이처럼 서비스가 기능별로 분리되어 있기 때문에  각 서비스는 독립적으로 개발되고 운영될 수 있습니다.

마이크로서비스 환경에서는 보통 JWT 인증 방식을 사용합니다.
로그인 과정은 다음과 같습니다.
```
사용자 로그인  
↓  
Auth Server에서 사용자 인증  
↓  
JWT 토큰 발급
```
이후 사용자는 API 요청을 보낼 때마다 JWT 토큰을 함께 전송합니다.
