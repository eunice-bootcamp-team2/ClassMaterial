`1.` 초기 인프라 및 핵심 API 구축 (0번 ~ 4번)
- 서비스 서버(Django)와 AI 서버(FastAPI)를 분리하는 멀티 서버 아키텍처를 가장 먼저 정의
- 순서: 프로젝트 생성 후 기본적인 CRUD와 ERD 기반의 모델링을 선행하여 데이터 구조를 확립

`2.` 사용자 기능 및 프런트엔드 연동 (5번 ~ 10번)
- 페이지네이션, 이미지 업로드, JWT 인증 등 기본적인 웹 서비스의 필수 기능을 먼저 완성
- 순서: 특히 9번 템플릿 정리 단계에서 JS를 분리하여 이후 단계(AI 분석 결과 출력 등)에서 프런트엔드 작업을 용이하였습니다. 10번에서 좋아요/댓글 등의 인터랙션 기능을 구현한 것도 인증(7-8번) 이후에 배치되었습니다.

`3.` 데이터베이스 전환 및 데이터 수집 (11번 ~ 12번)
- 본격적인 데이터 수집(크롤링) 전에 SQLite에서 PostgreSQL로 전환전략적을 구축했습니다.
- 크롤링을 통해 대량의 데이터가 유입될 경우 SQLite는 성능 및 동시성 문제가 발생할 수 있는데, 이를 미리 방지했습니다.

`4.` AI 서버 구축 및 동기식 연동 (13번 ~ 17번)
- FastAPI 서버를 독립적으로 구축하고, 이를 Django와 연결하여 동기 방식으로 먼저 동작을 확인한 후(15번) UI를 개선(16번)하고 결과를 DB에 저장(17번)하는 흐름은 현업에서 사용하는 방식입니다.

`5.` 시스템 최적화 및 실시간성 강화 (18번 ~ 21번)
- AI 분석처럼 오래 걸리는 작업을 처리하기 위해 Celery/Redis 비동기 작업을 도입하였습니다.
- 비동기 작업 처리로 인해 발생하는 언제 작업이 끝날지 모르는 문제를 20번 WebSocket 실시간 알림으로 해결하였습니다.
- 마지막에 전체 시스템의 로깅(Logging)을 삽입하여 운영 환경에서의 추적 가능성을 확보한 것도 실무적으로 매우 중요한 단계입니다

### 그러나 보완점이 존재합니다.

`1.` AI 검색 및 추천 성능 고도화 (Vector DB 도입)
현재 상태: 현재는 Django에서 특정 리뷰를 가져와 FastAPI를 통해 실시간으로 유사도를 계산하고 결과를 반환합니다
보안점: 리뷰 데이터가 수만 건 이상으로 늘어날 경우, 매번 전체 데이터를 비교하는 방식은 속도가 느려질 수 있습니다
제안: PostgreSQL의 확장 기능인 pgvector를 사용하거나 별도의 Vector DB(Chroma, Pinecone 등)를 도입하여, 임베딩된 벡터값을 인덱싱하고 빠르게 검색하는 구조를 고려합니다.


`2.` 크롤링 안정성 및 윤리적 측면 강화
현재 상태: Selenium과 스케줄러를 활용해 다나와, 화해 등의 사이트에서 데이터를 수집하고 있습니다
보안점: 상업적 사이트는 봇 차단 정책이 강력하므로, 단순히 Selenium을 실행하는 것만으로는 IP 차단을 당하기 쉽습니다
제안: User-Agent 회전(Rotation), Proxy 사용, 그리고 대상 사이트의 robots.txt 준수 여부를 체크하는 로직을 추가해야 합니다
또한, 사이트 구조 변경 시 알림을 받을 수 있는 모니터링 체계를 구축하는 것이 좋습니다


`3.` API 보안 및 인가(Authorization) 세분화
현재 상태: JWT를 사용하여 인증을 처리하며, 특정 API에 대해 권한 설정을 적용했습니다
보안점: Django와 FastAPI 간의 통신이 Docker 네트워크 내부에서 이루어지더라도, 외부 노출 가능성을 차단해야 합니다
제안: CORS(Cross-Origin Resource Sharing) 설정을 엄격하게 관리하고, API 호출 횟수를 제한하는 Rate Limiting을 도입하여 무분별한 AI 추론 요청으로 인한 리소스 낭비를 방지합니다.


`4.` 데이터 무결성 및 삭제 정책 (Soft Delete)
현재 상태: 모델 설계 시 외래키 관계를 CASCADE로 설정하여 부모 데이터 삭제 시 자식 데이터가 모두 삭제되도록 했습니다
보안점: 실무에서는 사용자의 실수나 관리적 이유로 데이터를 복구해야 할 상황이 자주 발생합니다
제안: 물리적으로 데이터를 지우는 대신 is_deleted 필드를 사용하는 Soft Delete(논리 삭제) 방식을 도입하는 것이 데이터 보존 및 분석 측면에서 더 유리할 수 있습니다


`5.` 에러 처리 및 비동기 작업 재시도 로직 강화
현재 상태: Celery 작업 중 에러 발생 시 로그를 남기고 WebSocket으로 실패를 알립니다
보안점: FastAPI 서버 일시 장애 등으로 분석이 실패했을 때, 단순히 실패로 끝내는 것은 사용자 경험에 좋지 않습니다
제안: Celery의 재시도(Retry) 정책을 설정하여, 일시적인 네트워크 오류 시 일정 시간 후 다시 시도하도록 구성합니다.


`6.` 환경 설정 및 배포 자동화 (CI/CD)
현재 상태: Docker와 .env를 통해 환경을 관리하고 있습니다
보안점: 소스 코드에 민감한 정보가 포함되지 않도록 더욱 주의해야 하며, 수동으로 컨테이너를 빌드하는 방식은 배포 실수를 유발할 수 있습니다
제안: GitHub Actions 등을 활용하여 코드가 푸시되면 자동으로 테스트를 수행하고 Docker 이미지를 빌드하여 배포하는 CI/CD 파이프라인 구축을 고려합니다.
