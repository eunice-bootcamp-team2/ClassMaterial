`1.` 모니터링의 핵심 개념: "왜 하는가?"

모니터링은 단순히 숫자를 보는 것이 아니라, 서비스의 건강 상태를 실시간으로 진단하여 문제가 생기기 전에 대응하거나 발생한 문제를 빠르게 해결하기 위한 활동입니다.

- **가용성:** 서버가 현재 살아있는가?
- **성능:** 응답 속도가 충분히 빠른가? (평균뿐만 아니라 상위 95%의 속도인 p95 지표가 중요함).
- **안정성:** 에러가 얼마나 발생하는가?
- **자원 상태:** CPU, 메모리 등 서버의 물리적 한계에 도달했는가?.

`2.` 프로메테우스와 그라파나의 역할 분담

① 프로메테우스 (데이터 수집 및 저장소)
- **역할:** 시간에 따라 변하는 데이터를 저장하는 **시계열 데이터베이스(TSDB)**이자 수집기입니다.
- **작동 방식 (Pull):** 프로메테우스가 직접 각 서버의 `/metrics` 주소에 접속해 데이터를 긁어가는(Scraping) 방식입니다.
- **데이터 단위 (Metric):** 무엇을 측정했는지를 나타내는 이름입니다.
    - **Counter:** 0부터 계속 **증가만 하는 값** (예: 총 요청 수). `rate()` 함수를 써서 초당 요청 수(RPS)를 구합니다.
    - **Gauge:** **올라가기도 내려가기도 하는 현재값** (예: 메모리 사용량, CPU 온도).
    - **Histogram:** 값의 **분포**를 측정. 응답 속도 중 95%가 몇 초 이내인지(p95) 계산할 때 필수입니다.
- **라벨 (Label):** 데이터에 붙이는 **태그**입니다. 예를 들어 "로그인 API"인지 "결제 API"인지 구분하는 식별자 역할을 합니다.

② 그라파나 (시각화 및 알림)
- **역할:** 프로메테우스에 저장된 딱딱한 숫자 데이터를 **예쁜 그래프와 대시보드**로 바꾸어 보여주는 "얼굴" 역할을 합니다.
- **알림:** 설정한 수치(예: 에러율 1% 초과)를 넘으면 디스코드나 슬랙으로 메시지를 보내 담당자를 깨우는 역할을 합니다.

`3.` 무엇을 중점적으로 봐야 하는가? (5대 핵심 지표)

개발자가 대시보드를 구성할 때 반드시 포함해야 할 5축 지표입니다:
1. **가용성 (Availability):** `up` 지표가 1인지 확인합니다. 0이면 서버가 죽은 것입니다.
2. **트래픽 (Traffic/RPS):** 초당 요청 수를 확인하여 서비스 규모와 부하를 파악합니다.
3. **성능 (Latency/p95):** 95%의 사용자가 느끼는 속도를 봅니다. 평균에 속지 말고 **"꼬리 지연(Tail Latency)"**을 잡는 것이 핵심입니다.
4. **오류 (Errors/5xx):** 서버 오류(5xx) 비율을 확인합니다. 보통 **1% 미만 유지**를 목표(SLO)로 합니다.
5. **리소스 (Resources):** CPU와 메모리 여유가 있는지 확인하여 서버 증설 시점을 판단합니다.

`4.` 초보개발자를 위한 단계별 테스트 방법

이론을 배웠다면, 시스템이 정상 작동하는지 확인하기 위해 다음과 같은 테스트를 수행해야 합니다.

1단계: 수집 연결 테스트 (Target Test)
- **방법:** 프로메테우스 UI(`:9090/targets`)에 접속합니다.
- **확인 사항:** 내가 등록한 서비스(FastAPI, Django 등) 상태가 **'UP'**으로 표시되는지 확인합니다. 만약 'DOWN'이라면 네트워크나 포트 설정이 잘못된 것입니다.

2단계: 실시간 트래픽 유입 테스트
- **방법:** `curl` 명령어나 부하 테스트 도구(k6 등)를 사용하여 서비스에 반복적인 요청을 보냅니다.
- **확인 사항:** 그라파나의 RPS 그래프가 **계단식으로 상승**하는지 확인합니다. `rate()` 쿼리가 정상적으로 동작하는지 보는 과정입니다.

3단계: 의도적 오류 발생 테스트 (Error Test)
- **방법:** 에러를 유도하는 엔드포인트(예: `/boom`)를 호출하여 의도적으로 500 에러를 발생시킵니다.
- **확인 사항:** 그라파나의 **5xx 에러율 패널**에서 스파이크(뾰족한 상승)가 발생하는지 확인합니다.

4단계: 성능 병목 테스트 (Latency Test)
- **방법:** 응답이 느린 API를 호출하거나 동시에 많은 요청을 보내 서버를 바쁘게 만듭니다.
- **확인 사항:** **p95 Latency** 그래프가 상승하는지 확인하여, 실제 사용자 지연 상황이 시각화되는지 검증합니다.

5단계: 알림(Alert) 발송 테스트
- **방법:** 알림 조건(예: CPU 사용량 > 10%)을 아주 낮게 설정하여 강제로 알림을 발생시킵니다.
- **확인 사항:** 연결된 **디스코드나 메시징 앱**으로 "🚨 Alert" 메시지가 정상적으로 도착하는지 확인합니다.

--------------------------------------------------------------------------------
정리하자면: 학습자는 살아있나(UP) → 얼마나 들어오나(RPS) → 빠른가(p95) → 에러는 없나(5xx) → 버틸 자원은 있나(CPU/MEM)라는 흐름으로 서비스를 관찰하는 법을 익혀야 합니다
