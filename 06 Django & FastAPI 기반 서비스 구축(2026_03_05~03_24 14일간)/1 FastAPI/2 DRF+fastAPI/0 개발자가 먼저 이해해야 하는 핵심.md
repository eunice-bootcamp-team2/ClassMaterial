프로젝트는 처음부터 완성품을 만드는 게 아니므로  
실무에서도 보통 아래 순서로 생각합니다
```
1. 내가 무엇을 만드는가
2. 사용자에게 어떤 화면/기능이 필요한가
3. 그 기능을 저장할 데이터는 무엇인가
4. 그 데이터를 다룰 API는 무엇인가
5. 화면과 API를 연결하면 무엇이 먼저 보여야 하는가
6. 무거운 기능은 나중에 어떻게 분리할 것인가
7. 마지막에 성능/운영/배포를 어떻게 붙일 것인가
```

`기능 → 데이터 → 연결 → 고도화` 이 순서로 가는 게 가장 안전합니다.

위의 자료의 흐름은 위의 과정을 따르고 있습니다.
- 먼저 Django/FastAPI 서버를 어떻게 나눌지 정하고
- CRUD와 모델 구조를 만들고
- 템플릿/JS를 정리하고 인증과 이미지 업로드를 붙인 뒤
- PostgreSQL, 크롤링, FastAPI, AI 연동으로 확장하고
- Celery/Redis/WebSocket/로깅/Vector DB로 고도화하는 흐름으로 구성했습니다.

### 개발 단계에서 가장 이상적인 단계는 다음과 같습니다.

1단계. “무엇을 만드는지” 한 줄로 먼저 정의하기
예시 문장
```
사용자가 상품을 보고 리뷰를 남기면,  
AI가 리뷰를 분석하고 비슷한 후기를 추천해주는 서비스
```

이 한 줄이 프로젝트의 중심이 됩니다.
Django는 서비스 서버, FastAPI는 AI 서버로 분리해서  
리뷰 분석 + 추천 시스템을 만드는 구조로 정리되어 있습니다.

---
2단계. 사용자 행동부터 적기
모델부터 만들기 이전에
실제로는 사용자가 뭘 하는지부터 적는 게 더 쉽습니다.
```
사용자는 회원가입한다  
사용자는 로그인한다  
사용자는 상품을 본다  
사용자는 리뷰를 작성한다  
사용자는 다른 사람 리뷰를 본다  
사용자는 AI 분석 버튼을 누른다  
사용자는 비슷한 후기를 본다
```
이걸 적으면 필요한 화면과 API가 자연스럽게 따라옵니다.

팁
- DB 테이블 이름부터 고민하지 말고
- 사용자 버튼과 화면 흐름부터 적어봅니다
---
3단계. 그다음 데이터 구조를 만듭니다.
사용자 행동이 정리되면, 그 행동을 저장할 모델이 보입니다.

예를 들면:
- 회원가입 → User
- 상품 조회 → Product
- 리뷰 작성 → Review
- 리뷰 이미지 → ReviewImage
- AI 결과 → ReviewAI 또는 ReviewSimilarityResult
- 좋아요/댓글 → interactions

특히 ReviewImage 분리, ReviewAI 분리, interactions 분리는  
“왜 나누는지” 이해하면 정말 큰 도움이 됩니다.

---
4단계. CRUD부터 먼저 완성한다
실무에서는 거의 항상 이렇게 갑니다.
```
CRUD 먼저  
고급 기능은 나중
```

왜냐하면 CRUD가 돼야:
- 데이터가 들어가고
- 화면이 뜨고
- API가 동작하고
- 나중에 AI도 붙일 수 있기 때문입니다.

팁:
- 저장/조회/수정/삭제가 안 되는데
- AI 붙이려고 하지 말아야 합니다

---
5단계. 프론트와 백엔드를 연결합니다.
모델과 API만 있으면 초보자는 된 것 같은데? 라고 느끼지만  
실제로는 아직 서비스가 아닙니다.

사용자가 직접 보는 건 결국:
- 템플릿
- JS
- 버튼 클릭
- 응답 표시
그래서 템플릿 구조와 static/js 분리는 초보자에게 아주 중요합니다.

팁:
- views.py만 만들고 끝내지 말고
- 실제로 버튼 눌렀을 때 움직이는지 빨리 확인해야 합니다.

---
6단계. 인증은 “기능 보호가 필요할 때” 붙인다

JWT는 초보자에게 어렵게 느껴지지만,  
생각 기준은 단순해.

이 질문만 하면 돼:

이 기능은 로그인한 사용자만 써야 하는가?

- 예 → JWT 영향 있음
- 아니오 → 공개 API

네 자료도 accounts 앱이 중심이지만, 실제 영향은 reviews/interactions까지 간다고 정리하고 있어.

초보자 팁:

- 인증은 “로그인 기능”이 아니라
- **누가 요청했는지 구분하는 기능**이라고 이해해라

---
7단계. 무거운 기능은 나중에 분리합니다.
초보자는 처음부터 “실무형 아키텍처”를 만들고 싶어 하는데,  
처음부터 너무 많이 나누면 더 어려워집니다.

실무에서도 보통은:
동기 방식으로 먼저 성공  
→ 그다음 비동기/분리

이 순서가 많습니다.

우리 자료도 FastAPI를 만들고, Django와 먼저 동기식 연결을 확인한 다음,  
그 후에 DB 저장, Celery/Redis, WebSocket으로 고도화하고 있습니다. 

이 순서가 아주 좋은 순서입니다.

팁:
- 처음부터 “완벽한 구조”보다
- 먼저 한 번 끝까지 돌아가는 구조를 만들어라

---
8단계. DB/크롤링/AI는 “확장 단계”로 넣습니다.
이부분이 가장 초보자에게는 어렵습니다.

이유:
- DB 전환
- 크롤링
- AI 서버
- 비동기 처리
- WebSocket
- 로깅
- Vector DB

이게 한 번에 몰려오면 너무 어렵거든요.

그래서 이해 기준을 이렇게 나누면 좋습니다.

저장 확장
- SQLite → PostgreSQL

데이터 수집 확장
- crawling 앱, 대상 URL, 원본 데이터, 실행 로그

 AI 기능 확장
- FastAPI 모델 로딩, 임베딩/유사도 API

운영 확장
- Celery/Redis/WebSocket/Logging

성능 확장
- pgvector 기반 유사도 검색

팁:
- 이것들은 전부 “후반부 확장 단계”입니다.
- 처음부터 동시에 하지 마세요.

---
### 추천하는 실제 개발 순서

A. 1차 목표: 서비스 뼈대 만들기

여기서는 “작동하는 웹서비스”가 목표입니다.
1. 프로젝트 생성
2. 앱 생성
3. URL 연결
4. 모델 설계
5. CRUD API
6. 템플릿 + JS 연결
7. 회원가입/로그인
8. 이미지 업로드
9. 페이지네이션
10. 인터랙션(좋아요/댓글)

이 단계가 끝나면 AI 없어도 서비스처럼 보이는 상태가 됩니다. 
이게 가장 중요해요.

---
B. 2차 목표: 데이터와 AI 붙이기

여기서는 기능 확장이 목표입니다.
1. PostgreSQL 전환
2. 크롤링 앱 추가
3. FastAPI AI 서버 구축
4. Django ↔ FastAPI 연결
5. 결과를 화면에 출력
6. 결과를 DB에 저장

이 단계가 끝나면 AI가 붙은 서비스가 됩니다.

---
C. 3차 목표: 실무형 구조로 고도화

여기서는 “운영 가능한 구조”가 목표입니다.
1. Celery + Redis
2. WebSocket 실시간 알림
3. Docker 전체 통합
4. Logging
5. Vector DB
6. 운영 최적화 계획

이 단계가 끝나면 실무형 아키텍처에 가까운 프로젝트가 됩니다.

---
### 실수하지 않기 위한 팁

팁 1. 매 단계마다 “이번 단계 목표”를 한 줄로 적기

예:
- 이번 단계 목표: Product/Review CRUD가 동작하게 하기
- 이번 단계 목표: 리뷰 이미지 여러 장 업로드 되게 하기
- 이번 단계 목표: AI 결과를 화면에 띄우기

이걸 안 적으면 코드만 따라치게 됩니다.

---
팁 2. 한 단계에서 한 가지 종류의 문제만 풀기

예:
- 모델 만드는 날엔 모델만
- JWT 붙이는 날엔 인증만
- WebSocket 하는 날엔 실시간 알림만

초보자는 여러 문제를 동시에 풀면 거의 반드시 꼬입니다.

---
팁 3. “먼저 로컬 성공 → 그다음 Docker 통합”

이건 이미 자료에도 흐름이 있어요. 
처음부터 모든 걸 컨테이너로 묶으면 어렵습니다.
하지만 후반부에는 Docker 기준으로 통일하는 게 좋습니다.

---
팁 4. 연결 성공 테스트를 중간중간 꼭 넣기

예:
- API 호출 테스트
- 이미지 업로드 테스트
- JWT 발급 테스트
- FastAPI swagger 테스트
- Celery task 실행 테스트
- WebSocket 수신 테스트

초보자는 “끝까지 만든 후 한 번에 테스트”하려고 하는데,  
실무에서는 오히려 작게 자주 테스트를 합니다.

---
팁 5. AI 품질과 시스템 연결은 분리해서 생각하기
이건 아주 중요합니다.

예를 들어:
- 크롤링 데이터가 이상해도
- FastAPI 연결은 성공할 수 있고
- Celery도 잘 돌 수 있다

즉:
- 시스템이 연결됐는지
- 데이터 품질이 좋은지

이건 별개입니다.

초보자는 “결과가 이상함 = 전체 시스템 실패”로 생각하는데  
실제로는 데이터 문제일 수도 있습니다.

---
### 먼저 이해해야 할 핵심  

이 프로젝트의 개발 순서는 다음 기준으로 나뉩니다.  
1. 서비스의 목적 먼저 정하기  
2. 사용자 기능 먼저 만들기  
3. 그 기능을 저장할 모델 설계하기  
4. CRUD와 화면 연결 먼저 완성하기  
5. 인증과 이미지 업로드 같은 필수 기능 붙이기  
6. DB, 크롤링, AI 서버를 확장 기능으로 추가하기  
7. 마지막에 Celery, Redis, WebSocket, Logging, Vector DB로 고도화하기  
  
즉, 처음부터 AI/비동기/배포를 한 번에 만드는 것이 아니라    
“기본 서비스 → 확장 기능 → 실무형 고도화” 순서로 진행합니다.  
  
### 이 프로젝트를 이해하는 가장 쉬운 방법  
- 1차: 사용자가 직접 쓰는 웹서비스 만들기  
- 2차: AI와 데이터 수집 기능 붙이기  
- 3차: 운영 가능한 구조로 고도화하기  
  
이 순서를 이해하면 각 파일과 단계가 왜 지금 필요한지 훨씬 쉽게 보입니다.
