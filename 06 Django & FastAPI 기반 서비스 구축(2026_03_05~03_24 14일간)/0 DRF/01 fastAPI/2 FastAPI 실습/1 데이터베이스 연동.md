DBeaver에서 직접 테이블 만드는 것도 가능하지만, 보통은 아래와 같이 작업합니다.
- Django가 관리해야 할 테이블(Admin에서 쓰고, 폼/권한도 Django가 맡음)  
    → Django 모델 + 마이그레이션으로 만들고, 필요하면 `myproject_db`에 생성.
- FastAPI 전용/서빙 전용 테이블(API에서만 쓰고, Django는 읽기만)  
    → SQLAlchemy + Alembic으로 만들고, Django에선 `managed=False`로 “읽기 전용 매핑”만 추가. 
FastAPI가 `myproject_db`에 새 테이블을 만든다면:
```bash
pip install alembic
alembic init alembic
```
`alembic/env.py`에:
```python
from src.core.database import Base
target_metadata = Base.metadata
# sqlalchemy.url 은 .env에서 읽거나, env.py에서 엔진 생성 로직 작성
```
SQLAlchemy 모델 정의(`user_like_model.py` 등)
	운영에선 `Base.metadata.create_all()`은 쓰지 말고 Alembic만 사용.
마이그레이션 생성/반영
```bash
alembic revision --autogenerate -m "create user like/follow/token tables"
alembic upgrade head
```
Django에는 같은 테이블을 `managed=False`로 매핑만 추가 (Admin에서 조회용)
절대 섞지 마세요. 같은 테이블을 Django/Alembic 둘 다에서 “관리”하면 망가집니다.

현재 추천맛집 플랫폼의 데이터는 아래와 같이 작업하였습니다.
- Django = 관리자 화면(Admin) + ORM.  
    화면에서 데이터 읽고, 간단히 수정도 가능함
- FastAPI = 실제 API 서버.  
    회원가입·로그인 같은 기능을 처리하고 JWT를 발급함.
- DBeaver = 데이터베이스를 보는 “도구”(뷰어).  
    어떤 DB를 선택하느냐에 따라 그 DB의 테이블과 데이터를 보여줌. 자체 DB가 아님.
    
데이터가 저장되는 곳(중요)
- myproject_db
    - 회원/권한 관련 테이블(auth_ , 일부 django_)
    - 외부에서 받은 테이블(`fdc_*`: 식당, 리뷰 등 크롤링/정제 데이터)
    - 즉 fast api는 여기에서 저장/조회 담당
- restaurant_db
    - 네가 Django에서 직접 만든 앱 테이블(예: `restaurant_*`, restaurants_kakao 등)
- FastAPI는 SQLAlchemy로 같은 테이블을 “맵핑만” 해서 쓰는 구조(테이블 생성/수정 X).
- Django는 라우터로 두 DB를 동시에 읽고, FastAPI는 `myproject_db`만 사용 중

> “회원/권한 + fdc 데이터는 myproject_db”,  
> “Django에서 만든 앱 데이터는 restaurant_db”.
> 지금 상태는 통합 데이터가 아닌 멀티 DB상태입니다.

- FastAPI
    - DB 연결을 myproject_db로 설정.
    - 그래서 회원가입을 하면 myproject_db의 auth_user 등에 저장됨.
    - JWT 발급 시 토큰 보관 테이블(fdc_user_access_tokens)도 myproject_db에 기록됨.
- Django(Admin)
    - 멀티 DB 라우팅 설정을 넣어둠.
        - `fdc_*` 와 `auth_*` 는 myproject_db를 보게 함.
        - Django 테이블(`restaurant_*`)은 계속 restaurant_db를 봄.
    - 그래서 Admin에서도 FastAPI가 저장한 회원과 토큰을 그대로 볼 수 있음.

실제 흐름(회원가입 기준)
1. 사용자가 FastAPI의 스웨거에서 회원가입
2. FastAPI가 myproject_db.auth_user 등에 사용자 행을 저장
3. (필요하면) 토큰도 myproject_db.fdc_user_access_tokens에 저장
4. Django Admin은 라우팅 덕분에 같은 테이블을 읽으므로,  
    방금 가입한 사용자가 그대로 보임

크롤링/정리 데이터(`fdc_*`) 흐름
- 외부 SQL을 받아 myproject_db(또는 임시로 staging에 넣었다가) 정리
- 지금은 myproject_db의 `fdc_*` 를 Django Admin이 직접 읽음 → Admin에서도 조회 가능
- DBeaver에서 myproject_db를 선택하면 같은 내용이 보임

상황 시나리오를 가장하면 
- 팀원 A (데이터 담당) → 웹 크롤링 + 데이터 정제/가공 + DB 테이블 관리
- 팀원 B (Django) → Django Admin 기반 데이터 관리 UI 개발
- 팀원 C (FastAPI) → API 서버 개발
- 문제: 데이터 담당 팀원이 DBeaver로 테이블을 직접 수정 → 기존 테이블 구조와 변경사항 발생 → 양쪽(Django, FastAPI)에서 DB 구조 불일치
ETL(Extract → Transform → Load)은  
데이터를 한쪽에서 추출 → 변환 → 다른 쪽에 적재하는 프로세스입니다.

이 경우에 해당한다는 시나리오로 작업
- 웹크롤링을 통해 판다스가공+dbever에 테이블을 직접 생성하여 데이터를 수집하여 채우고 그에 맞는 테이블을 dbever에서 가공함
- Django에서는 관리자를 위한 페이지가 완성되어 있음.
- FastAPI에서는 API 서버를 개발함
DB-우선(DB-first) ETL 방식으로 작업합니다.

스테이징 환경이란?
- 목적: 배포 전에 실제 서비스 환경(운영, production)과 최대한 비슷하게 테스트하는 공간
- 운영 서버에 영향을 주지 않고 기능, 성능, 버그 등을 최종 점검
- 보통 DB, 서버 설정, 도메인까지 운영 환경과 거의 동일하게 구성

`myproject_staging` = 운영 전에 테스트하는 스테이징 환경 전용 프로젝트/DB 이름으로 운영과 비슷하지만, 서비스 안정성을 위해 분리된 안전한 공간입니다.

myproject_staging를 만드는 이유
안전한 작업을 위해
- 격리: 외부에서 받은 SQL/덤프를 바로 운영 DB(`restaurant_db`)에 넣지 않고, 따로 풀어서 확인.
- 검증/정제: 스키마·데이터 품질 점검, 중복 제거, 컬럼 타입 수정, FK/인덱스 재구성 테스트.
- 이관 리허설: `INSERT … SELECT`로 옮기기 전에 성능/무결성 테스트.
- 롤백 안전: 문제 생기면 스테이징만 버리면 끝(운영 DB는 손대지 않음).

Django 프로젝트의 `settings.py`에서 데이터베이스 관련 설정만 따로 분리해 놓은 역할의 파일입니다.

src/core/database.py
```python
import os

from dotenv import load_dotenv
from sqlalchemy import create_engine
from sqlalchemy.engine import URL  # URL은 여기서 가져오는 게 안전
from sqlalchemy.orm import declarative_base, sessionmaker

load_dotenv(verbose=True)

env_url = os.getenv("DATABASE_URL")

# 1) DATABASE_URL이 있으면 그 문자열을 그대로 사용
if env_url:
    SQLALCHEMY_DATABASE_URL = env_url
# 2) 없으면 개별 항목으로 안전하게 생성
else:
    SQLALCHEMY_DATABASE_URL = URL.create(
        drivername=os.getenv("DATABASE_DRIVER", "mysql+pymysql"),
        username=os.getenv("DATABASE_USERNAME"),
        password=os.getenv("DATABASE_PASSWORD"),
        host=os.getenv("DATABASE_HOST", "localhost"),
        port=int(os.getenv("DATABASE_PORT", "3306")),  
        database=os.getenv("DATABASE_NAME"),
        query={"charset": "utf8mb4"},  
    )

engine = create_engine(
    SQLALCHEMY_DATABASE_URL,
    pool_pre_ping=True,    
    pool_recycle=3600,     
    future=True,           
)

SessionLocal = sessionmaker(
    bind=engine,
    autocommit=False,
    autoflush=False,
    expire_on_commit=False,
    future=True,
)

Base = declarative_base()
```
