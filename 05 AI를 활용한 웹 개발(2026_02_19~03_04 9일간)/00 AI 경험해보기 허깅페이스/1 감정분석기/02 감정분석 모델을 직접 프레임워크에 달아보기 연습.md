`3)` 모델 로딩 파일 만들기

요청 올 때마다 pipeline 만들면 서버가 느려지고 메모리도 불안정해져요.  
그래서 앱 내부에 한 번만 로딩되는 모듈을 만듭니다. 즉 hf_model.py는 서버 프로세스 안에 있는 공유 객체(메모리 캐시)입니다.

hf_model.py = 메모리 공유 지점으로 
- views.py는 요청을 처리하는 컨트롤러
- hf_model.py는 상태(state)를 가진 자원으로 views가 같은 물건을 계속 꺼내 쓰는 구조를 만드는것

3-1. `sentiment/hf_model.py` (신규생성)
```python
from transformers import pipeline # 허깅페이스에서 만든 파이썬 라이브러리를 쓰는 지점

MODEL_ID = "tabularisai/multilingual-sentiment-analysis"

# 서버 실행 후 이 파일이 처음 import 될 때 1번만 로드됨
_classifier = None # 초기값을 전역변수에 설정함

def get_classifier():
    global _classifier
    if _classifier is None:
        _classifier = pipeline(
            "text-classification",
            model=MODEL_ID,
            # 기본값으로도 되지만, 명시하면 의도가 분명해져요.
            return_all_scores=False,
        )
    return _classifier
```

`hf_model.py`의 정체
	Django 서버가 켜질 때 Hugging Face 모델을 한 번만 메모리에 로딩해 두기 위한 파일

pipeline이 하는 역할
```python
pipeline(
    "text-classification",
    model=MODEL_ID,
    return_all_scores=False,
)
```
이 한 줄이 실제로 하는 일:
1. 모델 다운로드 (없으면)
2. 토크나이저 다운로드
3. 모델 구조 로드
4. 전처리 / 후처리 로직 연결
5. 바로 호출 가능한 객체 생성

그래서 결과적으로:
```python
_classifier = pipeline(...)
```
이건 모델 객체 생성 + 추론 함수 세팅 완료 와 거의 같은 의미입니다.

```python
return_all_scores=False
```
여러 감정 점수를 전부 반환하지 않고 가장 높은 label 하나만 반환한다는 의미로

False 일 때:
```python
{'label': 'POSITIVE', 'score': 0.98}
```

True 일 때:
```python
[
  {'label': 'POSITIVE', 'score': 0.98},
  {'label': 'NEGATIVE', 'score': 0.02}
]
```
즉, False와 True는 반환 옵션입니다.

❌ 나쁜 예 (절대 하지 말 것)
```python
# views.py
def predict_view(request):
    classifier = pipeline("text-classification", model=MODEL_ID)
    result = classifier(text)
```

👉 이러면:
- 요청 올 때마다 모델 다시 로딩
- 서버 느려짐
- 메모리 폭발
- 실무에서 바로 탈락

✅ 좋은 예 (지금 구조)
```python
# hf_model.py
_classifier = None

def get_classifier():
    if _classifier is None:
        _classifier = pipeline(...)
    return _classifier
```

👉 의미:
- 서버 시작 후 딱 한 번만 로딩
- 이후 모든 요청이 같은 모델 인스턴스 사용
- 실무에서 쓰는 패턴 그대로

🔁 Django에서 이 파일은 언제 실행되나?
```
Django 서버 시작
  ↓
views.py에서 hf_model import
  ↓
hf_model.py가 최초 1회 실행
  ↓
pipeline 생성
```

그리고 나서:
- 사용자가 요청 100번 보내도
- 모델은 1번만 로딩
    
📌 이건 Django뿐 아니라:
- FastAPI
- Flask
- Celery  전부 동일한 패턴입니다.

###### Django 서버를 사무실로 비유하면
| 구성요소         | 비유              |
| ------------ | --------------- |
| Django 서버    | 사무실             |
| views.py     | 직원              |
| 요청(request)  | 전화              |
| 응답(response) | 전화 응답           |
| hf_model.py  | 사무실 안에 있는 AI 비서 |
| pipeline 객체  | AI 비서의 두뇌       |
직원(views.py)은 전화가 올 때마다 같은 AI 비서에게 물어봄
그러면 AI 비서는:
- 매번 새로 고용하지 않고 ❌
- 이미 사무실에 상주한 AI 비서를 관리하는 hf_model_을 통해 호출 ⭕
- 직원들이 번갈아 사용 ⭕

즉, 이것을 대입하여 설명하면:
> 직원(views.py)은 전화가 올 때마다 같은 AI 비서에게 물어봄

- 요청(request) 올 때마다
- view 함수가
- 같은 pipeline 객체를 사용

---
> 그러면 AI 비서는:

- 매번 새로 고용하지 않고 ❌

`4)` 입력 폼 + View 만들기
`sentiment/forms.py` (신규생성)
```python
from django import forms

class SentimentForm(forms.Form): # 이 폼은 어떤 입력을 받는 폼인지 정의
    text = forms.CharField( # 이 폼은 text라는 문자 입력 필드를 가짐
        label="문장 입력",
        widget=forms.Textarea(attrs={"rows": 4, "placeholder": "감정 분석할 문장을 입력하세요"}), # <textarea></textarea>로 랜더링됨
        max_length=500,  # 너무 긴 입력은 제한(안정성)
    )
```

`forms.py`의 역할
	forms.py는 HTML form의 구조 + 입력 검증 규칙을 파이썬 코드로 정의하는 곳

즉,
- 템플릿에 `<form>` 태그를 쓰긴 하지만
- 그 안의 입력 규칙은 forms.py가 책임집니다.

`forms.py`에서 
- 서버 측 입력 길이 검증
- 너무 긴 입력 차단
- 보안 + 안정성 
이것을 forms.py에서 작성했으므로 탬플릿에서 안써도 됩니다.

검증로직 예시: 이런식으로 검증을 하는 부분을 
```html
{% if text|length > 500 %}
  에러
{% endif %}
```

forms.py가 있으면 검증을 집중할수 있습니다.
```python
if form.is_valid():
    text = form.cleaned_data["text"]
```


템플릿은 forms.py를 직접 모릅니다.
view가 forms.py와 템플릿 사이를 연결해주는 중계자 입니다.

```
[ forms.py ]  ← 입력 규칙 정의
      ↑
      | (import)
[ views.py ]  ← 폼 생성 + 검증 + 결과 전달
      ↓
      | (context)
[ template ]  ← 화면 렌더링
```
- 템플릿은 forms.py를 직접 import하지 않습니다.
- 항상 views.py를 통해서만 연결됩니다.

`sentiment/views.py`
```python
# Django에서 제공하는 FormView (폼 처리 전용 클래스 기반 뷰)
from django.views.generic.edit import FormView

# 우리가 만든 입력 폼 (사용자가 문장을 입력하는 폼)
from .forms import SentimentForm

# Hugging Face 모델 로딩 함수 (감정분석 모델 반환)
from .hf_model import get_classifier


class PredictView(FormView):
    """
    감정 분석 예측용 뷰

    FormView는:
    - GET 요청 → 빈 폼 화면 보여줌
    - POST 요청 → 폼 검증 후 form_valid / form_invalid 실행
    """

    # 어떤 HTML 템플릿을 사용할지 지정
    template_name = "sentiment/predict.html"

    # 어떤 Form 클래스를 사용할지 지정
    form_class = SentimentForm

    def form_valid(self, form):
        """
        폼 검증이 성공했을 때 실행되는 함수

        즉,
        사용자가 입력한 값이 유효할 때만 여기로 들어옴
        """

        # 사용자가 입력한 text 값을 꺼냄
        # cleaned_data = 검증 & 정제 완료된 안전한 데이터
        text = form.cleaned_data["text"]

        # Hugging Face 감정분석 모델 로딩
        classifier = get_classifier()

        # 모델에 입력 텍스트 전달 → 예측 수행
        out = classifier(text)

        # HF pipeline 결과는 대부분 리스트 형태
        # 예: [{'label': 'POSITIVE', 'score': 0.98}]
        if isinstance(out, list) and out:
            out = out[0]  # 첫 번째 결과만 사용

        # 템플릿으로 전달할 결과 데이터 구성
        result = {
            "input": text,                       # 입력 문장
            "label": out.get("label"),            # 예측 라벨
            "score": float(out.get("score", 0.0)) # 신뢰도 점수
        }

        # ✅ 매우 중요한 부분
        # 일반 FormView는 성공 시 redirect 하는 경우가 많지만
        # 여기서는 redirect 하지 않고 같은 화면 다시 렌더링

        return self.render_to_response(
            self.get_context_data(
                form=form,     # 기존 폼 유지
                result=result  # 예측 결과 추가
            )
        )
```

</> 의사코드
```
클래스 PredictView는 FormView를 상속한다

1. 사용할 템플릿 파일을 지정한다
   - 감정 분석 결과를 보여줄 HTML 페이지

2. 사용할 폼 클래스를 지정한다
   - 사용자가 텍스트를 입력하는 SentimentForm

3. 사용자가 폼을 제출하고
   입력값이 유효하면 form_valid()가 실행된다

   3-1. 폼에서 사용자가 입력한 텍스트를 꺼낸다

   3-2. 허깅페이스 감정분석 모델을 불러온다

   3-3. 입력된 텍스트를 모델에 전달해 감정 분석을 수행한다

   3-4. 모델의 결과가 리스트라면
        첫 번째 결과만 꺼내어 사용한다

   3-5. 화면에 보여줄 결과 데이터를 정리한다
        - 원본 입력 문장
        - 예측된 감정 라벨
        - 예측 점수

   3-6. 페이지 이동(redirect)은 하지 않고
        같은 템플릿을 다시 렌더링한다

   3-7. 폼과 분석 결과를 함께 템플릿으로 전달한다
```
