한 줄 요약
- 바로 써보고 서비스에 붙이고 싶다  
    → Hugging Face (사전학습 모델 활용)
    
- 모델 구조를 이해하고 커스터마이징·연구까지 하고 싶다  
    → GitHub (학습 코드·논문 구현 분석)

1️⃣ Hugging Face를 사용하는 경우 (실무에서 가장 흔함)

언제 쓰는가?
- AI 기능을 빠르게 서비스에 적용해야 할 때
- 모델 성능보다 **서비스 완성도·속도**가 더 중요한 단계
- AI를 직접 만들었다보다 AI를 제품에 잘 통합했다가 중요한 경우

장점
- 이미 학습된 모델이 수백~수천 개
- 5~10줄 코드로 바로 테스트 가능
- 표준 인터페이스(`pipeline`) 제공
- FastAPI / Django에 바로 연결 가능
- 모델 교체가 쉬워 A/B 테스트에 유리

---
2️⃣ GitHub는 언제 쓰는 게 좋을까?
- 모델을 직접 학습하거나 재학습(fine-tuning) 해야 할 때
- 데이터 전처리·loss·training loop를 깊이 이해하고 싶을 때
- 논문 구현, 연구, 모델 성능 개선이 목적일 때

장점
- 모델 학습의 전체 과정을 볼 수 있음
- 데이터 파이프라인 구조 이해 가능
- 커스터마이징 자유도 높음
- 연구·실험에는 필수

❌ 단점 (플랫폼 초반 단계에서는)
- 실행 안 되는 코드가 많음
- 라이브러리·CUDA·버전 충돌 빈번
- 재현 환경 맞추는 데 시간 소모 큼
- 왜 안 돌아가지?에 하루 이상 소요 가능
    
📌 그래서 실무에서는
	바로 서비스에 붙일 때 GitHub부터 보지 않는다

---
3️⃣ 실무에서 가장 많이 쓰는 추천 조합

✅ 표준적인 실전 구조
```
Hugging Face (모델)
        ↓
FastAPI (AI 서빙 API)
        ↓
Django (플랫폼 / 서비스 로직)
```

이 구조의 장점
- AI와 서비스 로직 분리 → 유지보수 쉬움
- 모델 교체·확장 용이
- 포트폴리오 설명이 명확함
- 실제 서비스 아키텍처와 거의 동일
- 팀 협업 시 역할 분리 가능

결론 (실무 관점 정리)
- AI를 만드는 것보다
- AI를 제품에 잘 넣는 것이 더 중요한 단계에서는
    
👉 Hugging Face → FastAPI → Django가 가장 현실적인 선택

그리고 이후에:
- 성능이 부족해지면 → GitHub 코드 분석
- 데이터가 쌓이면 → Fine-tuning 진행
    
이 흐름이 실무에서 가장 많이 쓰이는 AI 도입 방식입니다.
