작업 목적

실제 센서 장비와 작업자 위치 추적 장치가 아직 연결되지 않은 상태에서도  
관제 화면, 차트, 지도, 지오펜스, 알람 로직이 정상적으로 동작하는지 검증할 수 있도록  
실시간처럼 보이는 시뮬레이션 데이터를 생성한다.

1단계에서는 실제 데이터 연동보다  
시스템 전체 흐름이 끊기지 않고 동작하는지 확인하는 것이 더 중요하므로,  
센서 수치와 작업자 이동 좌표를 난수 기반으로 생성하여  
UI, 실시간 통신, 상태 표시, 알람 발생 조건을 모두 테스트할 수 있게 한다.

---
작업 내용

1. 센서 데이터 시뮬레이션 구조 정의
- 실제 문서에 정의된 센서 구조를 기준으로 가짜 데이터를 생성한다.
- 유해가스 센서 9종(CO, H2S, CO2, O2, NO2, SO2, O3, NH3, VOC) 및 전력 데이터(전류, 전압, 전력량)를 JSON 형태로 만든다.
- 각 센서값은 무작위로 완전히 튀는 값만 만들지 말고, **정상 범위를 기본으로 하되 일부 구간에서 주의/위험 상태가 발생하도록** 설계한다.
- 즉, 단순 랜덤이 아니라 **“테스트 가능한 패턴 랜덤”** 형태로 작성해야 한다.

2. 센서 장비별 고정 위치와 측정값 분리
- 센서는 지도 위에 고정된 위치를 갖고 있으므로, 장비의 좌표는 고정값으로 관리한다.
- 실제로 랜덤으로 바뀌는 것은 센서의 측정값이며, 장비 위치 자체는 매번 변하지 않도록 한다.
- 예를 들어 센서 A는 공장 북쪽 구역, 센서 B는 설비 주변처럼 고정 배치하고, 그 장비가 보내는 수치만 주기적으로 변경한다.
- 이렇게 해야 지도 시각화와 센서 상태 변화가 자연스럽게 보인다.

3. 작업자 위치 시뮬레이션
- 작업자 좌표는 고정이 아니라 일정 범위 내에서 이동하는 점(point)으로 생성한다.
- 매 주기마다 이전 좌표 기준으로 조금씩 움직이는 방식으로 구현하여 실제 이동처럼 보이게 한다.
- 무작위 점프가 아니라 **연속 이동**처럼 보이도록 해야 지도에서 자연스럽다.
- 작업자 수는 1명부터 시작하고, 이후 2~3명 이상으로 확장 가능하게 설계한다.

4. 데이터 생성 주기 정의
- 센서 데이터와 작업자 위치 데이터의 생성 주기를 명확히 정한다.
- 예:
    - 센서 데이터: 1초 또는 3초 주기
    - 작업자 위치: 1초 주기
- 너무 빠르면 UI가 불안정해지고, 너무 느리면 실시간성이 떨어지므로  
    1단계에서는 **1초 단위 갱신**을 기준으로 테스트하는 것이 적절하다.

5. 정상 / 주의 / 위험 패턴 시뮬레이션
- 단순 난수만 생성하면 알람 테스트가 어렵기 때문에, 일정 주기마다 위험 상황이 의도적으로 발생하도록 패턴을 넣는다.
- 예:
    - 평상시: 정상 범위
    - 30초마다 특정 센서값 상승
    - 작업자가 위험구역에 진입한 상태에서 임계치 초과
- 이 방식으로 UI 색상 변경, 알람 발생, 이벤트 기록을 반복적으로 검증할 수 있다.

6. 실시간 송신 구조 연결
- 생성된 가짜 데이터는 FastAPI에서 WebSocket 또는 API 응답 형태로 프론트에 전달한다.
- 프론트는 이를 받아 차트, 지도, 카드, 알람 리스트를 갱신한다.
- 즉, 가짜 데이터 생성은 단순 콘솔 출력이 아니라 **실제 시스템 데이터 흐름에 태워야 한다.**

7. 테스트용 시나리오 데이터 구분
- 가짜 데이터는 최소 3가지 모드로 준비하는 것이 좋다.
    1. 정상 상태 전용
    2. 주의/위험 혼합 상태
    3. 특정 이벤트 강제 발생 상태
- 이렇게 구분하면 발표, 시연, 테스트 상황에 따라 원하는 흐름을 쉽게 재현할 수 있다.

---
세부 작업 순서

STEP 1. 센서 데이터 포맷 정의
- 문서에 정의된 필드를 기준으로 JSON 구조를 먼저 확정한다.
- 예: `device_id`, `timestamp`, `co`, `h2s`, `o2`, `current`, `voltage`, `watt`, `status`

STEP 2. 센서 장비 목록과 고정 좌표 준비
- 센서별 device_id와 위치 좌표를 미리 정의한다.
- 지도에 표시되는 센서와 데이터 생성기의 센서 ID가 반드시 일치해야 한다.

STEP 3. 기본 랜덤 생성 함수 작성
- 각 센서값을 범위 내에서 랜덤 생성하는 함수를 작성한다.
- 정상 범위 중심으로 값을 생성하고, 일부 확률로 경고 구간에 진입하도록 한다.

STEP 4. 작업자 이동 로직 작성
- 시작 좌표를 하나 정한 뒤, 매 주기마다 x, y 값을 소폭 이동시키는 방식으로 구현한다.
- 이동 범위는 공장 이미지 좌표 범위를 벗어나지 않도록 제한한다.

STEP 5. 상태 판단 필드 추가
- 생성된 값이 임계치 기준으로 정상 / 주의 / 위험 중 어느 상태인지 계산하여 함께 넣는다.
- 프론트는 이 status 값을 바로 사용해 색상과 알람 표시를 바꿀 수 있다.

STEP 6. WebSocket 송신 연결
- 1초마다 생성된 데이터를 WebSocket으로 브라우저에 전달한다.
- 브라우저는 이를 받아 차트, 카드, 지도, 이벤트 영역을 갱신한다.

STEP 7. 이벤트 강제 발생 시나리오 추가
- 특정 시점에 센서값 상승, 작업자 위험구역 진입, 전력 이상 등 이벤트를 일부러 발생시키는 모드를 추가한다.
- 발표 및 검증 시 매우 유용하다.

STEP 8. 로그 및 재현성 확인
- 콘솔 또는 로그 파일에 생성 데이터를 남겨, UI와 실제 송신 데이터가 일치하는지 점검한다.
- 동일 시나리오를 재실행할 수 있도록 seed 또는 시나리오 모드를 둘 수도 있다.

상태 생성 기준 예시

가짜 데이터도 실제 임계치 문서를 참고하여 정상/주의/위험 상태를 만들도록 한다.  
예를 들어 CO, H2S, O2, VOC 등은 문서에 정의된 임계치 기준으로 상태를 분류할 수 있다.

예:
- CO 25 미만 → 정상
- CO 25~200 → 주의
- CO 200 이상 → 위험

이 기준을 가짜 데이터 생성기 안에 함께 넣어 두면,  
프론트와 알람 로직 테스트가 훨씬 쉬워진다.

---
완료 기준
- 센서 데이터가 정해진 주기마다 지속적으로 생성된다.
- 작업자 위치가 지도 위에서 자연스럽게 이동한다.
- 프론트 차트, 카드, 지도, 알람 영역에 데이터가 반영된다.
- 정상 / 주의 / 위험 상태가 반복적으로 나타나 UI 테스트가 가능하다.
- 특정 시점에 강제로 위험 상황을 만들 수 있다.
- 데이터 구조가 실제 연동 시 사용할 포맷과 크게 다르지 않게 유지된다.
- 새로고침 후에도 데이터 생성기가 다시 동작하고 UI와 재연결된다.

주요 산출물
- 가짜 센서 데이터 생성 스크립트
- 작업자 이동 시뮬레이션 스크립트
- WebSocket 송신 모듈
- JSON 샘플 데이터
- 임계치 기반 상태 분류 로직
- 테스트 시나리오 문서 (정상 / 주의 / 위험 / 강제 이벤트)
- 로그 확인용 테스트 출력

---
작업 시 주의사항
- 단순히 랜덤 값만 생성하면 테스트가 어려우므로, **의도된 이벤트가 발생하는 패턴**을 반드시 포함해야 한다.
- 센서 위치는 고정, 측정값만 변동되도록 해야 지도 표현이 자연스럽다.
- 작업자 위치는 순간이동이 아니라 연속 이동처럼 보여야 한다.
- 프론트에서 사용하는 JSON 구조와 생성기에서 보내는 구조를 반드시 일치시켜야 한다.
- 센서 데이터 생성 주기와 WebSocket 송신 주기를 동일하게 맞추는 것이 디버깅에 유리하다.
- 실제 문서에 정의된 필드명과 단위를 최대한 맞추는 것이 좋다. 센서 필드 구조와 전송 주기(예: 1분 1회 정의)는 문서에 정리되어 있으므로, 1단계에서는 이를 축약한 실시간 테스트 버전으로 해석해 적용하면 된다.
- 발표용 또는 검증용으로 “위험 상황 재현 모드”를 준비해 두면 시연 품질이 크게 좋아진다.
