#### B. Django + DRF 구조 기능
이 파트는 단순 기능 구현이 아니라 백엔드 설계 능력을 보여주는 핵심 영역입니다.
```
코드를 잘 짜는 것이 아니라  
구조를 어떻게 나누고 설계했는가를 보여주는 단계입니다.
```

✔️ 반드시 구현해야 할 구조 요소
	아래 항목은 반드시 포함해야 합니다.

- Django Template와 DRF API 분리
- Serializer 설계
- APIView 또는 ViewSet 활용
- 앱 단위 분리
- static / js 분리
- 템플릿 구조 정리

###### 구조를 어떻게 이해해야 하는가
	구성 요소 역할

| 구성         | 역할               |
| ---------- | ---------------- |
| Model      | DB 구조 정의         |
| Serializer | DB ↔ JSON 변환     |
| View       | 요청 처리 + DB 접근 제어 |
| Template   | 화면 출력            |
✔️ 한 줄 핵심 정리
```
Model → 데이터 저장  
Serializer → 데이터 변환  
View → 데이터 처리  
Template → 사용자에게 보여주기
```

🔧 실제 구현 기준 (중요)

`1.` Django Template vs DRF API 분리

반드시 분리해야 합니다.
- Template  
    → 화면 렌더링 전용
- DRF API  
    → 데이터 처리 전용

❌ View에서 HTML + JSON 같이 처리하지 않는다    
✔️ 역할을 분리한다

---
`2.` Serializer 설계

반드시 작성해야 하는 핵심 요소
- Model 기반 Serializer 생성
- 입력값 검증 로직 포함
- 출력 데이터 구조 정의

Serializer = 데이터의 입구 + 출구

---

`3.` View 설계 (APIView / ViewSet)

둘 중 하나 선택해서 사용
- APIView → 직접 제어 (초보자 추천)
- ViewSet → 자동 CRUD 구성

중요: View는 "비즈니스 로직 위치"

---

`4.` static / js / Template 분리

프론트 구조도 반드시 정리
- static
    - css / js 파일 관리
- templates
    - HTML 구조

❌ HTML에 JS 직접 작성하지 않는다    
✔️ JS는 static으로 분리

#### C. 데이터베이스 기능

🔹 개요
이 영역은 단순히 데이터를 저장하는 것이 아니라,  
서비스 전체 구조를 설계하는 능력을 보여주는 핵심 파트입니다.

```
백엔드 = DB 설계  
기능 = DB 관계를 기반으로 동작
```

---
1. 기본 DB 환경 구성
✔️ 개발 단계 → 실무 단계 흐름
```
- SQLite로 시작 (개발 편의)  
    → 초기 개발 단계에서 빠르게 테스트 및 기능 구현
- PostgreSQL로 전환 (실무 환경)  
    → 실제 서비스 환경을 고려한 DB 구조 및 성능 경험
```

✔️ PostgreSQL 전환 기준 (매우 중요)

다음 조건이 충족되면 전환합니다.
- 핵심 모델 설계 완료
- CRUD 기능 완성
- 모델 구조 변경이 거의 없는 상태

✔️ 전환 체크포인트 (권장 작업 순서)
```
1. .env로 DB 설정 분리  
2. settings.py DB 설정 분리  
3. migration 파일 정리  
4. PostgreSQL 연결  
5. migrate 실행  
6. 기존 기능(E2E) 정상 동작 확인
```

3. 기본 데이터 구조 (서비스 데이터)

✔️ 전체 구조
```
User
  ↓
핵심 데이터 (중심 모델)
  ↓
 ├─ 파일
 ├─ 댓글
 ├─ 좋아요 / 북마크
 ├─ 태그 / 카테고리
```

✔️ 구조 설명
```
- User - 핵심 데이터(중심이 되는 모델)  
    → 모든 데이터의 시작점 (작성자, 소유자)
- 핵심 데이터(중심이 되는 모델) - 첨부파일  
    → 이미지, 문서 등 업로드 파일 연결
- 핵심 데이터(중심이 되는 모델) - 댓글  
    → 사용자 상호작용 구조
- 핵심 데이터(중심이 되는 모델) - 좋아요 / 북마크  
    → 사용자 행동 데이터
- 핵심 데이터(중심이 되는 모델) - 태그 / 카테고리  
    → 분류 및 검색 구조
```

✔️ 한 줄 핵심
```
모든 데이터는 핵심 모델을 중심으로 연결된다
```

4. 파일 저장 구조 설계

✔️ 기본 원칙
```
파일은 DB에 저장하지 않는다
```

✔️ 저장 방식
```
→ 파일은 로컬 또는 클라우드(S3 등)에 저장  
→ DB에는 파일이 아니라 경로를 저장  
→ 다중 업로드 및 확장 가능한 구조 설계
```

✔️ 설계 기준
```
- 다중 업로드 가능 구조
- 확장 가능 구조 (S3 연동 고려)
```

5. 데이터 보존 정책
- Soft Delete 또는 데이터 보존 정책  
    → 데이터를 물리적으로 삭제하지 않고 상태값으로 관리  
    → 삭제 / 복구 / 감사 로그 등을 고려한 설계
```python
is_deleted = models.BooleanField(default=False)  
deleted_at = models.DateTimeField(null=True, blank=True)  
deleted_by = models.ForeignKey(User, null=True, blank=True, on_delete=models.SET_NULL)
```

🔥 Soft Delete 기준 (보완)

#### 3차 단계 최종 수락 기준(Definition of Done)
이 기준은 단순 완료가 아니라

```
기능 구현 완료 ≠ 프로젝트 완료    
검증 가능한 상태가 되어야 완료입니다
```

###### ✔️ 기능 DoD (필수 기능 완료 기준)
	다음 기능이 인증된 사용자 기준으로 정상 동작해야 합니다.

필수 동작 조건
- 핵심 도메인 CRUD (생성 / 조회 / 수정 / 삭제)
- 사용자 상호작용 기능 (댓글 / 좋아요 / 북마크 등)
- 이미지 또는 파일 업로드
- 검색 / 필터링 기능
- 페이지네이션 적용

관리자 기능 기준
- 관리자 페이지에서 최소 3개 모델 관리 가능해야 함
    - 생성(Create)
    - 조회(Read)
    - 수정(Update)
    - Soft Delete 상태 확인
