### 발표 가이드

발표의 목적
```
첫째, 왜 이 관제 플랫폼이 필요한가  
둘째, 3차 단계에서 실제로 무엇이 동작하는가
```
이 프로젝트는 산업 현장에서 발생할 수 있는 유해가스, 전력 이상, 작업자 위치 위험 등을 통합하여 운영자가 한 화면에서 파악하고 대응할 수 있는 관제 플랫폼을 만드는 것이 목적입니다.

또한 전체 전략은 다음처럼 나뉘어 있습니다.
```
1단계 = 보여주는 것 (UI + 데이터 흐름)  
2단계 = 살아있는 시스템 (AI + 모니터링 + 운영)
```
따라서 3차 발표의 핵심은 보이게 만들었는가입니다.  
즉, Figma 기반 화면, 실시간처럼 보이는 데이터, 지오펜스 판단, 알람 흐름이 실제로 연결되어 보여야 합니다.

발표에서 가장 중요하게 봐야 하는 기준
	이번 발표에서는 아래 4가지를 중심으로 설명하는 것이 좋습니다.

(1) 이 프로젝트가 무엇을 해결하는지
- 어떤 산업 현장 문제를 해결하려는지
- 왜 관제 플랫폼이 필요한지
- 단순 모니터링이 아니라 왜 사전 감지/예방이 중요한지

(2) 3차 단계의 범위가 무엇인지
- 3차는 AI/모니터링/운영 완성이 아니라
- UI + 데이터 흐름 + 지오펜스 + 알람이 핵심이라는 점
- 실제 데이터가 아니라 “실시간처럼 보이는 구조”를 만드는 단계라는 점

(3) 핵심 흐름이 실제로 연결되는지
- 가짜 데이터 생성
- WebSocket 전송
- 프론트 실시간 반영
- 서버 판단
- 알람 발생

(4) 구조를 어떻게 나눴는지
- FastAPI는 가짜 데이터 생성/실시간 송신
- Django는 저장/판단
- Template + Chart.js + Leaflet은 시각화
- 각 역할이 어떻게 연결되는지

이 네 가지를 중심으로 발표하면, 단순 시연이 아니라 기획 + 구조 + 흐름 + 결과물이 모두 보이게 됩니다.

시스템 구조 설명
	이번 프로젝트는 기능보다 흐름 구조가 더 중요합니다.

핵심구조:
```
Template + Chart.js + Leaflet
        ↑
     WebSocket
        ↑
    FastAPI (가짜 데이터)
        ↓
     Django (저장/판단)
```
또는 큰 구조로는 아래처럼 설명할 수 있습니다.
```
[가짜 센서/위치 데이터] → [WebSocket 실시간 전송] → [Django 저장/판단] → [대시보드/지도 반영] → [알람 표시]
```
3차 발표에서는 AI 분석은 필수 설명 대상이 아닙니다.  
이번 발표의 핵심은 가짜 데이터 생성 → 실시간 전송 → 화면 반영 → 서버 판단 → 알람 표시 흐름이 실제로 보이게 동작하는가입니다.

발표에서 반드시 설명해야 하는 핵심 기능
	이번 발표에서 가장 중요하게 다뤄야 하는 기능은 아래 6개입니다.

(1) 대시보드 UI
- Figma 기반 화면 구현
- 차트가 정상적으로 보이는지
- 데이터가 들어왔을 때 UI가 갱신되는지

완료 기준:
- 페이지 로딩 시 그래프 출력
- 데이터가 일정 주기로 갱신됨

---
(2) 지도 + 지오펜스
- 공장 이미지 기반 좌표계
- Leaflet을 이용한 지도 구현
- 폴리곤 기반 지오펜스 생성
- 센서 위치 표시

완료 기준:
- 클릭으로 지오펜스 생성 가능
- 지도에 센서 위치 표시 가능

---
(3) 가짜 데이터 생성
- 센서 데이터가 랜덤으로 생성되는지
- 작업자 위치가 이동하는 것처럼 보이는지
- 정적인 화면이 아니라 살아 있는 화면처럼 보이는지

완료 기준:
- 데이터가 지속적으로 변함
- UI에 반영됨

---
(4) 실시간 통신
- FastAPI에서 WebSocket으로 데이터를 보내는지
- 프론트가 이를 정상적으로 수신하는지
- 끊김 없이 흐름이 유지되는지

완료 기준:
- 실시간 수신 확인
- 프론트 실시간 반영 확인

---
(5) 지오펜스 판단 로직
- 위치가 지오펜스 내부인지 판단
- 센서값이 임계치를 넘는지 비교
- 조건 만족 시 알람 발생

핵심 로직:
if 위치 ∈ 지오펜스 AND 값 > 임계치:  
    알람

이 부분이 프로젝트의 핵심 가치입니다.  
단순히 데이터를 보여주는 것이 아니라 **판단 로직이 실제로 작동한다**는 점을 보여줘야 합니다.

---
(6) 알람 UI
- 위험 시 색상 변화
- 이벤트 리스트 반영
- 실시간 경고 표현

완료 기준:
- 조건 충족 시 UI에서 알람 확인 가능

기술 스택 설명
	왜 이 기술을 썼는지 역할 중심으로 설명

예시 구성:
- FastAPI: 가짜 센서 데이터 생성 및 WebSocket 전송
- Django + DRF: 데이터 저장, 이벤트 처리, 지오펜스/알람 판단
- Template + Chart.js: 대시보드 시각화
- Leaflet.js: 공장 지도, 센서 위치, 지오펜스 시각화
- PostgreSQL: 데이터 저장 구조
- Redis / Celery / AI / Prometheus: 4차 확장 예정

필수 자료
- 프로젝트 개요 1장
- 시스템 구조도 1장
- 대시보드 UI 화면
- 지도 + 지오펜스 화면
- 데이터 흐름 설명 자료
- 알람 발생 흐름 설명 자료

있으면 좋은 자료
- 역할 분담표
- JSON 인터페이스 예시
- 향후 4차 확장 방향 1장

역할 분담표에 관하여 팀 발표 역할 설명
도메인 기반 개발 또는 데이터 흐름 기준 역할 분배

데이터 흐름 기준으로 역할 분배한 팀 (예시)
- UI 담당: 대시보드, Chart.js, 화면 통합
- 지도 담당: Leaflet, 좌표계, 지오펜스
- 데이터 담당: 랜덤 센서/위치 데이터 생성
- 통신 담당: WebSocket 연결
- 로직 담당: 지오펜스 판단, 임계치 비교, 알람 처리

도메인 기준으로 역할 분배한 팀 (예시)
1번 — accounts 담당  
담당 범위
- 로그인 / 로그아웃
- 사용자 계정 관리
- 권한 처리
- 관리자/운영자 계정 구분

역할 특징
- 시스템의 시작점
- 누가 어떤 화면과 기능에 접근할 수 있는지 제어
- 다른 도메인의 공통 사용자 기준 제공

---
2번 — facilities 담당  
담당 범위
- 사업장 / 건물 / 층 / 구역
- 위치 노드
- 작업자
- 작업자 위치
- 지오펜스

역할 특징
- 공간 구조를 담당하는 핵심 도메인
- 지도, 작업자 위치, 위험구역의 기준이 되는 영역
- 관제 화면의 공간 정보 기반 제공

---
3번 — monitoring 담당  
담당 범위
- 센서 장비 정보
- 유해가스 데이터
- 전력 데이터
- 실시간 측정값
- 장비 상태 로그
- 임계치 정책

역할 특징
- 관제 시스템의 원천 데이터 담당
- 센서와 측정값을 관리하는 중심 도메인
- 대시보드와 알람 도메인에 데이터를 공급하는 역할

---
4번 — alerts 담당  
담당 범위
- 알람 규칙
- 이벤트 발생
- 위험 판단
- 이벤트 이력
- 조치 이력

역할 특징
- 이 프로젝트의 핵심 가치 영역
- 단순 데이터 저장이 아니라  
    위험한지 아닌지를 판단하는 도메인
- monitoring, facilities, accounts와 연결되어 실제 서비스 기능을 완성함

---
5번 — dashboard 담당  
담당 범위
- 관리자 대시보드
- 차트 / 통계 / 위젯
- 화면용 집계 조회
- 관제 화면 출력

역할 특징
- 최종 결과물을 사용자에게 보여주는 도메인
- 원천 데이터 저장이 아니라  
    여러 도메인의 결과를 모아서 시각화하는 역할
- 발표 시 가장 눈에 보이는 결과를 담당

※ 아래 6개 기능은 각각 따로 설명하는 것도 좋지만,  
발표에서는 “데이터 생성 → 통신 → 화면 반영 → 판단 → 알람” 흐름으로 묶어서 시연하는 것이 가장 중요합니다.

---
도메인 기준 역할 분배의 장점
- 각자 맡은 범위가 명확합니다.
- 모델, API, 화면 연결 책임이 분명합니다.
- 기능별 랜덤 분배보다 충돌이 적습니다.
- 나중에 발표할 때도 “내가 맡은 도메인”을 설명하기 쉽습니다.
- 실제 현업에서도 센서별 분리보다  
    공간 / 모니터링 / 알람 / 대시보드 같은 도메인 기준 분리가 더 안정적일 수 있습니다.

가산점 적용 규칙
- 가산점은 구현 + 시연 + 설명이 모두 확인된 경우만 인정합니다.
- 단순히 코드만 존재하거나 발표에서 보여주지 못하면 인정하지 않습니다.
- 가산점 총합은 최대 +10점까지만 반영합니다.
